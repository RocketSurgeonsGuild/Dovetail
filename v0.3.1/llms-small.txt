# Dovetail

> Joint-driven application wiring for .NET. AOT-safe, zero runtime reflection.

AOT & Trim Safe Generated code requires zero runtime reflection — fully compatible with .NET Native AOT and IL trimming. Module Wiring Define services, configuration, logging, and hosting as assembly-level joints resolved at build time by a Roslyn source generator. Composable First-class support for Generic Host, ASP.NET Core, Autofac, DryIoc, Serilog, and .NET Aspire — all wired automagically.

# Dovetail Context

> The context object passed to every joint — how to create, configure, and query it.

# Dovetail Contexts [Section titled “Dovetail Contexts”](#dovetail-contexts) The joint context is the the result of collecting all the known joints for a given set of assembly. How those assemblies are collected can diff depending on on the joint context is created. Generally the joint context is created using the <xref:Joinery.Dovetail.DovetailContextBuilder> however you can implement your own <xref:Joinery.Dovetail.IDovetailContext> if you wish. ## Builder [Section titled “Builder”](#builder) A joint context is created from a <xref:Joinery.Dovetail.DovetailContextBuilder>. This class is used during the bootstrapping phase of your application. You can add joints manually, you can add them via attribute scanning, you can disable attribute scanning if you wish as well. ## Creating the context [Section titled “Creating the context”](#creating-the-context) A context can be created from a <xref:Joinery.Dovetail.DovetailContextBuilder> by using [DovetailContext.From](xref:Joinery.Dovetail.DovetailContext#Joinery_Dovetail_DovetailContext_From_Dovetail_DovetailContextBuilder_). ## Using the context [Section titled “Using the context”](#using-the-context) Once the context is created you can use the context to find out all sorts of information. Useful properties: * [`AssemblyProvider`](xref:Joinery.Dovetail.IDovetailContext#Joinery_Dovetail_DovetailContext_AssemblyProvider) - The type provider can be used to get a list of assemblies * [`Logger`](xref:Joinery.Dovetail.IDovetailContext#Joinery_Dovetail_DovetailContext_Logger) - This is a diagnostic logger that can be used for logging details. If a logger is provided to the builder it will be used here. * [`Properties`](xref:Joinery.Dovetail.IDovetailContext#Joinery_Dovetail_DovetailContext_Properties) - Contains all the properties provided to the builder. This implements `IServiceProvider` and can be used with \`ActivatorExtensions Useful methods / extension methods: * [`Get<T>([string name])`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_Get__1_Dovetail_IDovetailContext_) - Get a given type from the `Properties` dictionary. * [`GetHostType()`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_GetHostType_Dovetail_IDovetailContext_) - Get’s the given host type, as defined in the builder. * [`IsUnitTestHost()`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_IsUnitTestHost_Dovetail_IDovetailContext_) - Tests if the builder was setup for unit testing * This is handy to ensure different behavior during [unit tests](./unit-tests.md).

# Defining Dovetails

> How to create and register your own joints, including ordering and host type filtering.

# Defining Dovetail Joints [Section titled “Defining Dovetail Joints”](#defining-dovetail-joints) As stated previously joints are nothing more than a class that implements <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint>. ## Declaring a new kind of joint [Section titled “Declaring a new kind of joint”](#declaring-a-new-kind-of-joint) Everything below is about writing joints for kinds that already exist, such as `IServiceJoint` or `ISerilogJoint`. A package or application adds a new kind, a typed extension point other code can contribute to, with a single `<DovetailJoint>` item in its project file; the build generates the interface, the delegates and the `Apply` and `DovetailContextBuilder` methods for it. The [`DovetailJoint` reference](../../reference/dovetail-joint/) lists everything the item accepts. The entry points that run the joints come from a [`DovetailHost`](../../reference/dovetail-host/) item, which the SDK declares for most projects. ## Implementing Multiple Dovetail Joints [Section titled “Implementing Multiple Dovetail Joints”](#implementing-multiple-dovetail-joints) A defined joint can implement as many joints as you want. Configuration, Services, Command Line, Custom Dovetail Joints can all be handled by one joint. 
```c#
public class MultipleDovetail : IServiceJoint, IConfigurationJoint
{
    public void Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services) { }
    public void Register(IDovetailContext context, IConfiguration configuration, IConfigurationBuilder builder) { }
}
```
 ## Dovetail Ordering [Section titled “Dovetail Ordering”](#dovetail-ordering) By default the order of joints is [non-deterministic](https://en.m.wikipedia.org/wiki/Nondeterministic_algorithm) and not controlled. Dovetails are “left in place” such that once the list of joints is created it is not changed between runs. Sometimes you want to ensure that one joint runs before another, that can be done using different attributes. Delegate joints *cannot* be ordered in this manner and must be sorted manually. ### [\[BeforeDovetail\]](xref:Joinery.Dovetail.BeforeJointAttribute) / [\[DependentOfDovetail\]](xref:Joinery.Dovetail.DependentOfJointAttribute) [Section titled “\[BeforeDovetail\] / \[DependentOfDovetail\]”](#beforedovetail--dependentofdovetail) This attribute can be used to ensure that your joint is called before another joint. The order is still non-deterministic but Dovetail will ensure that the defined joint is run before the joint type defined by the attribute. 
```c#
// A before B
[BeforeDovetail(typeof(DovetailB))]
public class DovetailA
{
}


public class DovetailB
{
}
```
 ### [\[AfterDovetail\]](xref:Joinery.Dovetail.AfterJointAttribute) / [\[DependsOnDovetail\]](xref:Joinery.Dovetail.DependsOnJointAttribute) [Section titled “\[AfterDovetail\] / \[DependsOnDovetail\]”](#afterdovetail--dependsondovetail) This attribute can be used to ensure that your joint is called after another joint. The order is still non-deterministic but Dovetail will ensure that the defined joint is run after the joint type defined by the attribute. 
```c#
// B before A
[AfterDovetail(typeof(DovetailB))]
public class DovetailA
{
}


public class DovetailB
{
}
```
 ### Custom Attributes [Section titled “Custom Attributes”](#custom-attributes) If you want you can define your own custom attribute for use with joint ordering. Your attribute must implement <xref:Joinery.Dovetail.IDovetailDependency> and specify the <xref:Joinery.Dovetail.DependencyDirection>. ## Dovetail Host Type [Section titled “Dovetail Host Type”](#dovetail-host-type) You can define a joint that only runs for a given <xref:Joinery.Dovetail.HostType>. The HostType can be defined on the <xref:Joinery.Dovetail.DovetailContextBuilder> using `Set<DovetailHostType>(DovetailHostType.UnitTest)`. Using the `DovetailHostType` an assembly can define different behaviors given the context. The generated `Imports` class sets the host type only when the build specifies one. The `DovetailHostType` MSBuild property (`Live` or `UnitTest`) takes precedence; otherwise test projects (`IsTestProject`) get `UnitTest`. Anywhere else the host type is left unset, and the hosting extensions set it to `Live` if nothing else has. A good example of this is designing a system that uses [NodaTime](https://nodatime.org/). You can have a [\[LiveJoint\]](xref:Joinery.Dovetail.LiveJointAttribute) that registers `IClock` using the expected calendar system, and another [\[UnitTestJoint\]](xref:Joinery.Dovetail.UnitTestJointAttribute) that registers a `FakeClock` with a predefined starting date and time. * `Undefined` - The default host type, means the joint runs everywhere. * `Live` - This joint applies in a live running application * `UnitTest` - This joint applies to unit tests. ### [\[LiveJoint\]](xref:Joinery.Dovetail.LiveJointAttribute) [Section titled “\[LiveJoint\]”](#livejoint) This attribute ensures a joint that only runs when the `DovetailHostType` is `Live`. 
```c#
[LiveJoint]
public class DovetailA
{
}
```
 ### [\[UnitTestJoint\]](xref:Joinery.Dovetail.UnitTestJointAttribute) [Section titled “\[UnitTestJoint\]”](#unittestjoint) This attribute ensures a joint that only runs when the `DovetailHostType` is `UnitTest`. 
```c#
[UnitTestJoint]
public class DovetailA
{
}
```
 ### \[DovetailHostType] [Section titled “\[DovetailHostType\]”](#dovetailhosttype) The general form of the two attributes above. It takes the host type the joint applies to, for example `[DovetailHostType(DovetailHostType.Live)]`. It is also the only way to declare `Undefined` explicitly. ### Which attributes are honoured where [Section titled “Which attributes are honoured where”](#which-attributes-are-honoured-where) A joint reaches a context by one of two paths, and both honour all three attributes the same way: | Path | `[LiveJoint]` / `[UnitTestJoint]` | `[DovetailHostType]` | | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- | -------------------- | | Runtime reflection: `DovetailContextBuilder.AppendJoint(...)` / `PrependJoint(...)` with a joint instance or `AppendJoint<T>()` | Honoured | Honoured | | Generated metadata: the joints marked `[DovetailExport]`, which the source generator lists in the generated `Exports` class at build | Honoured | Honoured | On both paths: * `[LiveJoint]` and `[UnitTestJoint]` are read before `[DovetailHostType]`, so `[LiveJoint]` wins over a `[DovetailHostType]` on the same joint. Declaring both `[LiveJoint]` and `[UnitTestJoint]` on one joint isn’t meaningful, and which of them applies is not specified. * The attributes are inherited. A joint that derives from a `[LiveJoint]` class is a live joint too, and the closest declaration wins. * A joint that declares nothing has the `Undefined` host type and applies everywhere, apart from the test project default below. * A joint applies when its host type is `Undefined` or equals the host type of the context. The generated path adds one default of its own. In a test project (`IsTestProject`), an exported joint that declares no host type is exported as `UnitTest`. A joint’s own attribute always takes precedence over that default, so a `[LiveJoint]` in a test project stays live-only and `[DovetailHostType(DovetailHostType.Undefined)]` opts a joint out of the default. The runtime reflection path has no such default. ## Injecting dependencies [Section titled “Injecting dependencies”](#injecting-dependencies) By default joints are a simple class that can be created using `Activator.CreateInstance` however the goal of joints was to allow “bootstrap time” configuration to be provided. The <xref:Joinery.Dovetail.DovetailContextBuilder> acts as a bag of properties using [`indexer`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Item_System_Object_) or [`Properties`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Properties). Any type defined in the context is injectable into any defined joint. This can be used for any number of purposes such as… * allow consumers to provide configuration to your joint * allow joints to communicate or share common state Under the covers the [`Properties`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Properties) implements `IServiceProvider`, and a joint’s constructor parameters are resolved from it. *** 
```c#
public class InjectableDovetail : IServiceJoint
{
    private readonly IInjectData _joint;


    public InjectableDovetail(IInjectData joint) => _joint = joint;


    public void Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services)
    {
        //...
    }
}


public class OptionalInjectableDovetail : IServiceJoint
{
    private readonly IInjectData? _joint;


    public OptionalInjectableDovetail(IInjectData? joint = null) => _joint = joint;


    public void Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services)
    {
        if (_joint is { })
        {
            //...
        }
    }
}
```
 ### How constructor parameters are resolved [Section titled “How constructor parameters are resolved”](#how-constructor-parameters-are-resolved) A joint takes its constructor parameters from the properties of the <xref:Joinery.Dovetail.DovetailContextBuilder> that holds it, in the same way whether the joint is added with `AppendJoint<T>()` or exported with `[DovetailExport]`: * **By type.** Each parameter is looked up under its declared type, exactly: a value stored with `Set<IClock>(clock)` satisfies an `IClock` parameter and not a `SystemClock` one, and the other way round. `?` on a reference type changes nothing, so `IInjectData?` and `IInjectData` find the same value. A nullable value type is looked up as itself: an `int?` parameter is found under `int?`, not `int`. * **Optional parameters fall back to their default.** A parameter with a default value (`IInjectData? joint = null`, `int retries = 3`) gets that default when the properties hold nothing of its type. * **Required parameters must be there.** A parameter without a default whose type is missing makes creating the context throw an `InvalidOperationException`. For an exported joint its message names the missing type, the parameter and the joint. When the context has two or more joints it orders them with a comparer, and .NET wraps whatever a comparer throws, so the exception you catch is an `InvalidOperationException` that says “Failed to compare two elements in the array.” and the one that names the missing type is its `InnerException`. With a single joint the exception is not wrapped. * **At the point the joint is created, not before.** The joint is created the first time something needs it, which is while <xref:Joinery.Dovetail.IDovetailContext> is built, so anything you `Set` on the builder up to that point is seen, including after the joint was added. Values stored later, for example by another joint while it runs, are too late. `ExceptJoint(Type)` needs the joints too, so it creates them when it is called. With two or more joints they are created while the context orders them, before their host types are applied, so a missing required value can fail the context even for a joint that would not have applied. * **One constructor.** An exported joint is created by calling one constructor that is public or internal (`protected internal` counts, the generated code lives in the same assembly). A joint with more than one of those is the `DT0001` error. A joint that has constructors but none of those, for example a single `private` or `protected` one, is the `DT0017` error: it is reported at build time and left out of the exports. Private and protected constructors, and a static constructor, are not counted for `DT0001`. For an exported joint the generator writes this lookup into the `Exports` class as plain C#: the exported method itself takes no parameters, and each joint with constructor parameters is described by a factory that the context builder runs against its properties. Nothing is reflected on, so it is trimming and AOT safe. A joint without constructor parameters is created directly. The same factory is used if you read the `Joint` of that metadata before any builder has it, with the difference that there are no properties then: optional parameters get their defaults and a required one throws. (Joints you add with `AppendJoint<T>()` are created with `ActivatorUtilities`, which does use reflection.) 
```c#
// LaunchPad: a joint that tunes itself from options the host may or may not provide.
[DovetailExport]
public class TimeJoint(PrimitiveOptions? options = null) : IServiceJoint
{
    private readonly PrimitiveOptions _options = options ?? new PrimitiveOptions();


    public void Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services)
    {
        //...
    }
}


// With this set on the DovetailContextBuilder, TimeJoint gets this instance; without it, TimeJoint gets null and uses its own default.
builder.Set(new PrimitiveOptions { /* ... */ });
```

# Host Lifecycle

> Run code when the host is starting, started, stopping and stopped, without writing a hosted service, from an application builder or a service collection.

# Host Lifecycle [Section titled “Host Lifecycle”](#host-lifecycle) A host that runs `IHostedLifecycleService` (the generic host, and so ASP.NET Core) tells its hosted services when it is about to start, has started, is about to stop and has stopped. Most applications only want to run a little code at one of those moments — warm a cache once the host has started, flush a buffer before it stops — and writing a hosted service for that is a lot of ceremony. `Joinery.Dovetail.Hosting` lets you register the code directly: 
```c#
var builder = Host.CreateApplicationBuilder(args);


builder
   .OnHostStarting(provider => Console.WriteLine("Starting"))
   .OnHostStarted(async provider => await provider.GetRequiredService<CacheWarmer>().WarmUpAsync())
   .OnHostStopping(async (provider, cancellationToken) => await provider.GetRequiredService<Outbox>().FlushAsync(cancellationToken))
   .OnHostStopped(provider => Console.WriteLine("Stopped"));


using var host = await builder.ConfigureDovetail();
await host.RunAsync();
```
 An `ASP.NET Core` application does the same on its `WebApplicationBuilder`. ## The methods [Section titled “The methods”](#the-methods) There are four, one per moment, and each comes in three forms: | Method | Runs | `IHostedLifecycleService` method | | ---------------- | ---------------------------------------------- | -------------------------------- | | `OnHostStarting` | before the host starts its hosted services | `StartingAsync` | | `OnHostStarted` | after the host has started its hosted services | `StartedAsync` | | `OnHostStopping` | before the host stops its hosted services | `StoppingAsync` | | `OnHostStopped` | after the host has stopped its hosted services | `StoppedAsync` | | Form | Handler | | ------------ | ------------------------------------------------- | | synchronous | `Action<IServiceProvider>` | | asynchronous | `Func<IServiceProvider, Task>` | | cancellable | `Func<IServiceProvider, CancellationToken, Task>` | The handler gets the host’s service provider. The cancellable form also gets the cancellation token the host passes to the lifecycle method, which follows the token given to `StartAsync` or `StopAsync`. ## From an application builder or a service collection [Section titled “From an application builder or a service collection”](#from-an-application-builder-or-a-service-collection) Every method is an extension of both `IHostApplicationBuilder` (`HostApplicationBuilder`, `WebApplicationBuilder`, …), which returns the builder so the calls chain, and `IServiceCollection`, which returns the service collection. A host built the older way, with an `IHostBuilder`, has no application builder, but it has a service collection: 
```c#
using var host = Host
                .CreateDefaultBuilder(args)
                .ConfigureServices(services => services.OnHostStopped(_ => Console.WriteLine("Stopped")))
                .Build();
```
 A [joint](./defining-joints) registers its handlers the same way, while the application’s services are configured. That is how a library runs code with the host without the application doing anything: 
```c#
[DovetailExport]
public class WarmUpCache : IServiceJoint
{
    public void Register(IDovetailContext context, IServiceCollection services) =>
        services.OnHostStarted(async (provider, cancellationToken) => await provider.GetRequiredService<ICache>().WarmUpAsync(cancellationToken));
}
```
 Handlers have to be registered before the host is built. The first registration adds the hosted service that runs them, so there is nothing else to call, and a project that registers no handler gets no hosted service. ## Handlers of one moment run in parallel [Section titled “Handlers of one moment run in parallel”](#handlers-of-one-moment-run-in-parallel) All the handlers registered for a moment are started together and awaited together (with `Task.WhenAll`), not one after the other, so one slow handler doesn’t hold up the rest. The host moves on to the next step once every one of them has finished. * **Don’t depend on the order** the handlers of one moment run in. The moments themselves are ordered by the host, which calls `StartingAsync` on all its hosted lifecycle services, then `StartAsync` on all of them, then `StartedAsync` on all of them (and likewise `StoppingAsync`, `StopAsync` and `StoppedAsync` when it stops). The handlers of a moment have all finished before the host moves on to the next. * A **synchronous** handler runs to completion when it is started, so synchronous handlers of one moment, which don’t wait for anything, happen to run one after another. Handlers that `await` overlap. * A handler that **throws**, even before its first `await`, fails that step of the host like any hosted service would, and the other handlers of the moment have still been started. * The handlers that run in parallel are those of **one project** (see below): a library and the application that uses it each have a hosted service of their own, and the host runs hosted services one after the other (unless `HostOptions.ServicesStartConcurrently` and `ServicesStopConcurrently` say otherwise). The library’s handlers for a moment therefore run before or after the application’s, not alongside them. ## Where it is available [Section titled “Where it is available”](#where-it-is-available) The methods are emitted by `Joinery.Dovetail.Hosting` into the projects that reference the generic host (`Microsoft.Extensions.Hosting`), the same way it emits its other helpers, and nothing is emitted where the host doesn’t run `IHostedLifecycleService`: | Host | Methods | | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | | Generic host: workers | yes | | ASP.NET Core | yes | | Uno Platform (`Uno.Extensions.Hosting`) | yes: its host is a generic host, so handlers run once the host is started (`NavigateAsync<TShell>()` starts it, `ConfigureDovetail()` doesn’t) | | .NET MAUI | no | | Blazor WebAssembly | no | A .NET MAUI or Blazor WebAssembly project gets none even when `Microsoft.Extensions.Hosting` ends up among its references (another package brought it along, say): methods that compile but never run their handlers would be worse than methods that don’t exist, so calling one is a compile error. The methods are `internal`, as are all the helpers `Joinery.Dovetail.Hosting` emits, so a library that registers handlers needs to reference `Joinery.Dovetail.Hosting` and the generic host itself. ## Each project has its own [Section titled “Each project has its own”](#each-project-has-its-own) Every project that gets the methods gets its own, self-contained copy of them, of the registration they add and of the hosted service that runs it, all `internal` and `[Embedded]`, so no assembly sees another’s. Nothing is shared between projects: * A handler registered with a project’s methods is registered with, and run by, that project’s own hosted service. A library and an application that each register handlers end up with two hosted services, each running only its own project’s handlers, once. * The “first registration adds the hosted service” rule is per project too. It looks for that project’s own registration type in the service collection, so it neither depends on nor notices another project’s registrations. * Projects can’t coordinate on one list of handlers, and there is no single set of handlers that runs in parallel across the library and the application (see above). Handlers that must not run side by side, or in a fixed order, belong in one project, or in a hosted service of their own. * That holds for every way of registering: the application builder, the service collection and a joint all go through the methods of the project they are written in.

# Introduction

> What Dovetail is, why it exists, and when to use it.

# What is Dovetail? [Section titled “What is Dovetail?”](#what-is-dovetail) ![Dovetail overview diagram](https://dummyimage.com/1200x560/0b1220/f8fafc.png\&text=Dovetail+Overview+Architecture) The goal of Dovetail is to be a simple way to bridge the gap between Configuration driven development and Dovetail driven development. In an ASP.NET Core application it is “pay-for-play” in that you must register all your configurations, services, etc. This is great but it also forces you into cases where if you forget to call an extension method nothing lights up like you expected. Another draw back of using extension methods is that any dependencies you need, to configure services for example, must be included in the method call. One thing to keep in mind is that ASP.NET Core just got rid of the [double container](https://github.com/aspnet/Announcements/issues/353) problem, we are not introducing a second container, instead we just implement `IServiceProvider` using the same [dictionary that is provided by `IHostBuilder.Properties`](https://docs.microsoft.com/en-us/dotnet/api/microsoft.extensions.hosting.ihostbuilder.properties). Any services that you inject into your joints must exist inside of this dictionary, or be optional. At a high level Dovetail solves this problem in a very similar way to something like [Autofac Modules](https://autofaccn.readthedocs.io/en/latest/configuration/modules.html) or other similar assembly scanning solutions. Our goal is to be agnostic at a high level, strictly speaking using MSDI/MSEL/MSC is not required however is currently assumed that .NET Platform Extensions are going to be used. In the future this might be broken out. ## Why use Dovetail? [Section titled “Why use Dovetail?”](#why-use-dovetail) You have to make a choice with every library you introduce, and using Dovetail is no different. If it’s not for you, that’s okay! Here are some possible reasons why and why not to use Dovetail. ### Reasons to use? [Section titled “Reasons to use?”](#reasons-to-use) * You can create library code that “just works” without having to ensure that the correct extension method was called, with the correct parameters, for every library you add. * You can don’t have to worry about service registration extension methods in instead each module can setup it’s own registrations. * You can can group bootstrapping logic together to lessen cognitive load. ### Reasons not to use? [Section titled “Reasons not to use?”](#reasons-not-to-use) Everything has it’s positives and negatives. We cannot lie using joints will add time to starting up your application. There is a trade off to be made here and optimizations that can be made to lessen that trade-off. Fundamentally if you’re making a highly focused, and specialized microservice then using Dovetail may not be for you. You will own the burden to ensuring that configuration is done the same, extension methods are called, and everything else. It is called “pay-to-play” after all. #### Note on performance [Section titled “Note on performance”](#note-on-performance) A quick note on performance. We are now using Source Generators to generate export methods, that return all joints for a given assembly. This allows joint loading to have similar performance characteristics to pure extension methods, it’s still slower but reduces the need to assembly scan. The <xref:Joinery.Dovetail.ICompiledTypeProvider> is now generated by source generator at compile time, further reducing the need to assembly scan at runtime. # What is a Dovetail [Section titled “What is a Dovetail”](#what-is-a-dovetail) A joint is nothing but a class that implements the <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint> interface. Nothing special. By itself <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint> is just a marker interface used to identify a class that may implement one more joints. Dovetails are then interfaces that are implemented by the class some examples are: * <xref:Joinery.Dovetail.Configuration.IConfigurationJoint> * <xref:Joinery.Dovetail.DependencyInjection.IServiceJoint> * <xref:Joinery.Dovetail.Logging.ILoggingJoint> * <xref:Joinery.Dovetail.Setup.ISetupJoint> * <xref:Joinery.Dovetail.Hosting.IHostingDovetail> ad-hoc Dovetails (or delegate Dovetails) are a different kind of joint but written as a delegate, but they mirror the method given by the Dovetail interface. These can be used to during program startup just like `ConfigureServices` are used today. Some examples are: * <xref:Joinery.Dovetail.Configuration.ConfigurationJoint> * <xref:Joinery.Dovetail.DependencyInjection.ServiceJoint> * <xref:Joinery.Dovetail.Logging.LoggingJoint> * <xref:Joinery.Dovetail.Setup.SetupJoint> * <xref:Joinery.Dovetail.Hosting.HostingDovetail> ## Exporting a Dovetail [Section titled “Exporting a Dovetail”](#exporting-a-dovetail) A joint can be exported by using the <xref:Joinery.Dovetail.DovetailAttribute> (eg. `[assembly: Dovetail(typeof(MyDovetail))]`). This is important you may want to make joints are **not** enabled by default but are available to be loaded by users if they want to. The rules are straight forward. * A public joint - Will not be loaded unless it is added to the <xref:Joinery.Dovetail.DovetailContextBuilder>. * A public exported joint - Will always be loaded unless excluded by assembly or type in the <xref:Joinery.Dovetail.DovetailContextBuilder>. * A private joint - Will never be loaded. ever. * A private exported joint - Will always be loaded unless excluded by assembly in the <xref:Joinery.Dovetail.DovetailContextBuilder>. # Writing your own custom joints [Section titled “Writing your own custom joints”](#writing-your-own-custom-joints) Creating your own joints is fairly easily, and can be done by using existing joints or by executing it yourself. A package or application that wants to add a new kind of joint declares it with a `<DovetailJoint>` item, and a project the SDK does not recognise declares its host with a `<DovetailHost>` item. Both are listed, with every value they accept, in the [reference](../../reference/): [DovetailJoint](../../reference/dovetail-joint/) and [DovetailHost](../../reference/dovetail-host/).

# Managed Configuration

> Declare a library's configuration as code and get typed options, a reflection-free binder, and a JSON Schema for editors, merged per application.

# Managed Configuration [Section titled “Managed Configuration”](#managed-configuration) A library that ships configuration describes it once, as a C# type. Dovetail’s source generator reads that type and produces two things from the same model: * a **binder** that fills the type from `IConfiguration` and registers it as `IOptions<T>`, with no reflection, so it is AOT and trimming safe; * a **JSON Schema** fragment that describes the type’s section. The build merges the fragments of every referenced library into one schema for the application, which editors use for completion, hover documentation and validation of `appsettings.json`, YAML and TOML files. See [Editor setup](../guides/editor-setup). The library’s default values still ship as an `appsettings` file, which Dovetail packs and copies into hosts ([below](#shipping-default-values)). ## Declaring a section [Section titled “Declaring a section”](#declaring-a-section) Put `[DovetailConfiguration]` on the options class: 
```c#
using System.ComponentModel;
using System.ComponentModel.DataAnnotations;
using Joinery.Dovetail.Attributes;


/// <summary>Options for the greetings this library prints.</summary>
[DovetailConfiguration]
public sealed class GreetingsOptions
{
    /// <summary>What the greeting says before the name.</summary>
    [Description("The text that comes before the name, e.g. \"Hello\".")]
    public string Message { get; set; } = "Hello";


    /// <summary>How many times the greeting is said.</summary>
    [Range(1, 5)]
    public int Repeat { get; set; } = 1;
}
```
 Consume it the usual way, with `IOptions<GreetingsOptions>`, `IOptionsSnapshot<T>` or `IOptionsMonitor<T>`. The generator also exports a joint (`DovetailConfigurationOptions`) that registers the binding in every host that references the assembly, so there is nothing to call. The [`SdkSample.Greetings`](https://github.com/RocketSurgeonsGuild/Dovetail/tree/main/sample/SdkSample/SdkSample.Greetings) project is a working example. ### Types you don’t own [Section titled “Types you don’t own”](#types-you-dont-own) To bind a type from another library, use the generic attribute on the assembly. This registers `HostOptions` under `Hosting`: 
```c#
[assembly: DovetailConfiguration<HostOptions>("Hosting")]
```
 The assembly form is `DovetailConfiguration<T>` and needs C# 11. Descriptions for third-party types come from the XML documentation file that ships with the package, when there is one. ### Section names [Section titled “Section names”](#section-names) | Attribute | Section | | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `[DovetailConfiguration]` | The type name with one `Options`, `Settings`, `Configuration` or `Config` suffix removed: `GreetingsOptions` becomes `Greetings` (in the declared [key style](#key-style)). | | `[DovetailConfiguration("Http:Retry")]` | The path you give. `:` nests sections. Keys are case-insensitive. | | `[assembly: DovetailConfiguration<T>]` | The same rule as the class form, applied to `T`. | There is no prefix. A name that would become empty after stripping the suffix (a class called `Options`) is an error ([`DT0008`](#diagnostics)); give it a path. ### Key style [Section titled “Key style”](#key-style) `KeyStyle` on `[DovetailConfiguration]` (and on `DovetailConfiguration<T>`) picks how the keys of the section are spelled. It is set per attribute; there is no assembly-wide or MSBuild default. There are five values: | `KeyStyle` | What the canonical key is | `MaxFileSizeMb` | `HTTPServer` | `HttpClientOptions` section | | ------------ | ---------------------------------------------------- | ------------------ | ------------- | --------------------------- | | `Undefined` | The declared name exactly as written. The default. | `MaxFileSizeMb` | `HTTPServer` | `HttpClient` | | `Pascal` | The declared name with its first letter upper-cased. | `MaxFileSizeMb` | `HTTPServer` | `HttpClient` | | `Camel` | Lower camel case (`JsonNamingPolicy.CamelCase`). | `maxFileSizeMb` | `httpServer` | `httpClient` | | `Dash` | Lower-case words joined with `-` (`KebabCaseLower`). | `max-file-size-mb` | `http-server` | `http-client` | | `Underscore` | Lower-case words joined with `_` (`SnakeCaseLower`). | `max_file_size_mb` | `http_server` | `http_client` | 
```csharp
[DovetailConfiguration(KeyStyle = ConfigurationKeyStyle.Underscore)]
public class HttpClientOptions // section "http_client"
{
    public int MaxFileSizeMb { get; set; } // key "max_file_size_mb"
    public RetryPolicy Retry { get; set; } = new(); // "retry:max_attempts" through RetryPolicy.MaxAttempts
}
```
 * **`Undefined` respells nothing.** The binder literal, the schema’s `properties` key, the strict closing of the section and the derived section path (after the suffix is stripped) are the names as declared. Configuration keys are case-insensitive, so data in any casing binds, as long as the letters are right: `maxfilesizemb`, `MaxFileSizeMb` and `MAXFILESIZEMB` are the same key. Dashes and underscores are other letters, so `max-file-size-mb` does not match `MaxFileSizeMb`. * **`Pascal` is an explicit style.** It upper-cases the first letter of a declared name. C# property names already start in upper case, so for them `Undefined` and `Pascal` give identical output; they differ for a member declared as `myKey`, which stays `myKey` under `Undefined` and becomes `MyKey` under `Pascal`. * **What it covers.** The key of every bound property and constructor parameter of the options type and of every object type nested in it (in lists and dictionary values too). The generated binder reads those keys, and the schema uses them for `properties`, the case-insensitive `patternProperties` twins and the strict `propertyNames`. * **What it leaves alone.** Dictionary keys, enum values and every other piece of data are never restyled, and neither is an explicit section string (`"Http:Retry"` is used as written, segment by segment). * **Word splitting** is `System.Text.Json`’s: `Camel` is `JsonNamingPolicy.CamelCase`, `Dash` is `JsonNamingPolicy.KebabCaseLower` and `Underscore` is `JsonNamingPolicy.SnakeCaseLower`, so `HTTPServer` is `httpServer`, `http-server` and `http_server`, and `Http2Enabled` is `http2Enabled`, `http2-enabled` and `http2_enabled`. * **`[ConfigurationKeyName]` wins.** An explicit key name is used verbatim, in every style. * **Derived section names** follow the style, after the `Options`, `Settings`, `Configuration` or `Config` suffix is removed: `GreetingsOptions` is `Greetings`, `greetings` and `greetings`; `HttpClientOptions` is `HttpClient`, `httpClient`, `http-client` and `http_client`. * **Case.** Because keys ignore case, `Camel` against `Undefined` or `Pascal` only changes the spelling the schema suggests; `maxFileSizeMb` and `MaxFileSizeMb` bind the same value. `Dash` and `Underscore` change the letters the binder reads: a value written as `MaxFileSizeMb` no longer binds (`max-file-size-mb` or `max_file_size_mb` does), and the schema’s `patternProperties` only accept those keys in any case. * **One spelling per type.** The generated binder exists once for each type, so a type reached from sections that spell its keys differently, such as a `RetryOptions` used by a camel section and a dash section, can’t be bound correctly. The later declaration is reported as [`DT0016`](#diagnostics) and produces nothing, the same way as `DT0015`. The comparison is of the effective keys, not of the style names: `Undefined` and `Pascal` do not conflict on ordinary names, which spell the same keys, but do on a member declared in lower case. Use the same `KeyStyle` for every section that reaches the type, or give the shared type `[ConfigurationKeyName]` attributes (a type whose keys don’t depend on the style isn’t a conflict). Sections with `RegisterOptions = false` bind nothing, so they can’t conflict. ### One section per type [Section titled “One section per type”](#one-section-per-type) A type has exactly one section, so it is declared once. There are two attribute forms: * `[DovetailConfiguration]` (or `[DovetailConfiguration("Section")]`) on the class. It can’t be repeated on a type. * `[assembly: DovetailConfiguration<T>("Section")]` for a type you don’t own. Repeat it for each type; naming the same `T` twice is [`DT0015`](#diagnostics) as well. Declaring a type with both forms is an error ([`DT0015`](#diagnostics)). The diagnostic is reported on the assembly attribute; the class declaration is the one that produces the schema fragment and the registration, and the assembly attribute produces nothing. At run time each library reads only its own section from the application’s complete `IConfiguration`, which the service provider supplies when the options are first created, and creates or binds its options from it. Dovetail doesn’t order, de-duplicate or merge sections. The generated joint registers an assembly’s types by section path, then type name, and the standard options pipeline does the rest. Every type is created by generated code and registered through an `IOptionsFactory<T>`, so your own `Configure<T>`, `PostConfigure<T>` and validators run on the created instance, whenever they were registered. ### Registering by hand [Section titled “Registering by hand”](#registering-by-hand) The generated joint calls one public extension method on `IServiceCollection`, `AddDovetailConfigurationOptions`. You can call it yourself, for example for a type declared with `RegisterOptions = false`. It returns the `OptionsBuilder<TOptions>`, so `Validate` and `ValidateOnStart()` chain as usual. | Overload | Does | | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | | `AddDovetailConfigurationOptions<T>(sectionPath, Func<IConfiguration, T> create)` | Creates the default `T` with `create`, from the section at `sectionPath`, and watches the configuration for reloads. Reflection free, so it is AOT safe. | There is one overload because everything is created through generated create code: for a type with a public parameterless constructor the generator emits `new T()` followed by the bind, and for the rest the constructor or initializer call. No registration path uses reflection. To bind a type with reflection, use Microsoft’s `Configure<T>(IConfiguration)` or `AddOptions<T>().Bind(...)` yourself. * The configuration is the application’s complete `IConfiguration`, resolved from the service provider when the options are first created. `create` receives that configuration’s section at `sectionPath` (such as `Http:Retry`). An empty path throws. * A change token source watches the configuration, so `IOptionsMonitor<T>` and `IOptionsSnapshot<T>` see reloads of the default options. * The call registers an `IOptionsFactory<T>` with `TryAdd`: the first registration for a type wins, and later calls are ignored. A factory your application registers itself wins over Dovetail’s, so `create` is never called for that type. * The factory derives from `OptionsFactory<T>`, so configure and post-configure actions and validators still run on the instance `create` returns. On .NET 11, don’t give such a type asynchronous validators: they fail synchronous validation through a derived factory. ### Named options [Section titled “Named options”](#named-options) Dovetail registers the default options only. Reading a name other than the default, such as `IOptionsMonitor<T>.Get("tenant-a")`, throws an `InvalidOperationException` naming the type and the options name. ### `RegisterOptions` and `ValidateOnStart` [Section titled “RegisterOptions and ValidateOnStart”](#registeroptions-and-validateonstart) | Property | Default | Effect | | ----------------- | ------- | ------------------------------------------------------------------------------------------------------- | | `RegisterOptions` | `true` | `false` only describes the section in the schema. Nothing is registered, so you bind the type yourself. | | `ValidateOnStart` | `false` | Validates the options when the host starts, instead of the first time they are read. | ## Validation [Section titled “Validation”](#validation) Dovetail never turns on `ValidateDataAnnotations`. `[Range]`, `[MinLength]` and the other annotations describe the schema, which is how editors flag a bad value; they are not enforced at run time. To enforce rules, write an `[OptionsValidator]` class, the options validation source generator from `Microsoft.Extensions.Options`: 
```c#
[OptionsValidator]
public sealed partial class GreetingsOptionsValidator : IValidateOptions<GreetingsOptions>;
```
 Dovetail registers every such validator in the assembly for the option types it registers, with `TryAddEnumerable`, so it never duplicates one you added yourself. Add `ValidateOnStart = true` on the attribute and a bad configuration fails the host at startup. ## Supported types [Section titled “Supported types”](#supported-types) The generator follows Microsoft’s configuration binding source generator, not the serializer: * `string`, `bool`, every numeric type (including `Half`, `Int128` and `UInt128`), `char`, enums (any casing), `TimeSpan`, `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly`, `Guid`, `Version`, `Uri`, `CultureInfo`, `byte[]`; * `Nullable<T>` of the above; * nested classes, structs and records, and recursive types (the schema uses `$ref`); * arrays, lists, sets and the other collection types the binder supports, and dictionaries with string, enum or integer keys; * `object` and `IConfigurationSection`, which accept any value. A type with a `[TypeConverter]` is described as an object, because the binder ignores converters. A member the binder can’t bind is left out of both the schema and the binder, with warning [`DT0009`](#diagnostics). `[ConfigurationKeyName]` renames a key (see [Key style](#key-style) for restyling them all), and from binder 11 `[ConfigurationIgnore]` leaves a member out. ### Annotations that reach the schema [Section titled “Annotations that reach the schema”](#annotations-that-reach-the-schema) | Source | Schema | | ------------------------------------------- | --------------------------------------------------------- | | `[Description]`, else the XML `<summary>` | `description`. For a record parameter, its `<param>`. | | `[Range]`, length attributes | `minimum`/`maximum`, `minLength`/`maxLength`, item counts | | `[RegularExpression]` | `pattern`, when the expression can be anchored | | `[Url]`, `[EmailAddress]` | `format` | | `[Obsolete]` | `deprecated` and a deprecation message | | A constant initializer or parameter default | `default`, except an empty string | Ranges and defaults are also written into the description, since editors don’t show them. A default of `""` is skipped, both as `default` and in the description, because “Default: .” tells nobody anything. The XML summary is read from the source whether or not `GenerateDocumentationFile` is on. `<inheritdoc />` and `<include>` produce no description. Annotations that JSON Schema can’t express are dropped with [`DT0013`](#diagnostics). Fragments are permissive: nothing is `required` unless you set `<DovetailConfigurationSchemaRequired>true</DovetailConfigurationSchemaRequired>`, which marks `required` members, `[Required]` properties and value-type constructor parameters without defaults. ## The generated binder [Section titled “The generated binder”](#the-generated-binder) Dovetail doesn’t call Microsoft’s binding generator. A source generator never sees another generator’s output, so the calls in Dovetail’s own code would not be intercepted. Instead it **ports** that generator: the parser, the type specifications and the emitter from dotnet/runtime (MIT), at tags `v10.0.13` and `v11.0.0-rc.2`. The rules follow the **major version of `Microsoft.Extensions.Configuration.Binder`** that the project references (version 11 when it references none), not the target framework, because a net10.0 application can reference Binder 11. What the two versions do differently: | Case | Binder 10 | Binder 11 | | ---------------------------------------------- | ---------------------- | ---------------------------- | | `Nullable<T>` set to `""` | value kept | `null` | | String or object constructor parameter missing | throws | `null` | | Value-type constructor parameter set to `""` | default | throws | | Nullable or reference-type parameter missing | throws | `null` (structs still throw) | | Parameter with a default, set to null | `null` | the default | | Properties bound through the constructor | bound again afterwards | not bound again | | `[ConfigurationIgnore]` | ignored | honoured, in the schema too | The same data is bound three ways in the parity tests (Microsoft’s generator, the reflection binder, Dovetail’s) on both versions. ### Records and other immutable types [Section titled “Records and other immutable types”](#records-and-other-immutable-types) Types the options pipeline can’t create (constructor parameters, `init`-only or `required` members) are registered like any other type: the generated create code builds the instance from the type’s section, and your `Configure<T>` and validators still run on it. 
```c#
[DovetailConfiguration]
public sealed record FarewellOptions(string Message, [property: Range(0, 5)] int Exclamations);
```
 ### Where Dovetail differs from Microsoft’s generator, on purpose [Section titled “Where Dovetail differs from Microsoft’s generator, on purpose”](#where-dovetail-differs-from-microsofts-generator-on-purpose) 1. **Object-initializer types.** Microsoft’s generator never sets `init`-only members of a type with a parameterless constructor, and can’t create a type with `required` members (CS9035). Dovetail creates them with an object initializer, then binds the rest. A missing key keeps the member’s own initial value, as the reflection binder does; a `required` member with no value gets `default`. 2. **`required` members that can’t be bound** (an unsupported type or `[ConfigurationIgnore]`) are set to `default!`, so the generated code compiles. [`DT0009`](#diagnostics) reports the member. 3. **Empty sections still produce an instance** for factory types. `Get<T>()` returns `null` there, but `IOptions<T>.Value` can’t be `null`. A missing required constructor parameter throws the first time the options are read. 4. **No `NotSupportedException`s** and no `BindNonPublicProperties`. 5. **Self-expanding generics** such as `class Node<T> { Node<Node<T>> Next; }` are treated as unsupported past a nesting depth of 10 or 1,000 types, instead of making the analysis run forever. The schema reports [`DT0012`](#diagnostics) for the same graphs. Microsoft’s own quirks are kept. A positional record’s extra `init`-only property is set to `default` when its key is missing, overriding its initializer, and Binder 10 binds constructor-bound collections twice. Registration also differs from `services.Configure<T>(section)` in that the configuration’s reload token feeds `IOptionsMonitor<T>` through one change token source per type, and the `IConfiguration` is resolved from the container when the options are first created, not captured at registration. ## The schema [Section titled “The schema”](#the-schema) ### Library fragments [Section titled “Library fragments”](#library-fragments) Each assembly embeds one fragment per section as `[assembly: AssemblyMetadata("Dovetail.ConfigurationSchema.v1:<Section>", "<JSON Schema>")]`. Each fragment is a Draft-07 schema of the section’s value, with every object type described once under `definitions`. Every key also has a case-insensitive `patternProperties` entry with the same schema, so `retries: 99` is checked even when written as `Retries`. Every project that isn’t a host (a library) also writes its own fragments as `$(IntermediateOutputPath)ConfigurationSchema.json` (permissive, rooted at the configuration root like Aspire’s) and packs it at the NuGet package root, so Visual Studio and other tools that understand Aspire’s layout can use it. A multi-targeted library writes one per target framework and packs the first one’s. A library with no sections writes nothing. ### The merged application schema [Section titled “The merged application schema”](#the-merged-application-schema) Hosts are test projects (`IsTestProject`) and applications (detected by Joinery.Dovetail.Sdk, or `OutputType` of `Exe` or `WinExe`). A host merges its own fragments and those of every referenced assembly into `$(BaseIntermediateOutputPath)appsettings.schema.json`, normally `obj/appsettings.schema.json`. * The file is a stable path editors can point at. A host that targets several frameworks writes that file from its first target framework, and `$(IntermediateOutputPath)appsettings.schema.json` (for example `obj/Debug/net10.0/`) from the others. * It is copied to `$(OutDir)`, next to `appsettings.json`, and published as `appsettings.schema.json`. A project that references the host (a test project referencing an application) doesn’t get a second copy. * Hosts that embed their configuration (`DovetailEmbedConfiguration` is `true`, which Joinery.Dovetail.Sdk sets for MAUI and Uno applications) keep the file in `obj/` only: no copy to the output directory and no publishing. * A hand-made `appsettings.schema.json` (Web SDK content, or one from a reference) is removed from the publish items so it doesn’t collide with the generated one (NETSDK1152). The generated file is what gets published. * **It is strict.** Each Dovetail section, and the object types it uses, accepts only its own keys. The check is a case-insensitive `propertyNames` pattern rather than `additionalProperties: false`, so `message` is accepted and `Mesage` is flagged, with an error that lists the known keys. The root, parents shared between sections, dictionaries and sections declared by more than one assembly stay open for keys of other sources. * **It includes SchemaStore’s `appsettings.json` schema**, embedded rather than referenced, so `Logging`, `Kestrel` and `ConnectionStrings` complete too, online or offline. The copy ships with Dovetail and is refreshed each release (Apache-2.0). * **It is deterministic.** Sections compare ignoring case; when libraries spell a section differently, the ordinal-smallest spelling is displayed. A section several assemblies declare is merged into one object. The same references always produce a byte-identical file. | Property | Default | Effect | | ----------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `DovetailConfigurationSchema` | on | `false` writes no schema files at all, and removes the ones an earlier build wrote. | | `DovetailConfigurationSchemaHost` | detected | `true` or `false` overrides which projects count as hosts. | | `DovetailConfigurationSchemaStrict` | `true` | `false` leaves Dovetail’s sections open (no `propertyNames`) in the host file. | | `DovetailConfigurationSchemaIncludeSchemaStore` | `true` | `false` leaves SchemaStore’s schema out of the host file. | | `DovetailEmbedConfiguration` | detected | `true` for hosts that embed their configuration (Joinery.Dovetail.Sdk sets it for MAUI and Uno): the schema stays in `obj/`, with no copy to the output and no publish. | | `DovetailConfigurationSchemaRequired` | `false` | `true` lists required members in `required`. The generator reads this one, so it changes the fragments in every project; the MSBuild targets don’t use it. | 
```xml
<PropertyGroup>
  <!-- Permissive: unknown keys under Dovetail sections aren't flagged -->
  <DovetailConfigurationSchemaStrict>false</DovetailConfigurationSchemaStrict>
</PropertyGroup>
```
 The build target runs after `CoreCompile` and skips design-time builds. It writes only when its inputs change: the references, the project’s own assembly and the properties above. Merging runs in a compiled MSBuild task (`Joinery.Dovetail.Build.Tasks`) that reads the fragments with `System.Reflection.Metadata`, so no assembly is loaded and nothing is embedded in your application. ### Serilog [Section titled “Serilog”](#serilog) `Joinery.Dovetail.Serilog` ships a schema for the `Serilog` section, so a host that references it gets completion and validation for `Serilog` without any setup. The section is read by hand (see [Serilog](./serilog)), so no options type describes it and the generator has nothing to emit. `Joinery.Dovetail.Serilog` carries the same `AssemblyMetadata` fragment as a hand-written attribute instead, and it goes through the pipeline above unchanged: the library’s `ConfigurationSchema.json` is packed at the package root, and a host merges the fragment into its `appsettings.schema.json` like any other. The schema describes what `Joinery.Dovetail.Serilog` reads, which is the minimum level and nothing else, because the rest of Serilog.Settings.Configuration’s format needs reflection that is not trimming or Native AOT safe. It models one key: * **`MinimumLevel`**, as a level name (`Verbose`, `Debug`, `Information`, `Warning`, `Error` or `Fatal`; the names are matched exactly) or as an object with `Default` and `Override` (a map from a source such as `Microsoft.AspNetCore` to a level). A number, or an unknown name, is flagged. Every other key of the section (`Using`, `WriteTo`, `AuditTo`, `Enrich`, `Filter`, `Destructure`, `Properties`, `LevelSwitches`, `FilterSwitches` and `MinimumLevel`’s `ControlledBy`, or a level switch given as a value) is flagged by the strict merged schema rather than accepted, so that configuration copied from Serilog’s documentation, which would be ignored, does not look as if it were working. The level rules follow the `Serilog` definition in SchemaStore’s `appsettings.json` schema, the one the merged file embeds by default, narrowed to the six levels (SchemaStore also lists `Off`, which Serilog has no level for) and with no switches. Both apply in the merged file, so the fragment is what rejects the keys that are not read. What else differs from SchemaStore’s schema, and why it is harmless: * **Casing.** Configuration keys ignore case, so the fragment, like every Dovetail fragment, accepts any casing of its keys. SchemaStore’s schema lists them case-sensitively, and both apply in the merged file, so `minimumlevel` is flagged by SchemaStore’s half. * **Flat keys.** SchemaStore’s schema accepts the flat forms `"WriteTo:Async"` and `"Enrich:0"`, which Serilog reads. They are flagged like the other keys that are not read. Set `DovetailConfigurationSchemaStrict` to `false` to leave the section open. ### Serving the schema [Section titled “Serving the schema”](#serving-the-schema) ASP.NET Core applications that reference Joinery.Dovetail.Hosting can serve the merged schema over HTTP at `GET /.well-known/dovetail/configuration-schema`. It is off by default. Setting `DovetailConfigurationSchemaEndpoint` to `true` generates a joint that maps it, and the `MapDovetailConfigurationSchema(fallbackDirectory, environments)` extension on `IEndpointRouteBuilder`, which Joinery.Dovetail.Hosting emits into ASP.NET Core projects, maps it by hand. The properties, the response and the security trade-off are described in [Editor setup](../guides/editor-setup#the-schema-endpoint). ## Shipping default values [Section titled “Shipping default values”](#shipping-default-values) Defaults still live in a normal `appsettings` file in the library. ```plaintext
MyLibrary/
├── appsettings.yaml
├── appsettings.Development.yaml
├── appsettings.local.yaml   # never packed, never committed
└── MyLibrary.csproj

The `local` layer is never packed, and the SDK warns when no `.gitignore` at or above the project ignores `appsettings.local.*`. * JSON, YAML and TOML are supported. Opt in with `DovetailEnableConfiguration`; YAML is the default format, and `DovetailEnableJsonConfiguration` or `DovetailEnableTomlConfiguration` chooses another. # OpenTelemetry

> OpenTelemetry integration that exposes the OpenTelemetry builder, resource, and tracer, meter and logger providers as Dovetail joints, turned on for the application's host.

# OpenTelemetry [Section titled “OpenTelemetry”](#opentelemetry) `Joinery.Dovetail.OpenTelemetry` exposes OpenTelemetry’s configuration surface — the top-level `IOpenTelemetryBuilder`, the resource builder, and the tracer, meter and logger provider builders — as ordinary Dovetail [joints](./defining-joints). Any library can contribute an activity source, a meter, a log processor, or a resource attribute without taking a direct dependency on how the host wires up OpenTelemetry. Coming from `LaunchPad.Telemetry`? [Its parity check](./opentelemetry-launchpad-parity) maps each of its conventions to a joint here. ## Turning it on [Section titled “Turning it on”](#turning-it-on) An application turns OpenTelemetry on by referencing `Joinery.Dovetail.OpenTelemetry` along with `Joinery.Dovetail.Hosting`. Joinery.Dovetail.Sdk adds `Joinery.Dovetail.OpenTelemetry` to every project that references `OpenTelemetry` or `OpenTelemetry.Extensions.Hosting`; set `DovetailEnableOpenTelemetry` to `false` to leave OpenTelemetry to the application. `Joinery.Dovetail.Hosting` then emits joints into the application that add OpenTelemetry to its services, apply every OpenTelemetry joint, and start it. OpenTelemetry only listens to activity sources and meters once its providers are resolved, which `OpenTelemetry.Extensions.Hosting` does from a hosted service, so what an application needs depends on whether its host runs hosted services: | Host | Runs hosted services | Needs `OpenTelemetry.Extensions.Hosting` | Started by | | --------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | | Generic host: workers, ASP.NET Core | yes | yes | its hosted service | | Uno Platform (`Uno.Extensions.Hosting`) | once started: `NavigateAsync<TShell>()` starts the host, `ConfigureDovetail()` doesn’t | no | `DovetailOpenTelemetryUnoStartJoint`, once the host is built | | .NET MAUI (`MauiAppBuilder`) | no | no | `DovetailOpenTelemetryMauiStartJoint`, once the app is built | | Blazor WebAssembly | from .NET 11 | no | `DovetailOpenTelemetryWebAssemblyStartJoint`, once the host is built (and on .NET 11 the hosted service too, when referenced) | * With `OpenTelemetry.Extensions.Hosting`, whatever the host, `DovetailOpenTelemetryJoint` calls `services.AddOpenTelemetry()`. On .NET 11 it also traces ASP.NET Core’s `Microsoft.AspNetCore` activity source. * Without it, `DovetailOpenTelemetryServicesJoint` adds OpenTelemetry to the services directly, for the hosts that don’t need it. * A start joint resolves the meter, tracer and logger providers right after the host is built, as the hosted service does when the host starts, so OpenTelemetry runs on those hosts without a package the application wouldn’t otherwise use. * Only an application whose hosts all need `OpenTelemetry.Extensions.Hosting` (the generic host, with no Uno, MAUI or WebAssembly host) and that doesn’t reference it fails to compile, with an `#error` (CS1029) that says to add it. Packages that build on it, such as the Azure Monitor distro or .NET Aspire’s service defaults, bring it along, so they count. OpenTelemetry runs in the browser too: in single-threaded Blazor WebAssembly its batch export processor and periodic metric reader run on tasks instead of threads. Only applications and test projects get the joint, as an internal class: a library’s copy would be exported to every application that references it. A test project that imports its application’s joints gets the application’s copy as well as its own, and only the first one to run applies OpenTelemetry. Every `[DovetailExport]` joint, and anything registered with a `DovetailContextBuilder` method such as `ConfigureTracerProvider(...)`, is then applied with nothing else to call: 
```c#
var host = await Host
                .CreateApplicationBuilder(args)
                .ConfigureDovetail(dovetail => dovetail.ConfigureTracerProvider((_, tracing) => tracing.AddConsoleExporter()));
```
 ## The joints [Section titled “The joints”](#the-joints) `Joinery.Dovetail.OpenTelemetry` declares one [`<DovetailJoint>`](../../reference/dovetail-joint/), `OpenTelemetry`, for `OpenTelemetry.IOpenTelemetryBuilder`: `IOpenTelemetryJoint`, its `OpenTelemetryJointDelegate`, the `ConfigureOpenTelemetry(...)` builder method and the `ApplyOpenTelemetry` extension that the emitted joint calls. Narrower interfaces derive from `IOpenTelemetryJoint`, each for one of OpenTelemetry’s builders: | Joint interface | Builder | `DovetailContextBuilder` method | | ----------------------------- | -------------------------------------------- | ------------------------------- | | `IOpenTelemetryJoint` | `OpenTelemetry.IOpenTelemetryBuilder` | `ConfigureOpenTelemetry` | | `IResourceBuilderJoint` | `OpenTelemetry.Resources.ResourceBuilder` | `ConfigureResourceBuilder` | | `ITracerProviderJoint` | `OpenTelemetry.Trace.TracerProviderBuilder` | `ConfigureTracerProvider` | | `IMeterProviderBuilderJoint` | `OpenTelemetry.Metrics.MeterProviderBuilder` | `ConfigureMeterProvider` | | `ILoggerProviderBuilderJoint` | `OpenTelemetry.Logs.LoggerProviderBuilder` | `ConfigureLoggerProvider` | Since they’re all OpenTelemetry joints, they run together in the executor’s usual priority order. A library that only wants to register an activity source implements `ITracerProviderJoint` without knowing anything about `WithMetrics`, `WithLogging` or the resource — the same narrow, composable extension point the rest of Dovetail follows. ## Example: contributing an activity source [Section titled “Example: contributing an activity source”](#example-contributing-an-activity-source) A library adds a `System.Diagnostics.ActivitySource` to tracing by implementing `ITracerProviderJoint` and marking the class `[DovetailExport]`, the same pattern used for any other discovered Dovetail joint: 
```c#
using Joinery.Dovetail;
using Joinery.Dovetail.Attributes;
using Joinery.Dovetail.OpenTelemetry.Joints;
using OpenTelemetry.Trace;


namespace MyLibrary;


[DovetailExport]
public class MyLibraryTracing : ITracerProviderJoint
{
    public static readonly ActivitySource ActivitySource = new("MyLibrary");


    public void Register(IDovetailContext context, TracerProviderBuilder builder) =>
        builder.AddSource(ActivitySource.Name);
}
```
 ## What this package does *not* do [Section titled “What this package does not do”](#what-this-package-does-not-do) `Joinery.Dovetail.OpenTelemetry` only opens the extension points — it does not ship any exporters or instrumentation. In particular, it does **not** include: * The console exporter, the OTLP exporter, or any other exporter package. * ASP.NET Core, HttpClient, or other instrumentation packages. * Any default sampler, resource attribute, or processor configuration of its own. The OpenTelemetry SDK’s default resource still applies, and already has the telemetry SDK attributes and the environment variable detector. Consumers add exporters and instrumentation the same way they add anything else to a provider: by writing their own `ITracerProviderJoint`/`IMeterProviderBuilderJoint`/`ILoggerProviderBuilderJoint` implementation (or a plain `Configure{Kind}(...)` delegate) that calls the relevant `AddConsoleExporter()`, `AddOtlpExporter()`, `AddAspNetCoreInstrumentation()`, etc. This keeps `Joinery.Dovetail.OpenTelemetry` itself free of exporter dependencies, which also keeps it friendly to trimming/AOT — see [Non-Goals in the OpenTelemetry design doc](https://github.com/RocketSurgeonsGuild/Dovetail/blob/main/openspec/changes/add-dovetail-opentelemetry/design.md#goals--non-goals) for the full rationale.

# Serilog

> Serilog integration that builds a Serilog logger from Serilog joints and the application's configuration, and registers it in place of the host's default logging providers. Trimming and Native AOT safe.

# Serilog [Section titled “Serilog”](#serilog) `Joinery.Dovetail.Serilog` makes Serilog the logging of an application, and exposes Serilog’s `LoggerConfiguration` as an ordinary Dovetail [joint](./defining-joints). Any library can contribute a sink, an enricher or a destructuring policy without taking a dependency on how the application builds its logger. ## Turning it on [Section titled “Turning it on”](#turning-it-on) Reference `Joinery.Dovetail.Serilog`. Its `SerilogJoint` is exported to the application like any other joint, so there is nothing to call: every host that calls `ConfigureDovetail` and references it gets a Serilog logger. With `Joinery.Dovetail.Sdk`, set `DovetailEnableSerilog` to `true` and every project that references `Serilog` gets the package. ## What it does [Section titled “What it does”](#what-it-does) Once every Serilog joint has run, `SerilogJoint`: 1. applies the minimum level and the level overrides in the `Serilog:MinimumLevel` section of the application’s configuration to the logger configuration ([below](#configuration)); 2. removes the logging providers the host builders add by default (console, debug, event source and, on Windows, event log: the `ConsoleLoggerProvider`, `DebugLoggerProvider`, `EventSourceLoggerProvider` and `EventLogLoggerProvider` of `Microsoft.Extensions.Logging`) and the default `ILoggerFactory`; 3. registers the logger, as `Serilog.Core.Logger` and as Serilog’s `ILogger`, and `ILoggerFactory` (a `SerilogLoggerFactory`, which is what backs every `ILogger<T>`), as singletons. The logger also writes to the other logging providers of the container ([below](#the-other-logging-providers)). So `Serilog.ILogger`, `Microsoft.Extensions.Logging.ILogger<T>` and `ILoggerFactory.CreateLogger(...)` all write to the one logger, once. The container owns it: disposing the host disposes the logger, which flushes and disposes its sinks. A few consequences of replacing `ILoggerFactory`: * The `Logging:LogLevel` filters and `builder.Logging.SetMinimumLevel(...)` belong to the factory that was replaced. Use Serilog’s levels, `Serilog:MinimumLevel` and its `Override` entries, instead. * Serilog’s levels decide what every logging provider receives, the other providers included. A provider that used to be given `Debug` events by its own filter gets them only if the `Serilog:MinimumLevel` lets them through. * Dovetail does not set the static `Log.Logger`. Resolve the logger from the container. ### The other logging providers [Section titled “The other logging providers”](#the-other-logging-providers) Replacing `ILoggerFactory` would leave every other `ILoggerProvider` of the container without events: the default factory is what writes to them. OpenTelemetry’s is one, since its logging joints (`ConfigureLoggerProvider`) add the `OpenTelemetryLoggerProvider` that exports log records, and so is any provider an application or a package registers. So the logger forwards each event it writes to them, the way Serilog.Extensions.Hosting does with `writeToProviders`: a `WriteTo.Providers(...)` sink over a `LoggerProviderCollection`, which the logger factory fills with the container’s `ILoggerProvider`s when it is created. A provider registered at any point before the container is built is included, by a Serilog joint or after it, with the logging builder (`builder.Logging.AddProvider(...)`) or with the services. The events keep their level, category (the `SourceContext`) and exception, and the Serilog properties are the state they are logged with. Each event is written once to every sink and once to every provider. Two kinds of provider are not written to: * Serilog’s own `SerilogLoggerProvider`, which would write the event to Serilog again (and, if it wraps this very logger, without end). * The default providers that Serilog replaces: exactly the four types named above, matched by their full names. They are removed from the services; one that is registered after the Serilog joint ran stays out of the forwarding too, so that the events are not written to the console twice. Providers that merely share a namespace with them are not defaults and are written to, such as Application Insights’ `ApplicationInsightsLoggerProvider` (`Microsoft.Extensions.Logging.ApplicationInsights`) and the Azure App Service providers (`Microsoft.Extensions.Logging.AzureAppServices`). The logger factory is created when the container is asked for it, which a host does while it is being built. Until then the other providers are not known: an event written through `Serilog.ILogger` before that reaches the sinks only. The logger disposes the providers it writes to when it is disposed, as the container does, so they are disposed twice, which `Dispose` allows. ## The Serilog joint [Section titled “The Serilog joint”](#the-serilog-joint) `Joinery.Dovetail.Serilog` declares one [`<DovetailJoint>`](../../reference/dovetail-joint/), `Serilog`, for `Serilog.LoggerConfiguration`: `ISerilogJoint`, `ISerilogAsyncJoint`, the `SerilogJointDelegate` and the `ConfigureSerilog(...)` builder method. A joint is handed the context, the service collection and the logger configuration. Sinks and enrichers are configured here, in code: 
```c#
using Joinery.Dovetail;
using Joinery.Dovetail.Attributes;
using Joinery.Dovetail.Joints;
using Microsoft.Extensions.DependencyInjection;
using Serilog;


namespace MyLibrary;


[DovetailExport]
public class MyLibraryLogging : ISerilogJoint
{
    public void Register(IDovetailContext context, IServiceCollection services, LoggerConfiguration loggerConfiguration) =>
        loggerConfiguration.Enrich.WithProperty("Library", "MyLibrary");
}
```
 or, for one application, without a class: 
```c#
var host = await Host
                .CreateApplicationBuilder(args)
                .ConfigureDovetail(dovetail => dovetail.ConfigureSerilog((_, _, logger) => logger.WriteTo.Console()));
```
 ## Configuring the logger [Section titled “Configuring the logger”](#configuring-the-logger) The logger configuration is built in this order, and what comes later wins where only one value can exist (the minimum level): 1. the Serilog joints, in the executor’s usual priority order; 2. the `Serilog:MinimumLevel` section of the configuration; 3. the `IConfigureOptions<LoggerConfiguration>` registered in the services (`services.Configure<LoggerConfiguration>(...)`); 4. the `IPostConfigureOptions<LoggerConfiguration>` registered in the services (`services.PostConfigure<LoggerConfiguration>(...)`). The options are applied the way the options pattern applies them, to the unnamed options, when the logger is first resolved (which a host does while it is being built). That is what lets them use other services: 
```c#
services
   .AddOptions<LoggerConfiguration>()
   .Configure<IHostEnvironment>((logger, environment) => logger.Enrich.WithProperty("Environment", environment.EnvironmentName));
```
 ### Configuration [Section titled “Configuration”](#configuration) The application’s configuration sets the minimum level of the logger and of each source, in the `Serilog:MinimumLevel` section, in the same format as Serilog.Settings.Configuration: 
```json
{
    "Serilog": {
        "MinimumLevel": {
            "Default": "Information",
            "Override": { "Microsoft": "Warning", "Microsoft.Hosting.Lifetime": "Information" }
        }
    }
}
```
 `"MinimumLevel": "Debug"` is the short form of `"Default": "Debug"`. A level is the name of one of Serilog’s levels (`Verbose`, `Debug`, `Information`, `Warning`, `Error`, `Fatal`; casing is ignored), and anything else fails while Dovetail builds the host, with an exception that names the key. Levels follow the configuration when it reloads (a file provider with `reloadOnChange`, say). Only the levels that were in the configuration when the application started do: an override that is added later is not picked up, and a level that is removed or not a level any more leaves the level in effect as it is. That is all that is read from the `Serilog` section. In particular, **sinks, enrichers, filters and `Using` are not read from configuration**: Serilog.Settings.Configuration finds the methods they name by reflection, which is neither trimming nor Native AOT safe, so `Joinery.Dovetail.Serilog` does not depend on it. A `"WriteTo"` or `"Enrich"` in the section is ignored, and the schema flags it (below). Configure them in a [Serilog joint](#the-serilog-joint) instead, in code. `Joinery.Dovetail.Serilog` ships a JSON Schema for the section, which is merged into the application’s [`appsettings.schema.json`](../guides/editor-setup) for editor completion and validation. It describes exactly what is read: `MinimumLevel`, as a level name or as an object with `Default` and `Override`. Any other key of the `Serilog` section is flagged, so a `WriteTo` copied from Serilog’s documentation does not look as if it were working. ## Trimming and Native AOT [Section titled “Trimming and Native AOT”](#trimming-and-native-aot) `Joinery.Dovetail.Serilog` is trimming and Native AOT compatible: the project sets `IsAotCompatible`, builds with the trim and AOT analyzers on without a warning, and has no reflection to annotate or suppress. Reading the configuration uses only `IConfiguration` and enum parsing (`Enum.TryParse<LogEventLevel>`), and the rest is registration of the logger, which is Serilog’s, and of `Microsoft.Extensions.Logging`’s own open generic `ILogger<T>`. Forwarding to the other logging providers is not reflection either: it is Serilog.Extensions.Logging’s `WriteTo.Providers` sink and `SerilogLoggerFactory`, and a type check on the providers. The claim was checked by publishing a generic-host application that references `Joinery.Dovetail.Serilog`, reads `Serilog:MinimumLevel:Default` and `Override` from configuration, configures a sink in a `ConfigureSerilog(...)` joint and registers an `ILoggerProvider` in its services, with `PublishTrimmed` (`TrimMode=full`) and with `PublishAot` (.NET 10, osx-arm64, self-contained). Neither publish reported a trim or AOT warning, and both applications ran: the factory was a `SerilogLoggerFactory`, `ILogger<T>` wrote through the sink and to the provider, the default level and the override applied to both, and no default logging provider was left. What a published application depends on is therefore Serilog and the sinks and enrichers it configures in its joints, which are referenced from code and so are kept by the trimmer and compiled by the AOT compiler like any other code. Check the ones you use: Serilog and its sinks are not Dovetail’s.

# Source Generation

> How the Roslyn source generator resolves and exports joints at build time.

# Source Generation and Dovetails \[New] [Section titled “Source Generation and Dovetails \[New\]”](#source-generation-and-dovetails-new) We have built a Source Generator to use with Dovetail that allows us to export joints and import joints with easy, in a way that is statically compiled. # Exporting Dovetails [Section titled “Exporting Dovetails”](#exporting-dovetails) Any joint marked with `[assembly: Dovetail(typeof(MyDovetail))]` will automatically be added to a public partial static class named `Exports` that will exist in the root namespace of the assembly being built. Each exported joint carries the host type it declares with `[LiveJoint]`, `[UnitTestJoint]` or `[DovetailHostType]`, the same as when a joint is added through reflection at runtime. See [which attributes are honoured where](./defining-joints#which-attributes-are-honoured-where). A joint with constructor parameters is exported as a factory, because the exported method has no context to read from: the context builder that holds the metadata creates the joint from its properties, and an optional parameter falls back to its default. See [how constructor parameters are resolved](./defining-joints#how-constructor-parameters-are-resolved). # Importing Dovetails [Section titled “Importing Dovetails”](#importing-dovetails) The generator creates an internal static partial `Imports` class in the assembly’s root namespace. `Imports.Joints` is a `DovetailContextBuilderFactory` that creates a context builder loaded with the assembly’s own joints and those of every referenced assembly that exports joints. The `DovetailImportNamespace`, `DovetailImportClassName` and `DovetailImportMethodName` MSBuild properties change those names. You can also import the `GetDovetails` method onto a given class by using the `[ImportDovetails]` attribute on the class. ## Which projects import and export [Section titled “Which projects import and export”](#which-projects-import-and-export) Two MSBuild properties decide what the generator emits for a project: | Property | When `true` | | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | | `ImportDovetailAssembly` | The `Imports` class is generated. | | `ExportDovetailAssembly` | Referencing assemblies import this assembly’s joints. When `false`, the joints still reach this assembly’s own `Imports` class. | Joinery.Dovetail.Sdk sets both as part of its host detection. Projects that don’t use the SDK get these defaults: * test projects (`IsTestProject`) import but don’t export; * applications (`OutputType` of `Exe` or `WinExe`) import and export; * libraries export but don’t import. Set either property in a project file to override its default. The generator runs in every project that references a Dovetail package, including projects that only reference one indirectly, for example through `Joinery.Dovetail.Hosting`. Its diagnostics (`DT0001` to `DT0005`, such as the error for a joint with more than one constructor, and `DT0017`, the error for a joint with no constructor it can be created with) apply there too. The code it generates needs C# 12 or later: in a project whose `LangVersion` is older, it generates nothing and reports warning `DT0006` instead. ## Specular’s provider [Section titled “Specular’s provider”](#speculars-provider) An application that references [Specular](https://www.nuget.org/packages/Specular) doesn’t set its provider by hand. Specular generates an internal `SpecularProvider` into each project that emits one, and the generated `Imports` seeds that provider into the context builder it creates, so a joint reads it with `context.Get<ISpecularProvider>()`. Scanning through it covers the assemblies the application references, including the joints of libraries that don’t generate a provider of their own (`SpecularEmitProvider` set to `false`) and so keep receiving the application’s through the context. 
```csharp
public sealed class PluginJoint : ISetupJoint
{
    public void Register(IDovetailContext context)
    {
        var provider = context.Get<ISpecularProvider>()!;
        var plugins = provider.GetTypes(z => z.FromAssemblyOf<IPlugin>().GetTypes(f => f.AssignableTo<IPlugin>()));
    }
}
```
 Dovetail has no dependency on Specular, so the seeding is generated code that exists only where Specular does: * The generator adds it when the project’s compilation references the assembly that defines `Specular.ISpecularProvider` and the `SpecularEmitProvider` MSBuild property isn’t `false`, the two things Specular’s own generator looks at before it generates a `SpecularProvider`. It can’t look for `SpecularProvider` itself: a generator doesn’t see what another one adds. * In every other project nothing is generated and no diagnostic is raised. * A provider you set yourself wins. The generated code only adds the provider when the context doesn’t hold one, so `builder.ConfigureDovetail(b => b.Set<ISpecularProvider>(provider))`, or a provider passed in with the properties, is never overwritten. * Set `SpecularEmitProvider` to `false` for a project that references Specular without generating a provider (say it excludes Specular’s analyzers) and Dovetail stops naming one. Otherwise the build fails with CS0103 for `SpecularProvider`. ### Native AOT and trimming [Section titled “Native AOT and trimming”](#native-aot-and-trimming) The seeding adds no reflection: it is a generic call to `AddIfMissing<ISpecularProvider>` with the value of a static property, both of which the trimmer and the AOT compiler can follow. Specular generates `SpecularProvider` without reflection as well. The Joinery.Dovetail.Sdk.Tests publish an application that uses it trimmed and with Native AOT, without trim or AOT warnings, and the published application starts with the provider in its context and scans across assemblies.

# Editor Setup

> Get completion, hover documentation and validation for your Dovetail configuration in VS Code, Visual Studio and Rider.

# Editor setup [Section titled “Editor setup”](#editor-setup) Every application built with Dovetail gets one JSON Schema for its configuration, merged from the [`[DovetailConfiguration]`](../concepts/managed-configuration) sections of every library it references. This guide points your editor at it, so `appsettings.json`, YAML and TOML files complete section and key names, show the documentation you wrote on the options classes, and flag unknown keys and out-of-range values. ## Where the schema comes from [Section titled “Where the schema comes from”](#where-the-schema-comes-from) A build of an application or a test project writes the merged schema to: 
```text
<project>/obj/appsettings.schema.json
```
 That path is stable, so editor settings can point at it and be checked in. Build the project once before expecting completion: the file doesn’t exist before then. * A project that targets several frameworks writes that file from its first target framework. The others write `$(IntermediateOutputPath)appsettings.schema.json`, for example `obj/Debug/net10.0/appsettings.schema.json`. * The build also copies the file next to the application’s `appsettings.json` in the output directory and publishes it as `appsettings.schema.json`. * Applications that embed their configuration (MAUI and Uno, where `DovetailEmbedConfiguration` is `true`) keep the file in `obj/` only. It is not copied to the output directory and not published, so editors still use the `obj/` path. * A library (any project that isn’t a host) doesn’t write `appsettings.schema.json`. It writes `$(IntermediateOutputPath)ConfigurationSchema.json` and packs it at the package root. If a project that isn’t detected as an application should merge a schema, or an application shouldn’t, set `DovetailConfigurationSchemaHost` to `true` or `false`. The other properties (`DovetailConfigurationSchema`, `DovetailConfigurationSchemaStrict`, `DovetailConfigurationSchemaIncludeSchemaStore`, `DovetailEmbedConfiguration` and `DovetailConfigurationSchemaRequired`) are described under [the schema](../concepts/managed-configuration#the-schema). ## Visual Studio Code [Section titled “Visual Studio Code”](#visual-studio-code) VS Code needs one mapping per file type: its JSON support reads `json.schemas`, and the YAML and Even Better TOML extensions read `yaml.schemas` and `evenBetterToml.schema.associations`. Put them in `.vscode/settings.json`, which allows comments: 
```jsonc
{
    "json.schemas": [
        {
            "fileMatch": ["/MyApp/appsettings*.json"],
            "url": "./MyApp/obj/appsettings.schema.json",
        },
    ],
    "yaml.schemas": {
        "./MyApp/obj/appsettings.schema.json": ["MyApp/appsettings*.yaml", "MyApp/appsettings*.yml"],
    },
    "evenBetterToml.schema.associations": {
        "^.+/MyApp/appsettings.*\\.toml$": "./MyApp/obj/appsettings.schema.json",
    },
}
```
 The [SdkSample](https://github.com/RocketSurgeonsGuild/Dovetail/blob/main/sample/SdkSample/.vscode/settings.json) checks in a working file for a solution with two applications. Notes on the three extensions: * **JSON** reports unknown keys, completes the canonical names and shows descriptions on hover. * **YAML** (the Red Hat extension) does the same. Its `fileMatch` globs don’t match files under a dot-folder. * **TOML** needs the explicit association above: Even Better TOML can’t use the SchemaStore catalog, and it reports an unknown key on the table header rather than on the key. It ignores `deprecated`. * Keys are matched ignoring case, as the configuration system does: `message` is accepted, `Mesage` is flagged. ### Let Dovetail write the settings [Section titled “Let Dovetail write the settings”](#let-dovetail-write-the-settings) Set `DovetailScaffoldEditorSettings` to `true` in the application’s project file: 
```xml
<PropertyGroup>
  <DovetailScaffoldEditorSettings>true</DovetailScaffoldEditorSettings>
</PropertyGroup>
```
 On build, Dovetail creates or updates **only its own** entries in `.vscode/settings.json` (`json.schemas`, `yaml.schemas` and `evenBetterToml.schema.associations`), pointing at the application’s `obj/appsettings.schema.json`. Comments, trailing commas, indentation, line endings and a byte-order mark are preserved, other settings and other entries in those three maps are untouched, and re-running changes nothing (the file isn’t even rewritten, so its timestamp stays). Dovetail never adds `$schema` keys or `# yaml-language-server` modelines to your configuration files. Each application gets entries of its own, keyed by its schema path, so several applications in one repository can share one settings file. Dovetail recognises its entries by that path: an entry that already maps the application’s schema only gets whatever is missing (a file pattern, a glob), and anything you added to it stays. If you move a project, delete its old entries by hand. The file goes in the folder that holds `.vscode`: the nearest ancestor of the project that contains a `.git` entry, or the project folder when there is none. Set `DovetailEditorSettingsDirectory` to use another folder (a relative path is relative to the project). The folder must contain the project, because VS Code resolves the schema path relative to the folder it has open. The file and the `.vscode` folder are created only when they don’t exist. Only applications write the file, once per build (from the first target framework of a project that targets several), never in design-time builds, and not when `DovetailConfigurationSchema` is `false`. If the file can’t be updated safely, because it isn’t valid JSON with comments, isn’t UTF-8, has an unexpected shape (say `json.schemas` isn’t an array) or is read-only, Dovetail leaves it as it is and the build reports a warning with the entries to paste. Fix the file, or set `DovetailScaffoldEditorSettings` to `false`, to get rid of the warning. | Property | Default | Effect | | --------------------------------- | -------- | ------------------------------------ | | `DovetailScaffoldEditorSettings` | off | `true` writes the mappings on build. | | `DovetailEditorSettingsDirectory` | git root | The folder that holds `.vscode`. | It is off by default because it edits a file that is probably checked in. ## Visual Studio [Section titled “Visual Studio”](#visual-studio) Visual Studio’s JSON editor reads schemas from `JsonSchemaSegment` items, with no per-file settings. Dovetail adds, with the file pattern `appsettings\..*json` (the one Aspire’s packages use): * a segment for the application’s (or test project’s) merged `obj/appsettings.schema.json`; * a segment for each referenced package that ships a `ConfigurationSchema.json` at its root, which is where libraries built with Dovetail pack theirs. A package that declares its own segment for the file (Aspire’s client packages do) is skipped, so completions aren’t doubled. Referenced projects need no segment: their sections are in the merged file. Nothing needs configuring. Dovetail finds the packages from the build’s resolved references, in the builds Visual Studio runs when it loads the project too, not only in full builds. `DovetailConfigurationSchemaVisualStudio=false` turns the segments off and keeps the schema files; `DovetailConfigurationSchema=false` turns off both. If completion doesn’t appear after the first build, close and reopen the file. The repository’s tests check the items MSBuild produces, including in a design-time build. Whether Visual Studio itself picks up items a target adds, and how it merges two segments that describe the same section, has not been verified in Visual Studio. ## JetBrains Rider [Section titled “JetBrains Rider”](#jetbrains-rider) Rider uses its own JSON Schema mappings rather than the VS Code settings or the segments: 1. Open **Settings | Languages & Frameworks | Schemas and DTDs | JSON Schema Mappings**. 2. Add a mapping, choose `obj/appsettings.schema.json` as the schema file, set the version to Draft 7, and add the application’s `appsettings*.json` files as the mapped files. 3. Rider applies JSON Schema mappings to YAML files too. Add the `appsettings*.yaml` files the same way. ## TOML and YAML in other editors [Section titled “TOML and YAML in other editors”](#toml-and-yaml-in-other-editors) Any editor with a language server for the format can use the schema file: * **yaml-language-server** reads a `yaml.schemas` setting like VS Code’s, or a `# yaml-language-server: $schema=...` modeline in the file. * **Taplo** takes the schema from `.taplo.toml` or, in VS Code, `evenBetterToml.schema.associations`. ## The schema endpoint [Section titled “The schema endpoint”](#the-schema-endpoint) An application can also serve its schema, for tools that read it over HTTP. This needs an ASP.NET Core application that references Joinery.Dovetail.Hosting, and is off by default: 
```xml
<PropertyGroup>
  <DovetailConfigurationSchemaEndpoint>true</DovetailConfigurationSchemaEndpoint>
  <!-- Optional: serve it only in these environments -->
  <DovetailConfigurationSchemaEndpointEnvironments>Development;Staging</DovetailConfigurationSchemaEndpointEnvironments>
</PropertyGroup>
```
 | Property | Default | Effect | | --------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `DovetailConfigurationSchemaEndpoint` | off | `true` generates a joint that maps the endpoint. Only projects with `OutputType` `Exe` or `WinExe` that reference ASP.NET Core and Joinery.Dovetail.Hosting get it. | | `DovetailConfigurationSchemaEndpointEnvironments` | every environment | A semicolon-separated list of environment names (`Development;Staging`, compared ignoring case). The endpoint is mapped only when the host environment is one of them. | | `DovetailConfigurationSchemaEndpointSourceFallback` | `true` except below | Whether the project’s `obj/` directory is compiled into the application as a place to look for the schema. By default it is, except in publish builds and `ContinuousIntegrationBuild` builds, so a build machine path isn’t shipped. `false` never embeds it. | The route is `GET /.well-known/dovetail/configuration-schema`: * It looks for `appsettings.schema.json` in the application’s output directory first, then in the embedded `obj/` fallback directory, which is how it works when run from source with no copy beside the assembly. A published application serves the copy published with it. * The response is `application/schema+json` with a strong `ETag` and `Cache-Control: no-cache`. A request with a matching `If-None-Match` gets `304 Not Modified`. The file is re-read when it changes on disk. * It answers `404` when neither location has the file. Point a mapping at the URL, for example `"url": "http://localhost:5000/.well-known/dovetail/configuration-schema"` in `json.schemas`. To map it yourself, call the extension on the `WebApplication` (or any `IEndpointRouteBuilder`) instead of setting the property. Joinery.Dovetail.Hosting emits it into every ASP.NET Core project that references it, as an internal type. Both arguments are optional, and the method returns `null` when `environments` excludes the current environment: 
```c#
using Joinery.Dovetail.Hosting;


app.MapDovetailConfigurationSchema(fallbackDirectory: null, environments: "Development")
   ?.RequireAuthorization();
```
 Caution The schema lists every configuration key your application and its libraries accept, including the section names of libraries you may not want to advertise. Unless you restrict it, the endpoint is mapped in every environment, production included, and anyone who can reach the application can read it, with no authentication. Set `DovetailConfigurationSchemaEndpointEnvironments` to the environments that need it (usually `Development`), map it yourself and add authorization, or leave it off. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) * **No completion at all.** Build the project: the file is written after compilation. Then check the path in the mapping is relative to the folder VS Code opened, and that the file name matches `appsettings*`. * **A key is flagged as unknown.** Check its spelling against the options class. Keys can’t be added to a section that `[DovetailConfiguration]` declares; set `DovetailConfigurationSchemaStrict` to `false` to stop the check. * **A section is missing from completion.** The application’s schema only covers libraries it references. Check the library has `[DovetailConfiguration]` on its options type and that the application builds against it. * **Quoted numbers are flagged.** `"Timeout": "30"` is an incorrect type to the editor even though the binder accepts it. Write the number without quotes.

# Shipping Templates

> Ship C# source from your package as templates that Dovetail writes into only the projects that should get it, by host model, referenced assemblies and direct reference.

# Shipping templates [Section titled “Shipping templates”](#shipping-templates) A package can ship C# source that is written into a consuming project at build time, only when that project matches. This is how `Joinery.Dovetail.Hosting` works: its ASP.NET Core, MAUI, Uno and Blazor WebAssembly helpers and its OpenTelemetry joints are all templates, so the package depends on none of those frameworks. Referencing a framework is what turns its template on. The mechanism is a supported extension point. Any package can declare templates with `<DovetailTemplate>` items and get the same gating that `Joinery.Dovetail.Hosting` uses, including a mode that emits only into projects that reference your package themselves. ## Declare a template [Section titled “Declare a template”](#declare-a-template) Put the source in a `*.cs.template` file next to your package’s targets, and declare it from the targets (`build/` or `buildTransitive/`): 
```xml
<Project>
  <ItemGroup>
    <DovetailTemplate
      Include="HealthCheckJoint"
      File="$(MSBuildThisFileDirectory)HealthCheckJoint.cs.template"
      Package="Contoso.Hosting"
      DirectReferenceOnly="true"
      References="Microsoft.Extensions.Diagnostics.HealthChecks"
      Hosts="HostApplication;WebApplication" />
  </ItemGroup>
</Project>
```
 Pack both files, under `build/` (imported by NuGet into projects that reference the package directly) or `buildTransitive/` (imported into every project that gets it, which is what a package reached through other packages needs): `<None Include="build/*.*" Pack="true" PackagePath="buildTransitive" />`. | Metadata | Meaning | | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `Include` | The template’s name. It must be unique across packages, and names the generated file, `DovetailTemplate.<name>.g.cs` in `obj/`. | | `File` | Required. The full path of the template. | | `Package` | The id of the package that ships the template. It is only emitted into a project that references it: the package’s assembly (named after the package) is among the resolved references. | | `DirectReferenceOnly` | `true` limits the template to projects with a direct reference to `Package`. Requires `Package`. | | `References` | Semicolon-separated assembly names (file names without extension). Every one must be among the project’s resolved references. | | `Hosts` | Semicolon-separated host names. At least one must be declared by the project: the host model that `Joinery.Dovetail.Sdk` detects (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui` or `Uno`). | | `HostName`, `HostType` | When `HostType` is set, `{HostName}` and `{HostType}` in the template are replaced, so one template can be declared once per host model under different names. | | `OutputPrefix` | The generated file is `<prefix>.<name>.g.cs`; the default prefix is `DovetailTemplate`. | Every gate you set has to pass. A project that doesn’t run the Dovetail source generator gets no templates. The [`DovetailTemplate` reference](../../reference/dovetail-template/) lists the defaults, the errors and the generated file names. ## Direct references only [Section titled “Direct references only”](#direct-references-only) By default a template reaches every project that has your package’s assembly among its references, which includes projects that only get the package because a library they use references it. `DirectReferenceOnly="true"` narrows that to projects that declare the reference themselves: * a `PackageReference` to `Package`, including the ones `Joinery.Dovetail.Sdk` adds for you, or * a `ProjectReference` to a project named after `Package`, which is how a solution consumes what it ships. A project that only receives the package transitively still imports your `buildTransitive/` targets, so your items are declared there, but it gets no generated file. Use it for wiring that an application should opt into by referencing your package, and that a library reaching the application through a project reference should not impose on it. A package that ships from `build/` already gets this from NuGet for package references. The mode is for what NuGet can’t express: a package shipped from `buildTransitive/`, and a solution that consumes your project by `ProjectReference`. A project reference imports no package assets at all, so the solution imports your targets itself, into every project (this repository does that with `Joinery.Dovetail.Hosting.targets` for its test projects). `Package` is then what limits the templates to projects that reference yours, and `DirectReferenceOnly` to the ones that reference it themselves. ## Write the template [Section titled “Write the template”](#write-the-template) * The generated code is part of the consuming project, compiled against whatever it references. Reference-gate everything it needs (`References`), and your package then depends on none of it. * Make the types `internal` and `[Embedded]`, so an assembly never sees the copy a referenced assembly emitted for itself. A template may also declare joints (`[DovetailExport]`), which the Dovetail source generator picks up like any other. * A template must not contain backslashes: MSBuild rewrites them to forward slashes on Linux and macOS when it writes the file. ## When the metadata isn’t enough [Section titled “When the metadata isn’t enough”](#when-the-metadata-isnt-enough) The templates that pass their gates are the `DovetailEmittedTemplate` items, with the metadata above carried over. A target can add to them, or remove from them, after `DovetailResolveTemplates` and before `DovetailGenerateTemplates`: 
```xml
<Target Name="ChooseMyJoint" AfterTargets="DovetailResolveTemplates" BeforeTargets="DovetailGenerateTemplates">
  <ItemGroup>
    <DovetailEmittedTemplate
      Include="MyJoint"
      File="$(MSBuildThisFileDirectory)MyJoint.cs.template"
      Condition="@(DovetailEmittedTemplate->AnyHaveMetadataValue('Identity', 'MyHelpers')) == 'true'" />
  </ItemGroup>
</Target>
```
 `Joinery.Dovetail.Hosting` does this to choose which of its OpenTelemetry joints a host gets, depending on which helpers were emitted, and to leave the host lifecycle helper out of hosts that don’t run it. Removing is `<DovetailEmittedTemplate Remove="MyJoint" />`: only these items are written, so a copy of the list that a package keeps for itself is not enough. ## Test it [Section titled “Test it”](#test-it) The Dovetail SDK tests show how to prove a template’s gates: pack a package that ships the template, reference it from a project that declares the reference and from one that only receives it transitively, build, and read which `DovetailTemplate.*.g.cs` files landed in each project’s `obj/` (`test/Joinery.Dovetail.Sdk.Tests/TemplateExtensionPointTests.cs`).

Dovetail is extended through MSBuild items. You declare one in a project file, and the build writes the C# for it into `obj/` before the compiler runs. MSBuild targets expand the items, not the Roslyn source generator, so there is nothing to configure and nothing to call at run time. These pages list every metadata value an item reads, with its default, so you do not have to read the `.targets` files. # DovetailHost

> The DovetailHost MSBuild item declares the ConfigureDovetail entry points for one host builder type. Which hosts the SDK declares for you, every metadata value and its default, and what is generated.

# DovetailHost [Section titled “DovetailHost”](#dovetailhost) A `DovetailHost` item declares the **entry points of one host**: the `ConfigureDovetail` extension methods on its builder type. Calling one creates the Dovetail context, runs every joint the application imports, and builds the host. 
```c#
var host = await Host.CreateApplicationBuilder(args).ConfigureDovetail();
```
 The item is expanded by MSBuild targets, not by the Roslyn source generator: the C# is written to `obj/` before the compiler runs, so you can open it in your IDE like any other source file. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) In most projects, nobody: `Joinery.Dovetail.Sdk` looks at the project and declares the host for you. You declare your own when the SDK does not, which is one of: * the project does not use `Joinery.Dovetail.Sdk` but references `Joinery.Dovetail`. `sample/Sample`, the benchmarks and most test projects declare their host by hand; * the host is one the SDK does not detect. Aspire’s `IDistributedApplicationBuilder` is declared by hand in `test/Joinery.Dovetail.Aspire.Tests`; the SDK has that case commented out. Do not declare a host the SDK already did. The default fits the hosts `Joinery.Dovetail.Hosting` emits helpers for (`HostApplication`, `Maui`, `Uno`, `WebAssembly`) and Aspire’s `DistributedApplication`; for any other name, set `HelperName`. * **Two hosts on the same builder type in the same namespace make `ConfigureDovetail` ambiguous** (CS0121). An application built with the SDK already has `HostApplication` in `$(RootNamespace)`, so a second host on `HostApplicationBuilder` needs a `Namespace` of its own, and the caller imports only the one it wants. * **`HostBuilderType` and `HostType` have no default.** A host that sets neither generates a file that is not valid C# (CS1001). * **`BuildExpression` is spliced in as text.** It goes straight after `builder`, so it starts with a comma, and the `Configure` method it calls must take exactly those arguments. `HasBuildExpression="false"` removes it, including a `BuildExpression` you set. * **`HostBuilderName` changes nothing.** The template does not use it today. * **Types are written as given.** `HostBuilderType`, `HostType` and `HelperName` go into the generated code unchanged, so a bare name is looked up from `Namespace` outwards, as in any C# file. Use `global::` as the SDK does. * **`SyncEntryPoint` and `NavigateEntryPoint` belong to the MAUI and Uno host models.** `NavigateEntryPoint` emits calls to `{HelperName}.Navigate<TShell>`, which only `DovetailUnoHelpers` has; leave both alone on a host of your own. * **A misspelled metadata name is ignored.** The default applies, with no warning. * **When `Joinery.Dovetail.Hosting` is referenced, a host whose framework is missing is dropped.** If the helper a host names is one of the package’s but the project does not reference the framework it compiles against (a `Microsoft.NET.Sdk.WebAssembly` app without Blazor, say), the host is removed from the build, with a message at normal verbosity, and `ConfigureDovetail` does not exist for it. ## See also [Section titled “See also”](#see-also) * [DovetailJoint](../dovetail-joint/): the joint kinds that `ConfigureDovetail` runs. * [DovetailTemplate](../dovetail-template/): how `Joinery.Dovetail.Hosting` ships the helpers a host calls, and gates them on the host’s framework. * [Host Lifecycle](../../concepts/host-lifecycle/): code that runs as the host starts and stops. * [Defining Dovetails](../../concepts/defining-joints/): the host type a joint can be filtered by.

# DovetailJoint

> The DovetailJoint MSBuild item declares a joint kind, a typed extension point, and the build generates its interfaces, delegates, Apply method and DovetailContextBuilder method. Every metadata value, its default, and what it generates.

# DovetailJoint [Section titled “DovetailJoint”](#dovetailjoint) A `DovetailJoint` item declares a **joint kind**: a typed extension point that other code can contribute to without knowing who applies it. One line in a project file becomes a joint interface, its async twin, the delegates for both, an `Apply` extension that runs every joint of the kind, and a method on `DovetailContextBuilder` that registers a delegate. Dovetail’s own joints (`ISetupJoint`, `IServiceJoint`, `ILoggingJoint`, `IConfigurationJoint`, `IHostCreatedJoint<THost>`) are declared this way, and so are those of [Serilog](../../concepts/serilog/), [OpenTelemetry](../../concepts/opentelemetry/) and Aspire. The item is expanded by MSBuild targets, not by the Roslyn source generator: the C# is written to `obj/` before the compiler runs, so you can open it in your IDE like any other source file. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) A package or application that owns something other code should be able to configure declares a joint kind for it. Serilog’s package declares `Serilog` for `LoggerConfiguration`, so any library can add a sink; `Sample.Core` declares `DatabaseConfigurator` for its own `IDatabaseConfigurator`, so other assemblies can add tables and views. Declare one when: * you hand an object to other code at one point in startup (a builder, a configuration object) and want every library to be able to contribute to it without referencing your application or each other; * you are prepared to call `Apply{Name}` yourself at that point. A joint kind does not run by itself: `SerilogJoint` calls `loggerConfiguration.ApplySerilog(...)` once it has created the `LoggerConfiguration`. Do not declare one when: * you only want to run code at startup. Implement an existing joint such as `IServiceJoint` or `ILoggingJoint` instead, as described in [Defining Dovetails](../../concepts/defining-joints/); * Dovetail or one of its packages already declares a joint for the type you have: `Joinery.Dovetail` covers `IServiceCollection`, `IConfigurationBuilder` and `ILoggingBuilder`, and `Joinery.Dovetail.Hosting` covers the host builders. The item is read by the targets that ship in `Joinery.Dovetail`, so the project that declares it must reference that package (`Joinery.Dovetail.Sdk` adds the reference for you). The generated types are `public`, so anything that references your project sees them as ordinary API. ## Declaring a joint [Section titled “Declaring a joint”](#declaring-a-joint) The item’s `Include` is the joint’s name. It becomes part of every generated type name, and of the generated file names, so it has to be a valid C# identifier, and it must be unique in the project. 
```xml
<!-- src/Joinery.Dovetail/Joinery.Dovetail.csproj -->
<DovetailJoint Include="Setup" Namespace="Joinery.Dovetail.Joints" />
```
 That is the smallest useful declaration: a joint that is handed only the `IDovetailContext`. Everything else is metadata. ## Metadata [Section titled “Metadata”](#metadata) Metadata is optional unless stated. A name the item does not read is ignored without a warning, so a misspelling falls back to the default (`NMAmespace` leaves `Namespace` at its default). Boolean values are compared with `true` ignoring case; any other non-empty value counts as false. | Metadata | Default | What it changes | | ---------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `Namespace` | `$(RootNamespace).Joints` | The namespace of every generated type, and so the namespace consumers import. Joints of one package usually share one, as `Joinery.Dovetail.Joints` does. | | `ProvideConfiguration` | empty (false) | `true` adds an `IConfiguration configuration` parameter to `Register`, after the context. The value passed is `context.Configuration`; `Apply{Name}` takes no configuration parameter. | | `ProvideServices` | empty (false) | `true` adds an `IServiceCollection services` parameter to `Register`, after the configuration if there is one. With no `ParameterType` it is also the subject of `Apply{Name}`. | | `ParameterType` | empty | The type of one more `Register` parameter, the last one. It becomes the subject of `Apply{Name}`. Written into the generated code exactly as given; see [common mistakes](#common-mistakes). | | `ParameterName` | `parameter` when `ParameterType` is set | The name of that parameter, as it appears in `Register` and in `Apply{Name}`. Ignored without `ParameterType`. | | `BuilderMethodName` | `Configure{Name}` | The name of the extension method on `DovetailContextBuilder` that registers a delegate. `Service` is declared with `BuilderMethodName="ConfigureServices"`. | | `GenericParameter` | empty | A type parameter name that makes the joint generic: `I{Name}Joint<in T>`, `Apply{Name}<T>`, `Configure{Name}<T>`. `ParameterType` may be this name, and then the parameter is typed `T`. | | `GenericConstraint` | empty | The constraint of that type parameter: `where T : {GenericConstraint}`. Written as given. Ignored without `GenericParameter`. | | `GenericVariance` | `in` when `GenericParameter` is set | The variance modifier on the type parameter of the generated interfaces and delegates. Ignored without `GenericParameter`. When `ParameterType` is the type parameter, only `in` compiles; see [common mistakes](#common-mistakes). | | `IsAsync` | `true` | `false` generates only the synchronous joint. No `I{Name}AsyncJoint`, `{Name}AsyncJointDelegate` or async `Configure{Name}` overload, no `DovetailJointAsync.{Name}.g.cs`, and `Apply{Name}` returns `void` instead of `ValueTask`. | | `ReturnFirstArgument` | empty (false) | `true` makes `Apply{Name}` return `ValueTask<IDovetailContext>`, the context after the joints ran. It compiles only for a joint whose subject is the context itself: no `ParameterType` and no `ProvideServices`. With `IsAsync` false the result is discarded. | ### The parameter lists [Section titled “The parameter lists”](#the-parameter-lists) `Register` takes, in this order, only the parameters that apply: 1. `IDovetailContext context`, always; 2. `IConfiguration configuration`, with `ProvideConfiguration`; 3. `IServiceCollection services`, with `ProvideServices`; 4. `{ParameterType} {ParameterName}`, with `ParameterType`; 5. `CancellationToken cancellationToken = default`, in the async twin only. `Apply{Name}` is an extension method. Its subject (the `this` parameter) is the `ParameterType` if there is one, otherwise the service collection if `ProvideServices` is set, otherwise the context. After the subject come the context (unless it is the subject), the service collection (if `ProvideServices` and `ParameterType` are both set) and, last, a `CancellationToken cancellationToken = default`. ## What is generated [Section titled “What is generated”](#what-is-generated) Each joint is written to `$(IntermediateOutputPath)`, which is `obj/<Configuration>/<TargetFramework>/`, as ordinary `Compile` items: | File | Contents | | -------------------------------- | --------------------------------------------------------------------------------------------------------------- | | `DovetailJoint.{Name}.g.cs` | `I{Name}Joint`, its delegate, `Apply{Name}` and the `Configure{Name}` method for the delegate. | | `DovetailJointAsync.{Name}.g.cs` | `I{Name}AsyncJoint`, its delegate and the `Configure{Name}` method for it. Not written when `IsAsync` is false. | Everything is declared in `Namespace`: | Type | What it is | | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `I{Name}Joint` | The interface a contributor implements: `void Register(...)`. Mark the class `[DovetailExport]` so it is discovered; see [Defining Dovetails](../../concepts/defining-joints/). | | `{Name}JointDelegate` | A delegate with the same parameters, for registering a lambda. | | `I{Name}AsyncJoint` | The async twin: `ValueTask Register(..., CancellationToken cancellationToken = default)`. | | `{Name}AsyncJointDelegate` | The async delegate. | | `{Name}JointExtensions` | A static partial class holding `Apply{Name}`, which runs every registered `I{Name}Joint` and `I{Name}AsyncJoint` through the executor. | | `{Name}HostBuilderExtensions` | A static partial class with an `extension(DovetailContextBuilder)` block: `Configure{Name}(delegate, priority = 0, category = null, hostType = Undefined)`, once for each delegate type. Generated for every joint, including the ones whose subject is the context. | The interfaces derive from `IDovetailJoint` and, like the delegates, carry `[JointName("{Name}")]`. <DovetailJoint Include="DatabaseConfigurator" Namespace="Joinery.Dovetail.Joints" ParameterType="Sample.Core.Databases.IDatabaseConfigurator" ParameterName="builder" />
```
 sample/Sample.Core/Databases/DatabaseServiceDovetail.cs

 ### A generic joint [Section titled “A generic joint”](#a-generic-joint) `Joinery.Dovetail.Hosting` declares one joint for every host builder. `ParameterType` is the generic parameter, and, with no `GenericVariance`, the interface is contravariant, so `IHostApplicationJoint<IHostApplicationBuilder>` runs for every host whose builder is one: 
```xml
<!-- src/Joinery.Dovetail.Hosting/Joinery.Dovetail.Hosting.csproj -->
<DovetailJoint
    Include="HostApplication"
    Namespace="Joinery.Dovetail.Joints"
    GenericParameter="TBuilder"
    ParameterType="TBuilder"
    ParameterName="builder"
/>
```
 `Joinery.Dovetail` uses the same shape for `HostCreated`, with `GenericParameter="THost"`. ### The rarely needed values [Section titled “The rarely needed values”](#the-rarely-needed-values) Nothing in `src/` or `sample/` sets `ProvideConfiguration`, `GenericConstraint`, `IsAsync` or `ReturnFirstArgument`, so these declarations are compiled, and the signatures they generate checked, by `test/Joinery.Dovetail.Sdk.Tests/DovetailItemReferenceTests.cs` (it declares exactly these items): 
```xml
<DovetailJoint Include="Minimal" />
<DovetailJoint Include="Wired" ProvideConfiguration="true" ProvideServices="true" />
<DovetailJoint Include="Builder" Namespace="Custom.Joints" ProvideServices="true" ParameterType="global::Microsoft.Extensions.Logging.ILoggingBuilder" ParameterName="builder" BuilderMethodName="ConfigureTheBuilder" />
<DovetailJoint Include="Generic" GenericParameter="TBuilder" GenericConstraint="global::Microsoft.Extensions.Hosting.IHostApplicationBuilder" ParameterType="TBuilder" ParameterName="builder" />
<DovetailJoint Include="Covariant" GenericParameter="T" GenericVariance="out" />
<DovetailJoint Include="SyncOnly" IsAsync="false" />
<DovetailJoint Include="Chained" ReturnFirstArgument="true" />
<DovetailJoint Include="ChainedSync" ReturnFirstArgument="true" IsAsync="false" />
<DovetailJoint Include="Unprefixed" ParameterType="Microsoft.Extensions.Logging.ILoggingBuilder" ParameterName="builder" />
<DovetailJoint Include="Ignored" ParameterName="thing" GenericConstraint="class" GenericVariance="out" NMAmespace="Custom.Typo" />
<DovetailJoint Include="Shouting" IsAsync="False" ProvideServices="TRUE" />
<DovetailJoint Include="NotTrue" IsAsync="no" />
```
 * `Minimal` is handed only the context, and its types are in `worker.Joints` (the test project’s `RootNamespace` is `worker`). * `Wired` registers `Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services)`, and its `ApplyWired` is an extension on `IServiceCollection`. * `Builder` is applied with `logging.ApplyBuilder(context, services)` and registered with `ConfigureTheBuilder(...)`. * `Generic` declares `IGenericJoint<in TBuilder> where TBuilder : IHostApplicationBuilder`. * `Covariant` has a type parameter that `Register` does not take, so `out` compiles, and an `ICovariantJoint<string>` is an `ICovariantJoint<object>`. * `SyncOnly` has no async twin, and `context.ApplySyncOnly()` returns `void` but still takes a `CancellationToken`. * `Chained.ApplyChained` returns the context. `ChainedSync` has no async twin and `ApplyChainedSync` returns `void`: the context the executor returns is discarded. * `Unprefixed` is written into the generated code as `Microsoft.Extensions.Logging.ILoggingBuilder`, with nothing in front of it. * `Ignored` generates the same code as `Minimal`: `ParameterName` without a `ParameterType`, `GenericConstraint` and `GenericVariance` without a `GenericParameter`, and the misspelled `NMAmespace` all do nothing, so its types are in `worker.Joints`. * `Shouting` and `NotTrue` are synchronous: `False` and `no` are not `true`. `Shouting` also takes the service collection, because `TRUE` is `true` in any case. ## Common mistakes [Section titled “Common mistakes”](#common-mistakes) * **`ParameterType` and `GenericConstraint` are written exactly as you give them.** Dovetail puts nothing in front of them, so write the type fully qualified with `global::`, as every package in this repository does: `global::Serilog.LoggerConfiguration`. A bare `Serilog.LoggerConfiguration` compiles too, until a namespace that encloses the generated code has a member called `Serilog`, which then captures the name. A project that declares `Custom.Microsoft` does that to a bare `Microsoft.Extensions.Logging.ILoggingBuilder` in a joint in `Custom.Joints`, and the build fails with CS0234. * **A generic joint’s `ParameterType` may be its `GenericParameter`**, and then must be written bare, as `TBuilder`: a `global::` in front of it names a type in the global namespace, not the type parameter. * **`GenericVariance="out"` does not compile when the type parameter is the `ParameterType`** (CS1961): it is an input of `Register`, so a covariant one is invalid, and `in`, the default, is the only value that compiles. With a `GenericParameter` and no `ParameterType`, `Register` does not take the type parameter, and `out` compiles. * **`ReturnFirstArgument` only suits a joint whose subject is the context.** With a `ParameterType` or `ProvideServices` the generated `Apply{Name}` tries to return the `IDovetailContext` as a `ValueTask<ILoggingBuilder>` (or whatever the subject is), which fails with CS0029. * **`ParameterName` without a `ParameterType`, and `GenericConstraint` or `GenericVariance` without a `GenericParameter`, do nothing.** The metadata is ignored, with no warning. * **A misspelled metadata name is ignored too.** `src/Joinery.Dovetail.Aspire.Testing` writes `NMAmespace`, so its namespace is the default, which happens to be the one it meant. * **`IsAsync="false"` leaves contributors no way to do async work for the kind**, since there is no `I{Name}AsyncJoint` to implement. `Apply{Name}` still takes a `CancellationToken`, which the synchronous call ignores. * **The name is part of every generated file and type name**, so declare each joint once. ## See also [Section titled “See also”](#see-also) * [Defining Dovetails](../../concepts/defining-joints/): implementing, ordering and filtering the joints of a kind. * [DovetailHost](../dovetail-host/): the entry points that run the joints. * [Serilog](../../concepts/serilog/) and [OpenTelemetry](../../concepts/opentelemetry/): two packages built on joint kinds.

# DovetailTemplate

> The DovetailTemplate MSBuild item ships C# source from a package and has Dovetail write it into only the projects that should get it. Every metadata value, its default, the gates, and where the generated file lands.

# DovetailTemplate [Section titled “DovetailTemplate”](#dovetailtemplate) A `DovetailTemplate` item names a `*.cs.template` file that a package ships and says which projects should get a copy. When the project’s references have resolved, Dovetail checks every template’s gates, writes the ones that pass to `obj/` and adds them to the compilation. Nothing needs to be compiled against, so the shipping package depends on none of the assemblies its templates use: referencing them is what turns a template on. This page lists what the item accepts. [Shipping templates](../../guides/shipping-templates/) is the guide to using it: how to write a template, how to pack the targets that declare it, and how to test the gates. The item is expanded by MSBuild targets (`Joinery.Dovetail.Templates.targets`), not by the Roslyn source generator. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) A package that wants to put C# into the projects that use it declares its templates from its `build/` or `buildTransitive/` targets. `Joinery.Dovetail.Hosting` is the main user: its ASP.NET Core, MAUI, Uno and Blazor WebAssembly helpers and its OpenTelemetry joints are all templates, which is why that package has no dependency on any of those frameworks. A solution can declare templates in a `Directory.Build.targets` to the same effect. Declare one when the code you ship has to be compiled into the consumer, because it uses types the consumer references and you do not. Do not declare one when ordinary compiled code will do: a library the consumer references is simpler, and a template is only worth it for what needs to be gated on the project. A project that does not run the Dovetail source generator (`Joinery.Dovetail.Analyzers`) gets no templates, however they are gated, since a template is meant to hold joints and `[Embedded]` helpers that the generator discovers. ## Declaring a template [Section titled “Declaring a template”](#declaring-a-template) The item’s `Include` is the template’s name. It names the generated file, so it has to be unique across every package a project references. 
```xml
<!-- a package's declaration, built by test/Joinery.Dovetail.Sdk.Tests/TemplateExtensionPointTests.cs -->
<DovetailTemplate Include="Plain" File="$(MSBuildThisFileDirectory)Plain.cs.template" Package="DovetailTemplateShipper" />
```
 `File` is the only metadata that is required. Leave out `Package`, `References` and `Hosts` and the template goes into every project that runs the generator. ## Metadata [Section titled “Metadata”](#metadata) Metadata is optional unless stated. A name the item does not read is ignored without a warning, so a misspelling falls back to the default. Every gate you set has to pass; a gate you leave out does not restrict anything. Boolean values are compared with `true` ignoring case; any other non-empty value counts as false. | Metadata | Default | What it changes | | --------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `File` | none; required | The full path of the template, usually `$(MSBuildThisFileDirectory)Name.cs.template`. A template without one, or whose file does not exist, fails the build. It must not contain backslashes: MSBuild rewrites them to forward slashes on Linux and macOS when the file is written. | | `Package` | empty | The id of the package that ships the template. The template is only written into a project that references it: the package’s assembly, which is named after the package, is among the project’s resolved references (or, with `DirectReferenceOnly`, the project declares the reference itself). | | `DirectReferenceOnly` | empty (false) | `true` limits the template to projects with a direct reference to `Package`: a `PackageReference` to it (the ones the Dovetail SDK adds count), or a `ProjectReference` to a project named after it. A project that only gets the package transitively gets nothing. Requires `Package`; without it the build fails. | | `References` | empty | Semicolon-separated assembly names (file names without extension). Every one has to be among the project’s resolved references. | | `Hosts` | empty | Semicolon-separated `DovetailHost` names, at least one of which the project has to declare: the host model, as `Joinery.Dovetail.Sdk` detects it (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui`, `Uno`). These are the hosts declared when the templates resolve, before a package narrows them. | | `HostName` | empty | Replaces `{HostName}` in the template, but only when `HostType` is set too. | | `HostType` | empty | Replaces `{HostType}` in the template, and switches the `{HostName}` replacement on. Together they let one template be emitted once per host model under different names. | | `OutputPrefix` | `DovetailTemplate` | The prefix of the generated file name, `<prefix>.<name>.g.cs`. | The gates are applied together, and a template that fails any of them is not written. They are read once the project’s references have resolved, which is right after `ResolveAssemblyReferences` and before the compiler runs. ## What is generated [Section titled “What is generated”](#what-is-generated) Each template that passes is written to `$(IntermediateOutputPath)`, which is `obj/<Configuration>/<TargetFramework>/`, as an ordinary `Compile` item: | File | Contents | | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | | `<prefix>.<name>.g.cs` | The template’s text, with `{HostName}` and `{HostType}` replaced when `HostType` is set. The prefix is `OutputPrefix`, `DovetailTemplate` by default. | The item adds no namespace, type or method of its own: the template is the C#. For `Joinery.Dovetail.Hosting`, which sets `OutputPrefix="DovetailHosting"`, a generic-host application gets `obj/Debug/net10.0/DovetailHosting.DovetailHostApplicationHelpers.g.cs`. The templates that passed are the `DovetailEmittedTemplate` items, with the metadata above carried over. A target can add to them or remove from them between `DovetailResolveTemplates` and `DovetailGenerateTemplates`; the guide shows how. ## Examples [Section titled “Examples”](#examples) ### Minimal [Section titled “Minimal”](#minimal) The declaration above is the one the extension-point tests build. They pack a package that ships it, reference it from projects that declare the reference themselves and from one that only receives it transitively, and read which `DovetailTemplate.*.g.cs` files land in each `obj/`. ### A package that ships many [Section titled “A package that ships many”](#a-package-that-ships-many) `Joinery.Dovetail.Hosting` lists its helpers with the assemblies each needs, then declares every one as a template for the package: 
```xml
<!-- src/Joinery.Dovetail.Hosting/build/Joinery.Dovetail.Hosting.targets (verbatim) -->
  <ItemGroup>
    <_DovetailHostingHelper Include="DovetailHostApplicationHelpers" References="Microsoft.Extensions.Hosting" />
    <_DovetailHostingHelper Include="DovetailHostLifecycleHelpers" References="Microsoft.Extensions.Hosting" />
    <_DovetailHostingHelper Include="DovetailMauiHelpers" References="Microsoft.Maui" />
    <_DovetailHostingHelper Include="DovetailUnoHelpers" References="Uno.Extensions.Hosting.WinUI" />
    <_DovetailHostingHelper Include="DovetailUnoNavigationHelpers" References="Uno.Extensions.Hosting.WinUI;Uno.Extensions.Navigation.UI" />
    <_DovetailHostingHelper Include="DovetailWebAssemblyHelpers" References="Microsoft.AspNetCore.Components.WebAssembly" />
    <_DovetailHostingHelper Include="DovetailConfigurationSchemaEndpointExtensions" References="Microsoft.AspNetCore" />
  </ItemGroup>
  <ItemGroup>
    <DovetailTemplate
      Include="@(_DovetailHostingHelper)"
      File="$(MSBuildThisFileDirectory)%(Identity).cs.template"
      Package="Joinery.Dovetail.Hosting"
      OutputPrefix="DovetailHosting"
    />
  </ItemGroup>
```
 `References` carries over from `_DovetailHostingHelper` to each template, so a project gets `DovetailMauiHelpers` only when it references `Microsoft.Maui`. ### One template for several hosts [Section titled “One template for several hosts”](#one-template-for-several-hosts) The OpenTelemetry start joint is one template emitted once per host model, which is what `HostName` and `HostType` are for. The package adds the instances to `DovetailEmittedTemplate` itself, because which of them a host needs depends on helpers that have already been resolved: 
```xml
<!-- src/Joinery.Dovetail.Hosting/build/Joinery.Dovetail.Hosting.targets: one of the items of an ItemGroup, verbatim apart from the indentation -->
<DovetailEmittedTemplate
  Include="DovetailOpenTelemetryMauiStartJoint"
  Condition="'$(_DovetailHostingMaui)' == 'true'"
  File="$(MSBuildThisFileDirectory)DovetailOpenTelemetryStartJoint.cs.template"
  OutputPrefix="DovetailHosting"
  HostName="Maui"
  HostType="global::Microsoft.Maui.Hosting.MauiApp" />
```
 ### The gates, built [Section titled “The gates, built”](#the-gates-built) `test/Joinery.Dovetail.Sdk.Tests/DovetailItemReferenceTests.cs` builds a project that declares the following, and checks which files land in `obj/` (the project is a generic-host application that references `Microsoft.Extensions.Hosting`; its templates are `Plain.cs.template`, and so on): 
```xml
<DovetailTemplate Include="Plain" File="$(MSBuildThisFileDirectory)Plain.cs.template" />
<DovetailTemplate Include="Prefixed" File="$(MSBuildThisFileDirectory)Prefixed.cs.template" OutputPrefix="Contoso" />
<DovetailTemplate Include="Referenced" File="$(MSBuildThisFileDirectory)Referenced.cs.template" References="Microsoft.Extensions.Hosting" />
<DovetailTemplate Include="MissingReference" File="$(MSBuildThisFileDirectory)MissingReference.cs.template" References="Microsoft.Extensions.Hosting;Not.Referenced.Anywhere" />
<DovetailTemplate Include="ForThisHost" File="$(MSBuildThisFileDirectory)ForThisHost.cs.template" Hosts="Maui;HostApplication" />
<DovetailTemplate Include="ForOtherHosts" File="$(MSBuildThisFileDirectory)ForOtherHosts.cs.template" Hosts="Maui;Uno" />
<DovetailTemplate Include="PerHost" File="$(MSBuildThisFileDirectory)PerHost.cs.template" HostName="Mine" HostType="global::System.Object" />
<DovetailTemplate Include="NameOnly" File="$(MSBuildThisFileDirectory)NameOnly.cs.template" HostName="Mine" />
```
 `Plain`, `Referenced`, `ForThisHost`, `PerHost` and `NameOnly` are written, `Prefixed` as `Contoso.Prefixed.g.cs`; `MissingReference` and `ForOtherHosts` are not. In `PerHost` `{HostName}` and `{HostType}` are replaced; in `NameOnly` the text `{HostName}` is left as it is. ## Common mistakes [Section titled “Common mistakes”](#common-mistakes) * **`Include` is the file name, so it has to be unique across packages.** Two templates with one name write one file. * **`File` has to be a full path.** Use `$(MSBuildThisFileDirectory)`, which is the directory of the targets file that declares the item. A missing `File` fails the build with `the template '<name>' has no File`, and a path that does not exist with `names a file that doesn't exist`. * **`DirectReferenceOnly` without `Package` fails the build** (`is DirectReferenceOnly, so it needs the Package it is direct to`). * **`Package` is matched against an assembly name.** It is the package’s id, and it has to be the name of the package’s assembly as well, since that is what the project’s resolved references are searched for. * **`HostName` alone does nothing.** `{HostName}` is replaced only when `HostType` is set; set both. * **`Hosts` names are `DovetailHost` names.** Each is matched, by name, against the `DovetailHost` items declared when the templates resolve, which are the ones `Joinery.Dovetail.Sdk` detected (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui`, `Uno`) plus any you declared. See [DovetailHost](../dovetail-host/). * **A transitive reference declares your items but gets no file under `DirectReferenceOnly`.** Its `buildTransitive/` targets still run, so the `DovetailTemplate` items are there; the gate is what leaves the file out. * **A misspelled metadata name is ignored.** The default applies, with no warning. * **Templates do not reach projects that skip the generator.** A project without `Joinery.Dovetail.Analyzers` gets none. ## See also [Section titled “See also”](#see-also) * [Shipping templates](../../guides/shipping-templates/): the guide to writing, packing and testing templates. * [DovetailHost](../dovetail-host/): the hosts that `Hosts` refers to, and the helpers `Joinery.Dovetail.Hosting` ships as templates. * [DovetailJoint](../dovetail-joint/): the joint kinds a template can declare joints of.
