# Dovetail

> Joint-driven application wiring for .NET. AOT-safe, zero runtime reflection.

AOT & Trim Safe Generated code requires zero runtime reflection — fully compatible with .NET Native AOT and IL trimming. Module Wiring Define services, configuration, logging, and hosting as assembly-level joints resolved at build time by a Roslyn source generator. Composable First-class support for Generic Host, ASP.NET Core, Autofac, DryIoc, Serilog, .NET Aspire, and ModularPipelines — all wired automagically.

# Configuration Files

> How the Dovetail SDK renames, packs, copies, embeds and loads a library's appsettings files in JSON, YAML or TOML.

# Configuration Files [Section titled “Configuration Files”](#configuration-files) A library’s configuration values ship in its own `appsettings` files, and the Dovetail SDK takes them to every application that references it. Binding those values to types, and the JSON Schema editors use, come from [Optionary](./configuration-with-optionary). Defaults live in a normal `appsettings` file in the library. The SDK renames it, packs it, and loads it into the host’s configuration, where the options binding (Optionary’s, or your own) picks it up: 
```plaintext
MyLibrary/
├── appsettings.yaml
├── appsettings.Development.yaml
├── appsettings.local.yaml   # never packed, never committed
└── MyLibrary.csproj
```
 * `appsettings.{ext}` becomes `MyLibrary.{ext}` (`appsettings.Production.json` becomes `MyLibrary.Production.json`), so several libraries can ship their own file into one output directory. The name is the project’s assembly name (`AssemblyName`, which defaults to the project’s name): the `ApplicationName` the runtime conventions look for. * The files are packed under `contentFiles/any/any/configuration/`, copied to a same-solution host’s output directory through a `ProjectReference`, and restored from the package otherwise. * The generated joint loads, in ascending precedence, `MyLibrary.{ext}`, `MyLibrary.{Environment}.{ext}` and `MyLibrary.local.{ext}`. The `local` layer is never packed, and the SDK warns when no `.gitignore` at or above the project ignores `appsettings.local.*` (a `*.local.*` entry counts too). * YAML has two extensions and one joint. It requires `MyLibrary.yaml` or `MyLibrary.yml`, whichever the library has, not both, and reads the environment and local layers with either extension, `.yaml` before `.yml` in each layer. * A file-based app (`dotnet run Build.cs`) is named after its assembly, `Build`, without the `.cs`: its `appsettings.{ext}` files, next to `Build.cs`, are copied to its output directory as `Build.{ext}`, with or without the Dovetail SDK. At run time, though, the configuration joints read the files from next to `Build.cs` (the directory the .NET SDK names in the `EntryPointFileDirectoryPath` AppContext data), under their source names, so an edit takes effect on the next run without a rebuild. A host or pipeline whose configuration was given a base path or file provider of its own keeps it. * Outside a file-based app, the joints read the files through the host’s own file provider, the one its configuration uses for `appsettings.json`: the host roots it at its content root, unless `SetBasePath` or `SetFileProvider` pointed it somewhere else. * To read the files from another directory, set `Dovetail:ConfigurationDirectory` (`DovetailSettings.ConfigurationDirectory`) in the host’s configuration, for example `Dovetail__ConfigurationDirectory=./config` or `--Dovetail:ConfigurationDirectory=./config`. A relative path is resolved against the current directory. It wins over everything above. The `Dovetail__ConfigurationDirectory` environment variable is read directly too, for hosts whose configuration doesn’t read environment variables. * Every host that reads the files from disk (the generic host, ASP.NET Core, ModularPipelines, Uno) picks the directory in the same order: `Dovetail:ConfigurationDirectory`, then the directory of a file-based app’s entry point file, then the host’s own file provider. Configuration embedded in the application (MAUI and Uno apps) still wins over all of them: a MAUI app always reads its embedded copies, and a browser (WebAssembly) host fetches its files over HTTP. ### Naming the source files [Section titled “Naming the source files”](#naming-the-source-files) A library’s configuration files can be written under either of two names, and both end up in the same place: | Source file | Copied, packed and embedded as | Included when | | ------------------------------------------------------ | -------------------------------------------------- | -------------------------- | | `appsettings.{ext}`, `appsettings.{Environment}.{ext}` | `MyLibrary.{ext}`, `MyLibrary.{Environment}.{ext}` | `appsettings.{ext}` exists | | `MyLibrary.{ext}`, `MyLibrary.{Environment}.{ext}` | the same name | `MyLibrary.{ext}` exists | | `appsettings.local.{ext}` or `MyLibrary.local.{ext}` | `MyLibrary.local.{ext}`, never packed | as above | `MyLibrary` is the assembly name, as above: in a `lib.csproj` whose `AssemblyName` is `Contoso.Library`, `Contoso.Library.yaml` is configuration and `lib.yaml` is an ordinary file, because nothing would load a `lib.yaml`. A file-based app’s `Build.yaml`, next to `Build.cs`, is included the same way. Files named after the assembly are treated exactly like the `appsettings` ones: copied to the output directory, packed under `contentFiles/any/any/configuration/`, embedded, loaded by the generated joint, and added to a file-based app’s items. `MyLibrary.schema.json` and a file-based app’s `Build.run.json` (its launch profiles) are not configuration and are left alone. `appsettings.local.*` doesn’t ignore `MyLibrary.local.{ext}`, so when one exists the SDK warns, naming the file, until a `.gitignore` has `MyLibrary.local.*` or `*.local.*`, which covers both. Each pair of names that would land on the same file, such as `appsettings.yaml` and `MyLibrary.yaml`, or `appsettings.Development.yaml` and `MyLibrary.Development.yaml`, fails the build with `DT0019`; keep one of them. Different extensions are different files, so `appsettings.yaml` and `MyLibrary.yml` coexist, as do `appsettings.yaml` and `MyLibrary.Development.yaml` (which is only included next to a `MyLibrary.yaml`). ### Opting in [Section titled “Opting in”](#opting-in) * JSON, YAML and TOML are supported. Opt in with `DovetailEnableConfiguration`; YAML is the default format, and `DovetailEnableJsonConfiguration` or `DovetailEnableTomlConfiguration` chooses another. Hosts with no file system (MAUI, Uno) read copies embedded in the assembly: `DovetailEmbedConfiguration`. | Property | Default | Purpose | | --------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------- | | `DovetailEnableConfiguration` | `false` | Turns the pipeline on. Existing consumers see no change until it or a format flag is set. | | `DovetailEnableYamlConfiguration` | `true` when no other format is set | Adds the YAML provider. Setting it to `true` also enables the pipeline. | | `DovetailEnableJsonConfiguration` | `false` | Adds the JSON provider. Setting it to `true` also enables the pipeline, replacing the YAML default. | | `DovetailEnableTomlConfiguration` | `false` | Adds the TOML provider. Setting it to `true` also enables the pipeline, replacing the YAML default. | | `DovetailPackConfiguration` | `true`, `false` if not packable | Packs the library’s configuration files into the package. | ## Diagnostics [Section titled “Diagnostics”](#diagnostics) | Id | Severity | Meaning | | -------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | | `DT0019` | Error | A project has both `appsettings{suffix}.{ext}` and `{AssemblyName}{suffix}.{ext}`, which land on the same file. Reported by the build; keep one. |

# Configuration with Optionary

> Bind options from configuration and get a JSON Schema for editors with Optionary; what Dovetail adds on top, and what was renamed.

# Configuration with Optionary [Section titled “Configuration with Optionary”](#configuration-with-optionary) Dovetail’s options binding and configuration schema moved to their own package, [Optionary](https://rocketsurgeonsguild.github.io/Optionary/). Optionary’s source generator reads an options type and produces a reflection-free binder that registers it as `IOptions<T>`, and a JSON Schema fragment that its build merges into each application’s `appsettings.schema.json` for editor completion and validation. Optionary works without Dovetail; Dovetail registers what Optionary generates for you and tells it which projects are applications. Dovetail doesn’t depend on Optionary. Add it to the projects that declare options: 
```xml
<ItemGroup>
  <PackageReference Include="Optionary" Version="0.1.1" />
</ItemGroup>
```
 Then put `[Optionary]` on the options type, or `[assembly: Optionary<T>("Section")]` for a type you don’t own: 
```c#
using Optionary;


/// <summary>Options for the greetings this library prints.</summary>
[Optionary]
public sealed class GreetingsOptions
{
    /// <summary>What the greeting says before the name.</summary>
    public string Message { get; set; } = "Hello";
}
```
 Consume it the usual way, with `IOptions<GreetingsOptions>`, `IOptionsSnapshot<T>` or `IOptionsMonitor<T>`. Section names, key styles, validation, supported types, the schema and editor setup are all described in [Optionary’s documentation](https://rocketsurgeonsguild.github.io/Optionary/getting-started/). The [`SdkSample.Greetings`](https://github.com/RocketSurgeonsGuild/Dovetail/tree/main/sample/SdkSample/SdkSample.Greetings) project is a working example. ## What Dovetail adds [Section titled “What Dovetail adds”](#what-dovetail-adds) * **The joint.** Optionary emits `OptionaryConfigurationOptions.AddOptionaryConfigurationOptions(services)` in the project’s `RootNamespace`. When an assembly declares at least one `[Optionary]` type, Dovetail’s generator exports a joint that calls it, listed first so options are bound before other joints configure them in code. Every host that references the assembly registers its options, so there is nothing to call. Below C# 12 Dovetail emits nothing and reports `DT0006`. * **Host detection.** An application the [Dovetail SDK](../guides/microsoft-sdks) detects (ASP.NET Core, the generic host, Blazor WebAssembly, MAUI, Uno) is an Optionary schema host: Dovetail sets `OptionarySchemaHost` to `true` unless the project set it. * **Embedded hosts.** A host that embeds its configuration (`DovetailEmbedConfiguration`, which the SDK sets for MAUI and Uno applications) keeps the schema in `obj/` for editors: Dovetail sets `OptionarySchemaCopyToOutput` to `false`. * **ZeroAlloc.** `DovetailEnableZeroAllocValidation=false` also sets `OptionaryZeroAllocValidation` to `false`, so Optionary doesn’t call `ValidateWithZeroAlloc()` either. See [ZeroAlloc](./zeroalloc#validating-configuration). * **Serilog.** `Joinery.Dovetail.Serilog` ships a schema fragment for the `Serilog` section, which Optionary merges into an application’s schema like any other. See [Serilog](./serilog). * **The schema endpoint**, below. * **Configuration files.** Shipping a library’s `appsettings` files in JSON, YAML or TOML stays in Dovetail: see [Configuration Files](./configuration-files). These hook properties have no effect in a project that doesn’t reference Optionary, and Dovetail adds no warnings about it: an application without Optionary just has no schema. ## The schema endpoint [Section titled “The schema endpoint”](#the-schema-endpoint) An application can also serve the schema Optionary writes, for tools that read it over HTTP. This needs an ASP.NET Core application that references Joinery.Dovetail.Hosting, and is off by default: 
```xml
<PropertyGroup>
  <DovetailConfigurationSchemaEndpoint>true</DovetailConfigurationSchemaEndpoint>
  <!-- Optional: serve it only in these environments -->
  <DovetailConfigurationSchemaEndpointEnvironments>Development;Staging</DovetailConfigurationSchemaEndpointEnvironments>
</PropertyGroup>
```
 | Property | Default | Effect | | --------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `DovetailConfigurationSchemaEndpoint` | off | `true` generates a joint that maps the endpoint. Only projects with `OutputType` `Exe` or `WinExe` that reference ASP.NET Core and Joinery.Dovetail.Hosting get it. | | `DovetailConfigurationSchemaEndpointEnvironments` | every environment | A semicolon-separated list of environment names (`Development;Staging`, compared ignoring case). The endpoint is mapped only when the host environment is one of them. | | `DovetailConfigurationSchemaEndpointSourceFallback` | `true` except below | Whether the project’s `obj/` directory is compiled into the application as a place to look for the schema. By default it is, except in publish builds and `ContinuousIntegrationBuild` builds, so a build machine path isn’t shipped. `false` never embeds it. | The route is `GET /.well-known/dovetail/configuration-schema`: * It looks for `appsettings.schema.json` in the application’s output directory first, then in the embedded `obj/` fallback directory, which is how it works when run from source with no copy beside the assembly. A published application serves the copy published with it. * The response is `application/schema+json` with a strong `ETag` and `Cache-Control: no-cache`. A request with a matching `If-None-Match` gets `304 Not Modified`. The file is re-read when it changes on disk. * It answers `404` when neither location has the file, which is always the case in an application that doesn’t reference Optionary. Point a mapping at the URL, for example `"url": "http://localhost:5000/.well-known/dovetail/configuration-schema"` in `json.schemas`. To map it yourself, call the extension on the `WebApplication` (or any `IEndpointRouteBuilder`) instead of setting the property. Joinery.Dovetail.Hosting emits it into every ASP.NET Core project that references it, as an internal type. Both arguments are optional, and the method returns `null` when `environments` excludes the current environment: 
```c#
using Joinery.Dovetail.Hosting;


app.MapDovetailConfigurationSchema(fallbackDirectory: null, environments: "Development")
   ?.RequireAuthorization();
```
 Caution The schema lists every configuration key your application and its libraries accept, including the section names of libraries you may not want to advertise. Unless you restrict it, the endpoint is mapped in every environment, production included, and anyone who can reach the application can read it, with no authentication. Set `DovetailConfigurationSchemaEndpointEnvironments` to the environments that need it (usually `Development`), map it yourself and add authorization, or leave it off. ## Upgrading from Dovetail 0.6 [Section titled “Upgrading from Dovetail 0.6”](#upgrading-from-dovetail-06) This is a clean break: nothing old keeps working alongside the new names. Add the `Optionary` package to every project that declares configuration, then rename: | Dovetail 0.6 | Optionary | | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | | `Joinery.Dovetail.Attributes.DovetailConfigurationAttribute` | `Optionary.OptionaryAttribute` | | `Joinery.Dovetail.Attributes.DovetailConfigurationAttribute<T>` | `Optionary.OptionaryAttribute<T>` | | `Joinery.Dovetail.Attributes.ConfigurationKeyStyle` | `Optionary.ConfigurationKeyStyle` (same values) | | `DovetailConfigurationOptionsExtensions.AddDovetailConfigurationOptions<T>` | `OptionaryServiceCollectionExtensions.AddOptionaryOptions<T>` | | Assembly metadata prefix `Dovetail.ConfigurationSchema.v1:` | `Optionary.Schema.v1:` | | `DovetailConfigurationSchema` | `OptionarySchema` | | `DovetailConfigurationSchemaHost` | `OptionarySchemaHost` | | `DovetailConfigurationSchemaStrict` | `OptionarySchemaStrict` | | `DovetailConfigurationSchemaIncludeSchemaStore` | `OptionarySchemaIncludeSchemaStore` | | `DovetailConfigurationSchemaRequired` | `OptionarySchemaRequired` | | `DovetailConfigurationSchemaVisualStudio` | `OptionarySchemaVisualStudio` | | `DovetailScaffoldEditorSettings` | `OptionaryScaffoldEditorSettings` | | `DovetailEditorSettingsDirectory` | `OptionaryEditorSettingsDirectory` | | `DovetailConfigurationReferenceDocumentation` | `OptionaryReferenceDocumentation` | | `AdditionalFiles` metadata `DovetailReferenceDocumentation` | `OptionaryReferenceDocumentation` | | `DT0007`–`DT0016`, `DT0018` | `OPT0002`–`OPT0012` ([diagnostics](https://rocketsurgeonsguild.github.io/Optionary/reference/diagnostics/)) | * A library packed with Dovetail 0.6 or earlier carries `Dovetail.ConfigurationSchema.v1:` fragments, which Optionary doesn’t read. Its sections are missing from the merged schema until it is rebuilt with Optionary. Binding is unaffected for libraries you rebuild: `[DovetailConfiguration]` no longer compiles, so nothing is lost silently. * `DovetailEnableZeroAllocValidation`, `DovetailEmbedConfiguration` and the `DovetailConfigurationSchemaEndpoint*` properties keep their names: they are Dovetail’s. * The generated joint is now `OptionaryConfigurationOptionsJoint`; nothing should refer to it by name.

# Dovetail Context

> The context object passed to every joint — how to create, configure, and query it.

# Dovetail Contexts [Section titled “Dovetail Contexts”](#dovetail-contexts) The joint context is the the result of collecting all the known joints for a given set of assembly. How those assemblies are collected can diff depending on on the joint context is created. Generally the joint context is created using the <xref:Joinery.Dovetail.DovetailContextBuilder> however you can implement your own <xref:Joinery.Dovetail.IDovetailContext> if you wish. ## Builder [Section titled “Builder”](#builder) A joint context is created from a <xref:Joinery.Dovetail.DovetailContextBuilder>. This class is used during the bootstrapping phase of your application. You can add joints manually, you can add them via attribute scanning, you can disable attribute scanning if you wish as well. ## Creating the context [Section titled “Creating the context”](#creating-the-context) A context can be created from a <xref:Joinery.Dovetail.DovetailContextBuilder> by using [DovetailContext.From](xref:Joinery.Dovetail.DovetailContext#Joinery_Dovetail_DovetailContext_From_Dovetail_DovetailContextBuilder_). ## Categories [Section titled “Categories”](#categories) Every joint has a category. `DovetailCategory.Core` is for infrastructure joints (serializers, logging), and `DovetailCategory.Application` is the default for everything else. `DovetailContextBuilder.Create(joints, properties, categories)` takes a set of categories as well, and **the context loads the joints whose category is in that set, plus the `Core` joints, which are always loaded**. An empty set loads the `Application` joints and the `Core` joints, which is what the generated `Imports.Joints()` and `DovetailContextBuilder.Create()` pass when you give them no categories. A joint in any other category is loaded only when you name its category. | `categories` | Joints in the context | | ------------------------------------------------------- | --------------------------------------------------------------------------------- | | `[]` | The `Application` and the `Core` joints | | `[DovetailCategory.Core]` | Only the `Core` joints | | `[DovetailCategory.Application]` | The `Application` and the `Core` joints | | `[DovetailCategory.Core, DovetailCategory.Application]` | The `Application` and the `Core` joints | | `["Reporting"]` | The joints in `Reporting` and the `Core` joints, but not the `Application` joints | The set is available as `Categories` on the builder and on the context. It is the set that is loaded: the set you passed in with `Core` added, or `Application` and `Core` when you passed none. ## Using the context [Section titled “Using the context”](#using-the-context) Once the context is created you can use the context to find out all sorts of information. Useful properties: * [`AssemblyProvider`](xref:Joinery.Dovetail.IDovetailContext#Joinery_Dovetail_DovetailContext_AssemblyProvider) - The type provider can be used to get a list of assemblies * [`Properties`](xref:Joinery.Dovetail.IDovetailContext#Joinery_Dovetail_DovetailContext_Properties) - Contains all the properties provided to the builder. This implements `IServiceProvider` and can be used with \`ActivatorExtensions Useful methods / extension methods: * [`Get<T>([string name])`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_Get__1_Dovetail_IDovetailContext_) - Get a given type from the `Properties` dictionary. * [`GetHostType()`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_GetHostType_Dovetail_IDovetailContext_) - Get’s the given host type, as defined in the builder. * [`IsUnitTestHost()`](xref:Joinery.Dovetail.DovetailContextExtensions#Joinery_Dovetail_DovetailContextExtensions_IsUnitTestHost_Dovetail_IDovetailContext_) - Tests if the builder was setup for unit testing * This is handy to ensure different behavior during [unit tests](./unit-tests.md).

# Defining Dovetails

> How to create and register your own joints, including ordering and host type filtering.

# Defining Dovetail Joints [Section titled “Defining Dovetail Joints”](#defining-dovetail-joints) As stated previously joints are nothing more than a class that implements <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint>. ## Declaring a new kind of joint [Section titled “Declaring a new kind of joint”](#declaring-a-new-kind-of-joint) Everything below is about writing joints for kinds that already exist, such as `IServiceJoint` or `ISerilogJoint`. A package or application adds a new kind, a typed extension point other code can contribute to, with a single `<DovetailJoint>` item in its project file; the build generates the interface, the delegates and the `Apply` and `DovetailContextBuilder` methods for it. The [`DovetailJoint` reference](../../reference/dovetail-joint/) lists everything the item accepts. The entry points that run the joints come from a [`DovetailHost`](../../reference/dovetail-host/) item, which the SDK declares for most projects. ## Implementing Multiple Dovetail Joints [Section titled “Implementing Multiple Dovetail Joints”](#implementing-multiple-dovetail-joints) A defined joint can implement as many joints as you want. Configuration, Services, Command Line, Custom Dovetail Joints can all be handled by one joint. 
```c#
public class MultipleDovetail : IServiceJoint, IConfigurationJoint
{
    public void Register(IDovetailContext context, IServiceCollection services) { }
    public void Register(IDovetailContext context, IConfigurationBuilder builder) { }
}
```
 ### What `Register` takes [Section titled “What Register takes”](#what-register-takes) The build generates each joint interface from its [`<DovetailJoint>`](../../reference/dovetail-joint/) declaration, so what `Register` takes depends on the kind: the context first, then whatever the kind hands over. | Kind | Interface | `Register` | | ------------- | -------------------------- | ------------------------------------------------------------------- | | Setup | `ISetupJoint` | `Register(IDovetailContext context)` | | Service | `IServiceJoint` | `Register(IDovetailContext context, IServiceCollection services)` | | Configuration | `IConfigurationJoint` | `Register(IDovetailContext context, IConfigurationBuilder builder)` | | Logging | `ILoggingJoint` | `Register(IDovetailContext context, ILoggingBuilder builder)` | | Host created | `IHostCreatedJoint<THost>` | `Register(IDovetailContext context, THost host)` | Every kind has an async twin, such as `IServiceAsyncJoint`, whose `Register` returns a `ValueTask` and takes a trailing `CancellationToken cancellationToken = default`. None of Dovetail’s own kinds hands over an `IConfiguration`. A joint that needs the configuration reads `context.Configuration`. A kind that is declared with `ProvideConfiguration="true"` does get an `IConfiguration configuration` parameter, after the context; the [`DovetailJoint` reference](../../reference/dovetail-joint/#the-parameter-lists) lists every parameter a kind can have, in the order they come in. ## Dovetail Ordering [Section titled “Dovetail Ordering”](#dovetail-ordering) By default the order of joints is [non-deterministic](https://en.m.wikipedia.org/wiki/Nondeterministic_algorithm) and not controlled. Dovetails are “left in place” such that once the list of joints is created it is not changed between runs. Sometimes you want to ensure that one joint runs before another, that can be done using different attributes. Delegate joints *cannot* be ordered in this manner and must be sorted manually. ### [\[BeforeDovetail\]](xref:Joinery.Dovetail.BeforeJointAttribute) / [\[DependentOfDovetail\]](xref:Joinery.Dovetail.DependentOfJointAttribute) [Section titled “\[BeforeDovetail\] / \[DependentOfDovetail\]”](#beforedovetail--dependentofdovetail) This attribute can be used to ensure that your joint is called before another joint. The order is still non-deterministic but Dovetail will ensure that the defined joint is run before the joint type defined by the attribute. 
```c#
// A before B
[BeforeDovetail(typeof(DovetailB))]
public class DovetailA
{
}


public class DovetailB
{
}
```
 ### [\[AfterDovetail\]](xref:Joinery.Dovetail.AfterJointAttribute) / [\[DependsOnDovetail\]](xref:Joinery.Dovetail.DependsOnJointAttribute) [Section titled “\[AfterDovetail\] / \[DependsOnDovetail\]”](#afterdovetail--dependsondovetail) This attribute can be used to ensure that your joint is called after another joint. The order is still non-deterministic but Dovetail will ensure that the defined joint is run after the joint type defined by the attribute. 
```c#
// B before A
[AfterDovetail(typeof(DovetailB))]
public class DovetailA
{
}


public class DovetailB
{
}
```
 ### Custom Attributes [Section titled “Custom Attributes”](#custom-attributes) If you want you can define your own custom attribute for use with joint ordering. Your attribute must implement <xref:Joinery.Dovetail.IDovetailDependency> and specify the <xref:Joinery.Dovetail.DependencyDirection>. ## Dovetail Host Type [Section titled “Dovetail Host Type”](#dovetail-host-type) You can define a joint that only runs for a given <xref:Joinery.Dovetail.HostType>. The HostType can be defined on the <xref:Joinery.Dovetail.DovetailContextBuilder> using `Set<DovetailHostType>(DovetailHostType.UnitTest)`. Using the `DovetailHostType` an assembly can define different behaviors given the context. The generated `Imports` class sets the host type only when the build specifies one. The `DovetailHostType` MSBuild property (`Live` or `UnitTest`) takes precedence; otherwise test projects (`IsTestProject`) get `UnitTest`. Anywhere else the host type is left unset, and the hosting extensions set it to `Live` if nothing else has. A good example of this is designing a system that uses [NodaTime](https://nodatime.org/). You can have a [\[LiveJoint\]](xref:Joinery.Dovetail.LiveJointAttribute) that registers `IClock` using the expected calendar system, and another [\[UnitTestJoint\]](xref:Joinery.Dovetail.UnitTestJointAttribute) that registers a `FakeClock` with a predefined starting date and time. * `Undefined` - The default host type, means the joint runs everywhere. * `Live` - This joint applies in a live running application * `UnitTest` - This joint applies to unit tests. ### [\[LiveJoint\]](xref:Joinery.Dovetail.LiveJointAttribute) [Section titled “\[LiveJoint\]”](#livejoint) This attribute ensures a joint that only runs when the `DovetailHostType` is `Live`. 
```c#
[LiveJoint]
public class DovetailA
{
}
```
 ### [\[UnitTestJoint\]](xref:Joinery.Dovetail.UnitTestJointAttribute) [Section titled “\[UnitTestJoint\]”](#unittestjoint) This attribute ensures a joint that only runs when the `DovetailHostType` is `UnitTest`. 
```c#
[UnitTestJoint]
public class DovetailA
{
}
```
 ### \[DovetailHostType] [Section titled “\[DovetailHostType\]”](#dovetailhosttype) The general form of the two attributes above. It takes the host type the joint applies to, for example `[DovetailHostType(DovetailHostType.Live)]`. It is also the only way to declare `Undefined` explicitly. ### Which attributes are honoured where [Section titled “Which attributes are honoured where”](#which-attributes-are-honoured-where) A joint reaches a context by one of two paths, and both honour all three attributes the same way: | Path | `[LiveJoint]` / `[UnitTestJoint]` | `[DovetailHostType]` | | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- | -------------------- | | Runtime reflection: `DovetailContextBuilder.AppendJoint(...)` / `PrependJoint(...)` with a joint instance or `AppendJoint<T>()` | Honoured | Honoured | | Generated metadata: the joints marked `[DovetailExport]`, which the source generator lists in the generated `Exports` class at build | Honoured | Honoured | On both paths: * `[LiveJoint]` and `[UnitTestJoint]` are read before `[DovetailHostType]`, so `[LiveJoint]` wins over a `[DovetailHostType]` on the same joint. Declaring both `[LiveJoint]` and `[UnitTestJoint]` on one joint isn’t meaningful, and which of them applies is not specified. * The attributes are inherited. A joint that derives from a `[LiveJoint]` class is a live joint too, and the closest declaration wins. * A joint that declares nothing has the `Undefined` host type and applies everywhere, apart from the test project default below. * A joint applies when its host type is `Undefined` or equals the host type of the context. The generated path adds one default of its own. In a test project (`IsTestProject`), an exported joint that declares no host type is exported as `UnitTest`. A joint’s own attribute always takes precedence over that default, so a `[LiveJoint]` in a test project stays live-only and `[DovetailHostType(DovetailHostType.Undefined)]` opts a joint out of the default. The runtime reflection path has no such default. ## Dovetail Category [Section titled “Dovetail Category”](#dovetail-category) Every joint belongs to a category, a `DovetailCategory`, which is part of the joint’s metadata. A joint declares its category with `[DovetailCategory]`. The attribute takes a string: `DovetailCategory.Application` and `DovetailCategory.Core` are constants for the two well-known categories, and any other string is a category of its own. 
```c#
[DovetailExport]
[DovetailCategory(DovetailCategory.Core)]
public class CoreTimeJoint : IServiceJoint
{
    public void Register(IDovetailContext context, IServiceCollection services)
    {
        //...
    }
}
```
 A joint reaches a context by one of two paths, and both give it the same category: * A joint that declares none is in the `Application` category. * A joint that declares `[DovetailCategory(X)]` is in category `X`, whether it is added at runtime with `AppendJoint(...)` / `PrependJoint(...)` or exported with `[DovetailExport]`. The generated `Exports` class writes the category into each joint’s metadata as plain C#, the constant for `Application` and `Core` and a string literal for any other, so the exported joint above is described with category `Core`. Nothing is reflected on, and a joint that takes constructor parameters (created by a factory) gets its category the same way. * The attribute is inherited. A joint that derives from a `[DovetailCategory]` class is in that category too, and the closest declaration wins. A `[DovetailCategory]` on an interface the joint implements doesn’t count, because looking up an attribute on a type reads its base classes and not its interfaces. * The category is independent of the host type above; a joint can declare both. ## Injecting dependencies [Section titled “Injecting dependencies”](#injecting-dependencies) By default joints are a simple class that can be created using `Activator.CreateInstance` however the goal of joints was to allow “bootstrap time” configuration to be provided. The <xref:Joinery.Dovetail.DovetailContextBuilder> acts as a bag of properties using [`indexer`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Item_System_Object_) or [`Properties`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Properties). Any type defined in the context is injectable into any defined joint. This can be used for any number of purposes such as… * allow consumers to provide configuration to your joint * allow joints to communicate or share common state Under the covers the [`Properties`](xref:Joinery.Dovetail.DovetailContextBuilder#Joinery_Dovetail_DovetailContextBuilder_Properties) implements `IServiceProvider`, and a joint’s constructor parameters are resolved from it. *** 
```c#
public class InjectableDovetail : IServiceJoint
{
    private readonly IInjectData _joint;


    public InjectableDovetail(IInjectData joint) => _joint = joint;


    public void Register(IDovetailContext context, IServiceCollection services)
    {
        //...
    }
}


public class OptionalInjectableDovetail : IServiceJoint
{
    private readonly IInjectData? _joint;


    public OptionalInjectableDovetail(IInjectData? joint = null) => _joint = joint;


    public void Register(IDovetailContext context, IServiceCollection services)
    {
        if (_joint is { })
        {
            //...
        }
    }
}
```
 ### How constructor parameters are resolved [Section titled “How constructor parameters are resolved”](#how-constructor-parameters-are-resolved) A joint takes its constructor parameters from the properties of the <xref:Joinery.Dovetail.DovetailContextBuilder> that holds it, in the same way whether the joint is added with `AppendJoint<T>()` or exported with `[DovetailExport]`: * **By type.** Each parameter is looked up under its declared type, exactly: a value stored with `Set<IClock>(clock)` satisfies an `IClock` parameter and not a `SystemClock` one, and the other way round. `?` on a reference type changes nothing, so `IInjectData?` and `IInjectData` find the same value. A nullable value type is looked up as itself: an `int?` parameter is found under `int?`, not `int`. * **Optional parameters fall back to their default.** A parameter with a default value (`IInjectData? joint = null`, `int retries = 3`) gets that default when the properties hold nothing of its type. * **Required parameters must be there.** A parameter without a default whose type is missing makes creating the context throw an `InvalidOperationException`. For an exported joint its message names the missing type, the parameter and the joint. When the context has two or more joints it orders them with a comparer, and .NET wraps whatever a comparer throws, so the exception you catch is an `InvalidOperationException` that says “Failed to compare two elements in the array.” and the one that names the missing type is its `InnerException`. With a single joint the exception is not wrapped. * **At the point the joint is created, not before.** The joint is created the first time something needs it, which is while <xref:Joinery.Dovetail.IDovetailContext> is built, so anything you `Set` on the builder up to that point is seen, including after the joint was added. Values stored later, for example by another joint while it runs, are too late. `ExceptJoint(Type)` needs the joints too, so it creates them when it is called. With two or more joints they are created while the context orders them, before their host types are applied, so a missing required value can fail the context even for a joint that would not have applied. * **One constructor.** An exported joint is created by calling one constructor that is public or internal (`protected internal` counts, the generated code lives in the same assembly). A joint with more than one of those is the `DT0001` error. A joint that has constructors but none of those, for example a single `private` or `protected` one, is the `DT0017` error: it is reported at build time and left out of the exports. Private and protected constructors, and a static constructor, are not counted for `DT0001`. For an exported joint the generator writes this lookup into the `Exports` class as plain C#: the exported method itself takes no parameters, and each joint with constructor parameters is described by a factory that the context builder runs against its properties. Nothing is reflected on, so it is trimming and AOT safe. A joint without constructor parameters is created directly. The same factory is used if you read the `Joint` of that metadata before any builder has it, with the difference that there are no properties then: optional parameters get their defaults and a required one throws. (Joints you add with `AppendJoint<T>()` are created with `ActivatorUtilities`, which does use reflection.) 
```c#
// LaunchPad: a joint that tunes itself from options the host may or may not provide.
[DovetailExport]
public class TimeJoint(PrimitiveOptions? options = null) : IServiceJoint
{
    private readonly PrimitiveOptions _options = options ?? new PrimitiveOptions();


    public void Register(IDovetailContext context, IServiceCollection services)
    {
        //...
    }
}
```
 With this set on the `DovetailContextBuilder`, `TimeJoint` gets this instance; without it, `TimeJoint` gets null and uses its own default: 
```c#
builder.Set(new PrimitiveOptions { /* ... */ });
```

# Host Lifecycle

> Run code when the host is starting, started, stopping and stopped, without writing a hosted service, from an application builder or a service collection.

# Host Lifecycle [Section titled “Host Lifecycle”](#host-lifecycle) A host that runs `IHostedLifecycleService` (the generic host, and so ASP.NET Core) tells its hosted services when it is about to start, has started, is about to stop and has stopped. Most applications only want to run a little code at one of those moments — warm a cache once the host has started, flush a buffer before it stops — and writing a hosted service for that is a lot of ceremony. `Joinery.Dovetail.Hosting` lets you register the code directly: 
```c#
var builder = Host.CreateApplicationBuilder(args);


builder
   .OnHostStarting(provider => Console.WriteLine("Starting"))
   .OnHostStarted(async provider => await provider.GetRequiredService<CacheWarmer>().WarmUpAsync())
   .OnHostStopping(async (provider, cancellationToken) => await provider.GetRequiredService<Outbox>().FlushAsync(cancellationToken))
   .OnHostStopped(provider => Console.WriteLine("Stopped"));


using var host = await builder.ConfigureDovetail();
await host.RunAsync();
```
 An `ASP.NET Core` application does the same on its `WebApplicationBuilder`. ## The methods [Section titled “The methods”](#the-methods) There are four, one per moment, and each comes in three forms: | Method | Runs | `IHostedLifecycleService` method | | ---------------- | ---------------------------------------------- | -------------------------------- | | `OnHostStarting` | before the host starts its hosted services | `StartingAsync` | | `OnHostStarted` | after the host has started its hosted services | `StartedAsync` | | `OnHostStopping` | before the host stops its hosted services | `StoppingAsync` | | `OnHostStopped` | after the host has stopped its hosted services | `StoppedAsync` | | Form | Handler | | ------------ | ------------------------------------------------- | | synchronous | `Action<IServiceProvider>` | | asynchronous | `Func<IServiceProvider, Task>` | | cancellable | `Func<IServiceProvider, CancellationToken, Task>` | The handler gets the host’s service provider. The cancellable form also gets the cancellation token the host passes to the lifecycle method, which follows the token given to `StartAsync` or `StopAsync`. ## From an application builder or a service collection [Section titled “From an application builder or a service collection”](#from-an-application-builder-or-a-service-collection) Every method is an extension of both `IHostApplicationBuilder` (`HostApplicationBuilder`, `WebApplicationBuilder`, …), which returns the builder so the calls chain, and `IServiceCollection`, which returns the service collection. A host built the older way, with an `IHostBuilder`, has no application builder, but it has a service collection: 
```c#
using var host = Host
                .CreateDefaultBuilder(args)
                .ConfigureServices(services => services.OnHostStopped(_ => Console.WriteLine("Stopped")))
                .Build();
```
 A [joint](./defining-joints) registers its handlers the same way, while the application’s services are configured. That is how a library runs code with the host without the application doing anything: 
```c#
[DovetailExport]
public class WarmUpCache : IServiceJoint
{
    public void Register(IDovetailContext context, IServiceCollection services) =>
        services.OnHostStarted(async (provider, cancellationToken) => await provider.GetRequiredService<ICache>().WarmUpAsync(cancellationToken));
}
```
 Handlers have to be registered before the host is built. The first registration adds the hosted service that runs them, so there is nothing else to call, and a project that registers no handler gets no hosted service. ## Handlers of one moment run in parallel [Section titled “Handlers of one moment run in parallel”](#handlers-of-one-moment-run-in-parallel) All the handlers registered for a moment are started together and awaited together (with `Task.WhenAll`), not one after the other, so one slow handler doesn’t hold up the rest. The host moves on to the next step once every one of them has finished. * **Don’t depend on the order** the handlers of one moment run in. The moments themselves are ordered by the host, which calls `StartingAsync` on all its hosted lifecycle services, then `StartAsync` on all of them, then `StartedAsync` on all of them (and likewise `StoppingAsync`, `StopAsync` and `StoppedAsync` when it stops). The handlers of a moment have all finished before the host moves on to the next. * A **synchronous** handler runs to completion when it is started, so synchronous handlers of one moment, which don’t wait for anything, happen to run one after another. Handlers that `await` overlap. * A handler that **throws**, even before its first `await`, fails that step of the host like any hosted service would, and the other handlers of the moment have still been started. * The handlers that run in parallel are those of **one project** (see below): a library and the application that uses it each have a hosted service of their own, and the host runs hosted services one after the other (unless `HostOptions.ServicesStartConcurrently` and `ServicesStopConcurrently` say otherwise). The library’s handlers for a moment therefore run before or after the application’s, not alongside them. ## Where it is available [Section titled “Where it is available”](#where-it-is-available) The methods are emitted by `Joinery.Dovetail.Hosting` into the projects that reference the generic host (`Microsoft.Extensions.Hosting`), the same way it emits its other helpers, and nothing is emitted where the host doesn’t run `IHostedLifecycleService`: | Host | Methods | | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | | Generic host: workers | yes | | ASP.NET Core | yes | | Uno Platform (`Uno.Extensions.Hosting`) | yes: its host is a generic host, so handlers run once the host is started (`NavigateAsync<TShell>()` starts it, `ConfigureDovetail()` doesn’t) | | .NET MAUI | no | | Blazor WebAssembly | no | A .NET MAUI or Blazor WebAssembly project gets none even when `Microsoft.Extensions.Hosting` ends up among its references (another package brought it along, say): methods that compile but never run their handlers would be worse than methods that don’t exist, so calling one is a compile error. The methods are `internal`, as are all the helpers `Joinery.Dovetail.Hosting` emits, so a library that registers handlers needs to reference `Joinery.Dovetail.Hosting` and the generic host itself. ## Each project has its own [Section titled “Each project has its own”](#each-project-has-its-own) Every project that gets the methods gets its own, self-contained copy of them, of the registration they add and of the hosted service that runs it, all `internal` and `[Embedded]`, so no assembly sees another’s. Nothing is shared between projects: * A handler registered with a project’s methods is registered with, and run by, that project’s own hosted service. A library and an application that each register handlers end up with two hosted services, each running only its own project’s handlers, once. * The “first registration adds the hosted service” rule is per project too. It looks for that project’s own registration type in the service collection, so it neither depends on nor notices another project’s registrations. * Projects can’t coordinate on one list of handlers, and there is no single set of handlers that runs in parallel across the library and the application (see above). Handlers that must not run side by side, or in a fixed order, belong in one project, or in a hosted service of their own. * That holds for every way of registering: the application builder, the service collection and a joint all go through the methods of the project they are written in.

# Introduction

> What Dovetail is, why it exists, and when to use it.

# What is Dovetail? [Section titled “What is Dovetail?”](#what-is-dovetail) ![Dovetail overview diagram](https://dummyimage.com/1200x560/0b1220/f8fafc.png\&text=Dovetail+Overview+Architecture) The goal of Dovetail is to be a simple way to bridge the gap between Configuration driven development and Dovetail driven development. In an ASP.NET Core application it is “pay-for-play” in that you must register all your configurations, services, etc. This is great but it also forces you into cases where if you forget to call an extension method nothing lights up like you expected. Another draw back of using extension methods is that any dependencies you need, to configure services for example, must be included in the method call. One thing to keep in mind is that ASP.NET Core just got rid of the [double container](https://github.com/aspnet/Announcements/issues/353) problem, we are not introducing a second container, instead we just implement `IServiceProvider` using the same [dictionary that is provided by `IHostBuilder.Properties`](https://docs.microsoft.com/en-us/dotnet/api/microsoft.extensions.hosting.ihostbuilder.properties). Any services that you inject into your joints must exist inside of this dictionary, or be optional. At a high level Dovetail solves this problem in a very similar way to something like [Autofac Modules](https://autofaccn.readthedocs.io/en/latest/configuration/modules.html) or other similar assembly scanning solutions. Our goal is to be agnostic at a high level, strictly speaking using MSDI/MSEL/MSC is not required however is currently assumed that .NET Platform Extensions are going to be used. In the future this might be broken out. ## Why use Dovetail? [Section titled “Why use Dovetail?”](#why-use-dovetail) You have to make a choice with every library you introduce, and using Dovetail is no different. If it’s not for you, that’s okay! Here are some possible reasons why and why not to use Dovetail. ### Reasons to use? [Section titled “Reasons to use?”](#reasons-to-use) * You can create library code that “just works” without having to ensure that the correct extension method was called, with the correct parameters, for every library you add. * You can don’t have to worry about service registration extension methods in instead each module can setup it’s own registrations. * You can can group bootstrapping logic together to lessen cognitive load. ### Reasons not to use? [Section titled “Reasons not to use?”](#reasons-not-to-use) Everything has it’s positives and negatives. We cannot lie using joints will add time to starting up your application. There is a trade off to be made here and optimizations that can be made to lessen that trade-off. Fundamentally if you’re making a highly focused, and specialized microservice then using Dovetail may not be for you. You will own the burden to ensuring that configuration is done the same, extension methods are called, and everything else. It is called “pay-to-play” after all. #### Note on performance [Section titled “Note on performance”](#note-on-performance) A quick note on performance. We are now using Source Generators to generate export methods, that return all joints for a given assembly. This allows joint loading to have similar performance characteristics to pure extension methods, it’s still slower but reduces the need to assembly scan. The <xref:Joinery.Dovetail.ICompiledTypeProvider> is now generated by source generator at compile time, further reducing the need to assembly scan at runtime. # What is a Dovetail [Section titled “What is a Dovetail”](#what-is-a-dovetail) A joint is nothing but a class that implements the <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint> interface. Nothing special. By itself <xref:Joinery.Dovetail.Infrastructure.IDovetailJoint> is just a marker interface used to identify a class that may implement one more joints. Dovetails are then interfaces that are implemented by the class some examples are: * <xref:Joinery.Dovetail.Configuration.IConfigurationJoint> * <xref:Joinery.Dovetail.DependencyInjection.IServiceJoint> * <xref:Joinery.Dovetail.Logging.ILoggingJoint> * <xref:Joinery.Dovetail.Setup.ISetupJoint> * <xref:Joinery.Dovetail.Hosting.IHostingDovetail> ad-hoc Dovetails (or delegate Dovetails) are a different kind of joint but written as a delegate, but they mirror the method given by the Dovetail interface. These can be used to during program startup just like `ConfigureServices` are used today. Some examples are: * <xref:Joinery.Dovetail.Configuration.ConfigurationJoint> * <xref:Joinery.Dovetail.DependencyInjection.ServiceJoint> * <xref:Joinery.Dovetail.Logging.LoggingJoint> * <xref:Joinery.Dovetail.Setup.SetupJoint> * <xref:Joinery.Dovetail.Hosting.HostingDovetail> ## Exporting a Dovetail [Section titled “Exporting a Dovetail”](#exporting-a-dovetail) A joint can be exported by using the <xref:Joinery.Dovetail.DovetailAttribute> (eg. `[assembly: Dovetail(typeof(MyDovetail))]`). This is important you may want to make joints are **not** enabled by default but are available to be loaded by users if they want to. The rules are straight forward. * A public joint - Will not be loaded unless it is added to the <xref:Joinery.Dovetail.DovetailContextBuilder>. * A public exported joint - Will always be loaded unless excluded by assembly or type in the <xref:Joinery.Dovetail.DovetailContextBuilder>. * A private joint - Will never be loaded. ever. * A private exported joint - Will always be loaded unless excluded by assembly in the <xref:Joinery.Dovetail.DovetailContextBuilder>. # Writing your own custom joints [Section titled “Writing your own custom joints”](#writing-your-own-custom-joints) Creating your own joints is fairly easily, and can be done by using existing joints or by executing it yourself. A package or application that wants to add a new kind of joint declares it with a `<DovetailJoint>` item, and a project the SDK does not recognise declares its host with a `<DovetailHost>` item. Both are listed, with every value they accept, in the [reference](../../reference/): [DovetailJoint](../../reference/dovetail-joint/) and [DovetailHost](../../reference/dovetail-host/).

# OpenTelemetry

> OpenTelemetry integration that exposes the OpenTelemetry builder, resource, and tracer, meter and logger providers as Dovetail joints, turned on for the application's host.

# OpenTelemetry [Section titled “OpenTelemetry”](#opentelemetry) `Joinery.Dovetail.OpenTelemetry` exposes OpenTelemetry’s configuration surface — the top-level `IOpenTelemetryBuilder`, the resource builder, and the tracer, meter and logger provider builders — as ordinary Dovetail [joints](./defining-joints). Any library can contribute an activity source, a meter, a log processor, or a resource attribute without taking a direct dependency on how the host wires up OpenTelemetry. Coming from `LaunchPad.Telemetry`? [Its parity check](./opentelemetry-launchpad-parity) maps each of its conventions to a joint here. ## Turning it on [Section titled “Turning it on”](#turning-it-on) An application turns OpenTelemetry on by referencing `Joinery.Dovetail.OpenTelemetry` along with `Joinery.Dovetail.Hosting`. Joinery.Dovetail.Sdk adds `Joinery.Dovetail.OpenTelemetry` to every project that references `OpenTelemetry` or `OpenTelemetry.Extensions.Hosting`, and to every file-based app (`dotnet run app.cs`) along with `OpenTelemetry.Extensions.Hosting`; set `DovetailEnableOpenTelemetry` to `false` to leave OpenTelemetry to the application. `Joinery.Dovetail.Hosting` then emits joints into the application that add OpenTelemetry to its services, apply every OpenTelemetry joint, and start it. OpenTelemetry only listens to activity sources and meters once its providers are resolved, which `OpenTelemetry.Extensions.Hosting` does from a hosted service, so what an application needs depends on whether its host runs hosted services: | Host | Runs hosted services | Needs `OpenTelemetry.Extensions.Hosting` | Started by | | --------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | | Generic host: workers, ASP.NET Core | yes | yes | its hosted service | | Uno Platform (`Uno.Extensions.Hosting`) | once started: `NavigateAsync<TShell>()` starts the host, `ConfigureDovetail()` doesn’t | no | `DovetailOpenTelemetryUnoStartJoint`, once the host is built | | .NET MAUI (`MauiAppBuilder`) | no | no | `DovetailOpenTelemetryMauiStartJoint`, once the app is built | | Blazor WebAssembly | from .NET 11 | no | `DovetailOpenTelemetryWebAssemblyStartJoint`, once the host is built (and on .NET 11 the hosted service too, when referenced) | * With `OpenTelemetry.Extensions.Hosting`, whatever the host, `DovetailOpenTelemetryJoint` calls `services.AddOpenTelemetry()`. On .NET 11 it also traces ASP.NET Core’s `Microsoft.AspNetCore` activity source. * Without it, `DovetailOpenTelemetryServicesJoint` adds OpenTelemetry to the services directly, for the hosts that don’t need it. * A start joint resolves the meter, tracer and logger providers right after the host is built, as the hosted service does when the host starts, so OpenTelemetry runs on those hosts without a package the application wouldn’t otherwise use. * Only an application whose hosts all need `OpenTelemetry.Extensions.Hosting` (the generic host, with no Uno, MAUI or WebAssembly host) and that doesn’t reference it fails to compile, with an `#error` (CS1029) that says to add it. Packages that build on it, such as the Azure Monitor distro or .NET Aspire’s service defaults, bring it along, so they count. OpenTelemetry runs in the browser too: in single-threaded Blazor WebAssembly its batch export processor and periodic metric reader run on tasks instead of threads. Only applications and test projects get the joint, as an internal class: a library’s copy would be exported to every application that references it. A test project that imports its application’s joints gets the application’s copy as well as its own, and only the first one to run applies OpenTelemetry. Every `[DovetailExport]` joint, and anything registered with a `DovetailContextBuilder` method such as `ConfigureTracerProvider(...)`, is then applied with nothing else to call: 
```c#
var host = await Host
                .CreateApplicationBuilder(args)
                .ConfigureDovetail(dovetail => dovetail.ConfigureTracerProvider((_, tracing) => tracing.AddConsoleExporter()));
```
 ## The joints [Section titled “The joints”](#the-joints) `Joinery.Dovetail.OpenTelemetry` declares one [`<DovetailJoint>`](../../reference/dovetail-joint/), `OpenTelemetry`, for `OpenTelemetry.IOpenTelemetryBuilder`: `IOpenTelemetryJoint`, its `OpenTelemetryJointDelegate`, the `ConfigureOpenTelemetry(...)` builder method and the `ApplyOpenTelemetry` extension that the emitted joint calls. Narrower interfaces derive from `IOpenTelemetryJoint`, each for one of OpenTelemetry’s builders: | Joint interface | Builder | `DovetailContextBuilder` method | | ----------------------------- | -------------------------------------------- | ------------------------------- | | `IOpenTelemetryJoint` | `OpenTelemetry.IOpenTelemetryBuilder` | `ConfigureOpenTelemetry` | | `IResourceBuilderJoint` | `OpenTelemetry.Resources.ResourceBuilder` | `ConfigureResourceBuilder` | | `ITracerProviderJoint` | `OpenTelemetry.Trace.TracerProviderBuilder` | `ConfigureTracerProvider` | | `IMeterProviderBuilderJoint` | `OpenTelemetry.Metrics.MeterProviderBuilder` | `ConfigureMeterProvider` | | `ILoggerProviderBuilderJoint` | `OpenTelemetry.Logs.LoggerProviderBuilder` | `ConfigureLoggerProvider` | Since they’re all OpenTelemetry joints, they run together in the executor’s usual priority order. A library that only wants to register an activity source implements `ITracerProviderJoint` without knowing anything about `WithMetrics`, `WithLogging` or the resource — the same narrow, composable extension point the rest of Dovetail follows. ## Example: contributing an activity source [Section titled “Example: contributing an activity source”](#example-contributing-an-activity-source) A library adds a `System.Diagnostics.ActivitySource` to tracing by implementing `ITracerProviderJoint` and marking the class `[DovetailExport]`, the same pattern used for any other discovered Dovetail joint: 
```c#
using System.Diagnostics;
using Joinery.Dovetail;
using Joinery.Dovetail.Attributes;
using Joinery.Dovetail.OpenTelemetry.Joints;
using OpenTelemetry.Trace;


namespace MyLibrary;


[DovetailExport]
public class MyLibraryTracing : ITracerProviderJoint
{
    public static readonly ActivitySource ActivitySource = new("MyLibrary");


    public void Register(IDovetailContext context, TracerProviderBuilder builder) =>
        builder.AddSource(ActivitySource.Name);
}
```
 ## What this package does *not* do [Section titled “What this package does not do”](#what-this-package-does-not-do) `Joinery.Dovetail.OpenTelemetry` only opens the extension points — it does not ship any exporters or instrumentation. In particular, it does **not** include: * The console exporter, the OTLP exporter, or any other exporter package. * ASP.NET Core, HttpClient, or other instrumentation packages. * Any default sampler, resource attribute, or processor configuration of its own. The OpenTelemetry SDK’s default resource still applies, and already has the telemetry SDK attributes and the environment variable detector. Consumers add exporters and instrumentation the same way they add anything else to a provider: by writing their own `ITracerProviderJoint`/`IMeterProviderBuilderJoint`/`ILoggerProviderBuilderJoint` implementation (or a plain `Configure{Kind}(...)` delegate) that calls the relevant `AddConsoleExporter()`, `AddOtlpExporter()`, `AddAspNetCoreInstrumentation()`, etc. This keeps `Joinery.Dovetail.OpenTelemetry` itself free of exporter dependencies, which also keeps it friendly to trimming/AOT — see [Non-Goals in the OpenTelemetry design doc](https://github.com/RocketSurgeonsGuild/Dovetail/blob/main/openspec/changes/add-dovetail-opentelemetry/design.md#goals--non-goals) for the full rationale.

# OpenTelemetry parity with LaunchPad.Telemetry

> Which Dovetail OpenTelemetry joint replaces each LaunchPad.Telemetry convention, how logs reach the logging provider, what the SDK's default resource already contains, and the evidence for each.

# OpenTelemetry parity with LaunchPad.Telemetry [Section titled “OpenTelemetry parity with LaunchPad.Telemetry”](#opentelemetry-parity-with-launchpadtelemetry) `Rocket.Surgery.LaunchPad.Telemetry` offered six convention abstractions, a default convention that turned OpenTelemetry on, and a default convention for the resource. `Joinery.Dovetail.OpenTelemetry` (with the joints `Joinery.Dovetail.Hosting` emits) covers all of that, so an application can drop the LaunchPad package. This page is the written check, made against OpenTelemetry SDK 1.20.1, and names the test that shows each row. See [OpenTelemetry](./opentelemetry) for how the joints work. The one LaunchPad.Telemetry convention that has no equivalent here is the instrumentation convention (HTTP client tracing, and HTTP client, runtime and process metrics). Dovetail’s package ships no instrumentation on purpose, so LaunchPad keeps it as a joint of its own in `LaunchPad.Hosting` # Serilog

> Serilog integration that builds a Serilog logger from Serilog joints and the application's configuration, and registers it in place of the host's default logging providers. Trimming and Native AOT safe.

# Serilog [Section titled “Serilog”](#serilog) `Joinery.Dovetail.Serilog` makes Serilog the logging of an application, and exposes Serilog’s `LoggerConfiguration` as an ordinary Dovetail [joint](./defining-joints). Any library can contribute a sink, an enricher or a destructuring policy without taking a dependency on how the application builds its logger. ## Turning it on [Section titled “Turning it on”](#turning-it-on) Reference `Joinery.Dovetail.Serilog`. Its `SerilogJoint` is exported to the application like any other joint, so there is nothing to call: every host that calls `ConfigureDovetail` and references it gets a Serilog logger. With `Joinery.Dovetail.Sdk`, set `DovetailEnableSerilog` to `true` and every project that references `Serilog` gets the package. A file-based app (`dotnet run app.cs`) gets it without either, unless it sets `DovetailEnableSerilog` to `false`. ## What it does [Section titled “What it does”](#what-it-does) Once every Serilog joint has run, `SerilogJoint`: 1. applies the minimum level and the level overrides in the `Serilog:MinimumLevel` section of the application’s configuration to the logger configuration ([below](#configuration)); 2. removes the logging providers the host builders add by default (console, debug, event source and, on Windows, event log: the `ConsoleLoggerProvider`, `DebugLoggerProvider`, `EventSourceLoggerProvider` and `EventLogLoggerProvider` of `Microsoft.Extensions.Logging`) and the default `ILoggerFactory`; 3. registers the logger, as `Serilog.Core.Logger` and as Serilog’s `ILogger`, and `ILoggerFactory` (a `SerilogLoggerFactory`, which is what backs every `ILogger<T>`), as singletons. The logger also writes to the other logging providers of the container ([below](#the-other-logging-providers)). So `Serilog.ILogger`, `Microsoft.Extensions.Logging.ILogger<T>` and `ILoggerFactory.CreateLogger(...)` all write to the one logger, once. The container owns it: disposing the host disposes the logger, which flushes and disposes its sinks. A few consequences of replacing `ILoggerFactory`: * The `Logging:LogLevel` filters and `builder.Logging.SetMinimumLevel(...)` belong to the factory that was replaced. Use Serilog’s levels, `Serilog:MinimumLevel` and its `Override` entries, instead. * Serilog’s levels decide what every logging provider receives, the other providers included. A provider that used to be given `Debug` events by its own filter gets them only if the `Serilog:MinimumLevel` lets them through. * Dovetail does not set the static `Log.Logger`. Resolve the logger from the container. ### The other logging providers [Section titled “The other logging providers”](#the-other-logging-providers) Replacing `ILoggerFactory` would leave every other `ILoggerProvider` of the container without events: the default factory is what writes to them. OpenTelemetry’s is one, since its logging joints (`ConfigureLoggerProvider`) add the `OpenTelemetryLoggerProvider` that exports log records, and so is any provider an application or a package registers. So the logger forwards each event it writes to them, the way Serilog.Extensions.Hosting does with `writeToProviders`: a `WriteTo.Providers(...)` sink over a `LoggerProviderCollection`, which the logger factory fills with the container’s `ILoggerProvider`s when it is created. A provider registered at any point before the container is built is included, by a Serilog joint or after it, with the logging builder (`builder.Logging.AddProvider(...)`) or with the services. The events keep their level, category (the `SourceContext`) and exception, and the Serilog properties are the state they are logged with. Each event is written once to every sink and once to every provider. Two kinds of provider are not written to: * Serilog’s own `SerilogLoggerProvider`, which would write the event to Serilog again (and, if it wraps this very logger, without end). * The default providers that Serilog replaces: exactly the four types named above, matched by their full names. They are removed from the services; one that is registered after the Serilog joint ran stays out of the forwarding too, so that the events are not written to the console twice. Providers that merely share a namespace with them are not defaults and are written to, such as Application Insights’ `ApplicationInsightsLoggerProvider` (`Microsoft.Extensions.Logging.ApplicationInsights`) and the Azure App Service providers (`Microsoft.Extensions.Logging.AzureAppServices`). The logger factory is created when the container is asked for it, which a host does while it is being built. Until then the other providers are not known: an event written through `Serilog.ILogger` before that reaches the sinks only. The logger disposes the providers it writes to when it is disposed, as the container does, so they are disposed twice, which `Dispose` allows. ## The Serilog joint [Section titled “The Serilog joint”](#the-serilog-joint) `Joinery.Dovetail.Serilog` declares one [`<DovetailJoint>`](../../reference/dovetail-joint/), `Serilog`, for `Serilog.LoggerConfiguration`: `ISerilogJoint`, `ISerilogAsyncJoint`, the `SerilogJointDelegate` and the `ConfigureSerilog(...)` builder method. A joint is handed the context, the service collection and the logger configuration. Sinks and enrichers are configured here, in code: 
```c#
using Joinery.Dovetail;
using Joinery.Dovetail.Attributes;
using Joinery.Dovetail.Joints;
using Microsoft.Extensions.DependencyInjection;
using Serilog;


namespace MyLibrary;


[DovetailExport]
public class MyLibraryLogging : ISerilogJoint
{
    public void Register(IDovetailContext context, IServiceCollection services, LoggerConfiguration loggerConfiguration) =>
        loggerConfiguration.Enrich.WithProperty("Library", "MyLibrary");
}
```
 or, for one application, without a class: 
```c#
var host = await Host
                .CreateApplicationBuilder(args)
                .ConfigureDovetail(dovetail => dovetail.ConfigureSerilog((_, _, logger) => logger.WriteTo.Console()));
```
 ## Configuring the logger [Section titled “Configuring the logger”](#configuring-the-logger) The logger configuration is built in this order, and what comes later wins where only one value can exist (the minimum level): 1. the Serilog joints, in the executor’s usual priority order; 2. the `Serilog:MinimumLevel` section of the configuration; 3. the `IConfigureOptions<LoggerConfiguration>` registered in the services (`services.Configure<LoggerConfiguration>(...)`); 4. the `IPostConfigureOptions<LoggerConfiguration>` registered in the services (`services.PostConfigure<LoggerConfiguration>(...)`). The options are applied the way the options pattern applies them, to the unnamed options, when the logger is first resolved (which a host does while it is being built). That is what lets them use other services: 
```c#
services
   .AddOptions<LoggerConfiguration>()
   .Configure<IHostEnvironment>((logger, environment) => logger.Enrich.WithProperty("Environment", environment.EnvironmentName));
```
 ### Configuration [Section titled “Configuration”](#configuration) The application’s configuration sets the minimum level of the logger and of each source, in the `Serilog:MinimumLevel` section, in the same format as Serilog.Settings.Configuration: 
```json
{
    "Serilog": {
        "MinimumLevel": {
            "Default": "Information",
            "Override": { "Microsoft": "Warning", "Microsoft.Hosting.Lifetime": "Information" }
        }
    }
}
```
 `"MinimumLevel": "Debug"` is the short form of `"Default": "Debug"`. A level is the name of one of Serilog’s levels (`Verbose`, `Debug`, `Information`, `Warning`, `Error`, `Fatal`; casing is ignored), and anything else fails while Dovetail builds the host, with an exception that names the key. Levels follow the configuration when it reloads (a file provider with `reloadOnChange`, say). Only the levels that were in the configuration when the application started do: an override that is added later is not picked up, and a level that is removed or not a level any more leaves the level in effect as it is. That is all that is read from the `Serilog` section. In particular, **sinks, enrichers, filters and `Using` are not read from configuration**: Serilog.Settings.Configuration finds the methods they name by reflection, which is neither trimming nor Native AOT safe, so `Joinery.Dovetail.Serilog` does not depend on it. A `"WriteTo"` or `"Enrich"` in the section is ignored, and the schema flags it (below). Configure them in a [Serilog joint](#the-serilog-joint) instead, in code. `Joinery.Dovetail.Serilog` ships a JSON Schema for the section, which is merged into the application’s [`appsettings.schema.json`](./configuration-with-optionary) by Optionary, when the application references it, for editor completion and validation. It describes exactly what is read: `MinimumLevel`, as a level name or as an object with `Default` and `Override`. Any other key of the `Serilog` section is flagged, so a `WriteTo` copied from Serilog’s documentation does not look as if it were working. ## Trimming and Native AOT [Section titled “Trimming and Native AOT”](#trimming-and-native-aot) `Joinery.Dovetail.Serilog` is trimming and Native AOT compatible: the project sets `IsAotCompatible`, builds with the trim and AOT analyzers on without a warning, and has no reflection to annotate or suppress. Reading the configuration uses only `IConfiguration` and enum parsing (`Enum.TryParse<LogEventLevel>`), and the rest is registration of the logger, which is Serilog’s, and of `Microsoft.Extensions.Logging`’s own open generic `ILogger<T>`. Forwarding to the other logging providers is not reflection either: it is Serilog.Extensions.Logging’s `WriteTo.Providers` sink and `SerilogLoggerFactory`, and a type check on the providers. The claim was checked by publishing a generic-host application that references `Joinery.Dovetail.Serilog`, reads `Serilog:MinimumLevel:Default` and `Override` from configuration, configures a sink in a `ConfigureSerilog(...)` joint and registers an `ILoggerProvider` in its services, with `PublishTrimmed` (`TrimMode=full`) and with `PublishAot` (.NET 10, osx-arm64, self-contained). Neither publish reported a trim or AOT warning, and both applications ran: the factory was a `SerilogLoggerFactory`, `ILogger<T>` wrote through the sink and to the provider, the default level and the override applied to both, and no default logging provider was left. What a published application depends on is therefore Serilog and the sinks and enrichers it configures in its joints, which are referenced from code and so are kept by the trimmer and compiled by the AOT compiler like any other code. Check the ones you use: Serilog and its sinks are not Dovetail’s.

# Source Generation

> How the Roslyn source generator resolves and exports joints at build time.

# Source Generation and Dovetails \[New] [Section titled “Source Generation and Dovetails \[New\]”](#source-generation-and-dovetails-new) We have built a Source Generator to use with Dovetail that allows us to export joints and import joints with easy, in a way that is statically compiled. # Exporting Dovetails [Section titled “Exporting Dovetails”](#exporting-dovetails) Any joint marked with `[assembly: Dovetail(typeof(MyDovetail))]` will automatically be added to a public partial static class named `Exports` that will exist in the root namespace of the assembly being built. Each exported joint carries the host type it declares with `[LiveJoint]`, `[UnitTestJoint]` or `[DovetailHostType]`, the same as when a joint is added through reflection at runtime. See [which attributes are honoured where](./defining-joints#which-attributes-are-honoured-where). A joint with constructor parameters is exported as a factory, because the exported method has no context to read from: the context builder that holds the metadata creates the joint from its properties, and an optional parameter falls back to its default. See [how constructor parameters are resolved](./defining-joints#how-constructor-parameters-are-resolved). # Importing Dovetails [Section titled “Importing Dovetails”](#importing-dovetails) The generator creates an internal static partial `Imports` class in the assembly’s root namespace. `Imports.Joints` is a `DovetailContextBuilderFactory` that creates a context builder loaded with the assembly’s own joints and those of every referenced assembly that exports joints. The `DovetailImportNamespace`, `DovetailImportClassName` and `DovetailImportMethodName` MSBuild properties change those names. You can also import the `GetDovetails` method onto a given class by using the `[ImportDovetails]` attribute on the class. ## Which projects import and export [Section titled “Which projects import and export”](#which-projects-import-and-export) Two MSBuild properties decide what the generator emits for a project: | Property | When `true` | | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | | `ImportDovetailAssembly` | The `Imports` class is generated. | | `ExportDovetailAssembly` | Referencing assemblies import this assembly’s joints. When `false`, the joints still reach this assembly’s own `Imports` class. | Joinery.Dovetail.Sdk sets both as part of its host detection. Projects that don’t use the SDK get these defaults: * test projects (`IsTestProject`) import but don’t export; * applications (`OutputType` of `Exe` or `WinExe`) import and export; * libraries export but don’t import. Set either property in a project file to override its default. The generator runs in every project that references a Dovetail package, including projects that only reference one indirectly, for example through `Joinery.Dovetail.Hosting`. Its diagnostics (`DT0001` to `DT0005`, such as the error for a joint with more than one constructor, and `DT0017`, the error for a joint with no constructor it can be created with) apply there too. The code it generates needs C# 12 or later: in a project whose `LangVersion` is older, it generates nothing and reports warning `DT0006` instead. ## Specular’s provider [Section titled “Specular’s provider”](#speculars-provider) An application that references [Specular](https://www.nuget.org/packages/Specular) doesn’t set its provider by hand. Specular generates an internal `SpecularProvider` into each project that emits one, and the generated `Imports` seeds that provider into the context builder it creates, so a joint reads it with `context.Get<ISpecularProvider>()`. Scanning through it covers the assemblies the application references, including the joints of libraries that don’t generate a provider of their own (`SpecularEmitProvider` set to `false`) and so keep receiving the application’s through the context. 
```csharp
public sealed class PluginJoint : ISetupJoint
{
    public void Register(IDovetailContext context)
    {
        var provider = context.Get<ISpecularProvider>()!;
        var plugins = provider.GetTypes(z => z.FromAssemblyOf<IPlugin>().GetTypes(f => f.AssignableTo<IPlugin>()));
    }
}
```
 Dovetail has no dependency on Specular, so the seeding is generated code that exists only where Specular does: * The generator adds it when the project’s compilation references the assembly that defines `Specular.ISpecularProvider` and the `SpecularEmitProvider` MSBuild property isn’t `false`, the two things Specular’s own generator looks at before it generates a `SpecularProvider`. It can’t look for `SpecularProvider` itself: a generator doesn’t see what another one adds. * In every other project nothing is generated and no diagnostic is raised. * A provider you set yourself wins. The generated code only adds the provider when the context doesn’t hold one, so `builder.ConfigureDovetail(b => b.Set<ISpecularProvider>(provider))`, or a provider passed in with the properties, is never overwritten. * Set `SpecularEmitProvider` to `false` for a project that references Specular without generating a provider (say it excludes Specular’s analyzers) and Dovetail stops naming one. Otherwise the build fails with CS0103 for `SpecularProvider`. ### Native AOT and trimming [Section titled “Native AOT and trimming”](#native-aot-and-trimming) The seeding adds no reflection: it is a generic call to `AddIfMissing<ISpecularProvider>` with the value of a static property, both of which the trimmer and the AOT compiler can follow. Specular generates `SpecularProvider` without reflection as well. The Joinery.Dovetail.Sdk.Tests publish an application that uses it trimmed and with Native AOT, without trim or AOT warnings, and the published application starts with the provider in its context and scans across assemblies.

# ZeroAlloc

> ZeroAlloc.Mediator and ZeroAlloc.Validation register themselves through joints Dovetail writes into every project that runs their source generators, and [Validate] configuration types are validated with ZeroAlloc.Validation.Options. Trimming and Native AOT safe.

# ZeroAlloc [Section titled “ZeroAlloc”](#zeroalloc) [ZeroAlloc.Mediator](https://mediator.zeroalloc.net/) and [ZeroAlloc.Validation](https://validation.zeroalloc.net/) generate their dependency injection registration into the project that uses them: `AddMediator()`, `AddZeroAllocValidators()` and `AddZeroAllocAspNetCoreValidation()` are written into each assembly by the libraries’ source generators, for that assembly’s handlers and validators. A package can’t call a method that only exists in the project, so Joinery.Dovetail writes a service [joint](./defining-joints) into the project instead, and that joint calls it. ## Turning it on [Section titled “Turning it on”](#turning-it-on) Reference the ZeroAlloc packages as their documentation says. There is nothing to call and no Dovetail package to add: `Joinery.Dovetail` sees which ZeroAlloc generators the project runs and writes the matching joints when it builds. | The project runs | Joint | It calls | | -------------------------------------------------------------------------------------- | -------------------------------------------- | --------------------------------------------- | | `ZeroAlloc.Mediator.Generator` | `DovetailZeroAllocMediatorJoint` | `services.AddMediator()` and the bridges | | `ZeroAlloc.Validation.Inject` | `DovetailZeroAllocValidatorsJoint` | `services.AddZeroAllocValidators()` | | `ZeroAlloc.Validation.AspNetCore`’s generator, with a direct reference to that package | `DovetailZeroAllocAspNetCoreValidationJoint` | `services.AddZeroAllocAspNetCoreValidation()` | The generator is what turns a joint on, not the runtime package: `ZeroAlloc.Mediator` on its own has no `AddMediator()`. Every project that runs a generator gets its joint, libraries included. ZeroAlloc registers handlers and validators one assembly at a time, so a library’s joint registers the library’s own, and it is exported to the applications that reference the library like any other joint. The application only calls `ConfigureDovetail()`. ### Mediator bridges [Section titled “Mediator bridges”](#mediator-bridges) The mediator joint turns on each ZeroAlloc.Mediator bridge package the project references, by calling its `With...()` method on the builder `AddMediator()` returns: | Package | Call | | ------------------------------- | ------------------ | | `ZeroAlloc.Mediator.Validation` | `WithValidation()` | | `ZeroAlloc.Mediator.Cache` | `WithCache()` | | `ZeroAlloc.Mediator.Resilience` | `WithResilience()` | | `ZeroAlloc.Mediator.Telemetry` | `WithTelemetry()` | `ZeroAlloc.Mediator.Authorization` is left out: `WithAuthorization(...)` takes the application’s policies, so call it from a joint of your own. With `ZeroAlloc.Mediator.Validation` and `ZeroAlloc.Validation.Inject` in the project that has the handlers, a request is validated before its handler runs, with nothing registered by hand. ### Validating configuration [Section titled “Validating configuration”](#validating-configuration) An [`[Optionary]`](./configuration-with-optionary) class marked `[Validate]` is validated by its generated validator whenever its options are read, through [ZeroAlloc.Validation.Options](https://validation.zeroalloc.net/docs/options): the registration Optionary generates, which Dovetail’s joint calls, calls that package’s `ValidateWithZeroAlloc()` on the type’s options builder, before `ValidateOnStart()` when the attribute asks for it. 
```c#
[Optionary(ValidateOnStart = true), Validate]
public class DatabaseOptions
{
    [NotEmpty]
    public string ConnectionString { get; set; } = "";
}
```
 `Joinery.Dovetail.Sdk` adds `ZeroAlloc.Validation.Options` to every project that references `ZeroAlloc.Validation`, at the same version (ZeroAlloc ships them together), so there is nothing to add. Without the SDK, reference the package yourself. * Only types of the project itself are validated this way: `ValidateWithZeroAlloc()` is generated for the `[Validate]` classes of each project, so a type from another assembly named by `[assembly: Optionary<T>]` isn’t. * A type with an asynchronous rule, its own or a nested model’s, isn’t validated, and Optionary reports `OPT0012`: options validation is synchronous. ### ASP.NET Core [Section titled “ASP.NET Core”](#aspnet-core) `AddZeroAllocAspNetCoreValidation()` registers the validators too and adds an MVC action filter. Each call adds the filter again, and the package’s generator also runs in the projects that only get it through another project, so only a project that references `ZeroAlloc.Validation.AspNetCore` itself gets that joint. ## Turning it off [Section titled “Turning it off”](#turning-it-off) Set `DovetailEnableZeroAllocMediator` or `DovetailEnableZeroAllocValidation` to `false` to leave that registration to the project. Neither turns the ZeroAlloc generators off. `DovetailEnableZeroAllocValidation=false` also stops the SDK adding `ZeroAlloc.Validation.Options` and the configuration options calling `ValidateWithZeroAlloc()`.

```text
    public void Register(IDovetailContext context, IServiceCollection services) => services.AddSingleton<Greeter>();


    public void Register(IDovetailContext context, ConsoleApp.ConsoleAppBuilder app) => app.Add<GreetCommands>();
}
```

The others work the same way. `Microsoft.NET.Sdk.WindowsDesktop` has been unnecessary since .NET 5 (the SDK warns `NETSDK1137`): `Microsoft.NET.Sdk` with `UseWPF` or `UseWindowsForms` is enough, and so is `Joinery.Dovetail.Sdk`. Its mirror is for projects that have not moved off it yet. ## Aspire AppHosts [Section titled “Aspire AppHosts”](#aspire-apphosts) There is no Aspire SDK to mirror any more. Builds resolve the Aspire CLI (`ASPIRE009` when they can’t), so install it alongside, at the same version as the packages. # ModularPipelines

> Apply Dovetail joints to a ModularPipelines PipelineBuilder, so joints add the modules, options and services of a build pipeline.

# ModularPipelines [Section titled “ModularPipelines”](#modularpipelines) `Joinery.Dovetail.ModularPipelines` makes a [ModularPipelines](https://github.com/thomhurst/ModularPipelines) pipeline a Dovetail host. Joints add the pipeline’s modules, options and services, and the pipeline project only builds and runs it. The package targets `net11.0` only, as ModularPipelines 4 does. ## Getting the package [Section titled “Getting the package”](#getting-the-package) A build script names one SDK, `Joinery.Dovetail.Sdk.ModularPipelines`, and nothing else: 
```csharp
#:sdk Joinery.Dovetail.Sdk.ModularPipelines


using Build;


await using var pipeline = await Pipeline.CreateBuilder(args).ConfigureDovetail();
await pipeline.RunAsync();
```
 It chains `Joinery.Dovetail.Sdk` and adds `ModularPipelines` itself, at the version the SDK was built with (`DovetailModularPipelinesVersion` picks another; a project that references `ModularPipelines` keeps its own reference). A project file uses it the same way, `<Project Sdk="Joinery.Dovetail.Sdk.ModularPipelines">`, and needs no `OutputType`: the SDK makes it an `Exe`. Pin its version in `global.json` under `msbuild-sdks`, as for the other Dovetail SDKs. With `Joinery.Dovetail.Sdk` alone, a project that references `ModularPipelines` on `net11.0` or later gets the same: the SDK adds `Joinery.Dovetail.ModularPipelines` and `ModularPipelines.OpenTelemetry`, and declares the ModularPipelines host for an application (`DovetailEnableModularPipelines=false` opts out of all of it). Without either SDK, reference `Joinery.Dovetail.ModularPipelines` yourself, next to `ModularPipelines`: its build targets declare the host. `Joinery.Dovetail.ModularPipelines` holds the `PipelineBuilder` joint kind (`IPipelineBuilderJoint`, `IPipelineBuilderAsyncJoint`), which a library of joints references. The code the host’s entry points call, `DovetailPipelineHelpers`, is not in it: `Joinery.Dovetail.Hosting`, which the package depends on, emits it into the application, as it does the helpers of every other host, once the application references `ModularPipelines` and `Joinery.Dovetail.ModularPipelines`. It is internal to the application. ## OpenTelemetry [Section titled “OpenTelemetry”](#opentelemetry) `ModularPipelines.OpenTelemetry` traces and measures a pipeline’s modules and commands. The SDK adds it next to `ModularPipelines`, at the same version (the package pins `ModularPipelines` to its own), and `Joinery.Dovetail.Hosting` emits a `PipelineBuilder` joint into the application that calls its `AddOpenTelemetry()`. Exporting is up to the application, as for the rest of its OpenTelemetry: an `IOpenTelemetryJoint`, or a `PipelineBuilder` joint that calls `AddOpenTelemetry(z => z.AddOtlpExporter())` itself. `DovetailEnableOpenTelemetry=false` leaves the package and the joint out. ## Building the pipeline [Section titled “Building the pipeline”](#building-the-pipeline) The host is declared for `PipelineBuilder`, so an application (a project that imports joints, as the SDK makes every `Exe`) gets `ConfigureDovetail` extension methods on it, generated into the project’s root namespace like those of every other host: sample/ModularPipelinesSample/Program.cs 
```csharp
using ModularPipelines;
using ModularPipelinesSample;


// ConfigureDovetail (generated into the project's root namespace) applies the joints, BuildJoint among them, then builds the pipeline.
await using var pipeline = await Pipeline.CreateBuilder(args).ConfigureDovetail();
await pipeline.RunAsync();
```
 `ConfigureDovetail` returns the built `IPipeline`, ready to run. Before building it, it applies, in this order: 1. the configuration joints, whose sources go in front of the pipeline’s environment variables and command line, so those still win. The pipeline’s configuration is registered as the `IConfiguration` first, so the one a service joint may add with `TryAdd` (as OpenTelemetry’s `AddOpenTelemetry()` does, which reads only the environment variables) does not take its place; 2. the service joints, and with them the logging joints, to `builder.Services`; 3. the `PipelineBuilder` joints, to the builder itself. After building it, it hands the pipeline to the `HostCreated` joints (`IHostCreatedJoint<IPipeline>`). The overloads that take an action configure the `DovetailContextBuilder` first, as for the other hosts: 
```csharp
await using var pipeline = await Pipeline
                                .CreateBuilder(args)
                                .ConfigureDovetail(z => z.ConfigurePipelineBuilder((_, builder) => builder.AddModule<ReleaseModule>()));
```
 Configure what has to come before the joints on the builder before calling `ConfigureDovetail`: once it returns, the builder is consumed. That includes where configuration files are read from: the configuration joints resolve their files (`appsettings.json` and the rest) against the file provider of the pipeline’s configuration, so a pipeline whose build scripts live in their own folder points it there first: 
```csharp
var builder = Pipeline.CreateBuilder(args);
builder.Configuration.SetBasePath(Path.Combine(Environment.CurrentDirectory, "build"));
await using var pipeline = await builder.ConfigureDovetail();
```
 ## Writing a PipelineBuilder joint [Section titled “Writing a PipelineBuilder joint”](#writing-a-pipelinebuilder-joint) The `PipelineBuilder` joint is handed the builder, so it can do anything the pipeline project would: add modules, register services, set options, add plugins. A joint that adds the module of a sample pipeline and the service the module uses: sample/ModularPipelinesSample/BuildJoint.cs 
```csharp
[DovetailExport]
public sealed class BuildJoint : IPipelineBuilderJoint
{
    public void Register(IDovetailContext context, PipelineBuilder builder)
    {
        builder.Services.AddSingleton(TimeProvider.System);
        builder.AddModule<GreetingModule>();
    }
}
```
 `IPipelineBuilderAsyncJoint` is the asynchronous kind. A joint that only registers services can be an `IServiceJoint` instead, which every host applies. Joints run in the order of their dependencies and priorities, so a library of modules can export its joints and order them against the application’s. Add modules with `AddModule<TModule>()`: it registers the module by its type, which is what keeps the pipeline trimmable and Native AOT compatible. Dovetail finds the joints at build time, so nothing is scanned at run time either.

# Shipping Templates

> Ship C# source from your package as templates that Dovetail writes into only the projects that should get it, by host model, referenced assemblies and direct reference.

# Shipping templates [Section titled “Shipping templates”](#shipping-templates) A package can ship C# source that is written into a consuming project at build time, only when that project matches. This is how `Joinery.Dovetail.Hosting` works: its ASP.NET Core, MAUI, Uno and Blazor WebAssembly helpers and its OpenTelemetry joints are all templates, so the package depends on none of those frameworks. Referencing a framework is what turns its template on. The mechanism is a supported extension point. Any package can declare templates with `<DovetailTemplate>` items and get the same gating that `Joinery.Dovetail.Hosting` uses, including a mode that emits only into projects that reference your package themselves. ## Declare a template [Section titled “Declare a template”](#declare-a-template) Put the source in a `*.cs.template` file next to your package’s targets, and declare it from the targets (`build/` or `buildTransitive/`): 
```xml
<Project>
  <ItemGroup>
    <DovetailTemplate
      Include="HealthCheckJoint"
      File="$(MSBuildThisFileDirectory)HealthCheckJoint.cs.template"
      Package="Contoso.Hosting"
      DirectReferenceOnly="true"
      References="Microsoft.Extensions.Diagnostics.HealthChecks"
      Hosts="HostApplication;WebApplication" />
  </ItemGroup>
</Project>
```
 Pack both files, under `build/` (imported by NuGet into projects that reference the package directly) or `buildTransitive/` (imported into every project that gets it, which is what a package reached through other packages needs): `<None Include="build/*.*" Pack="true" PackagePath="buildTransitive" />`. | Metadata | Meaning | | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `Include` | The template’s name. It must be unique across packages, and names the generated file, `DovetailTemplate.<name>.g.cs` in `obj/`. | | `File` | Required. The full path of the template. | | `Package` | The id of the package that ships the template. It is only emitted into a project that references it: the package’s assembly (named after the package) is among the resolved references. | | `DirectReferenceOnly` | `true` limits the template to projects with a direct reference to `Package`. Requires `Package`. | | `References` | Semicolon-separated assembly names (file names without extension). Every one must be among the project’s resolved references. | | `Hosts` | Semicolon-separated host names. At least one must be declared by the project: the host model that `Joinery.Dovetail.Sdk` detects (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui` or `Uno`). | | `HostName`, `HostType` | When `HostType` is set, they replace their tokens like any other metadata, so one template can be declared once per host model under different names. `HostName` alone replaces nothing. | | `OutputPrefix` | The generated file is `<prefix>.<name>.g.cs`; the default prefix is `DovetailTemplate`. | Every gate you set has to pass. A project that doesn’t run the Dovetail source generator gets no templates. The [`DovetailTemplate` reference](../../reference/dovetail-template/) lists the defaults, the errors and the generated file names. ## Direct references only [Section titled “Direct references only”](#direct-references-only) By default a template reaches every project that has your package’s assembly among its references, which includes projects that only get the package because a library they use references it. `DirectReferenceOnly="true"` narrows that to projects that declare the reference themselves: * a `PackageReference` to `Package`, including the ones `Joinery.Dovetail.Sdk` adds for you, or * a `ProjectReference` to a project named after `Package`, which is how a solution consumes what it ships. A project that only receives the package transitively still imports your `buildTransitive/` targets, so your items are declared there, but it gets no generated file. Use it for wiring that an application should opt into by referencing your package, and that a library reaching the application through a project reference should not impose on it. A package that ships from `build/` already gets this from NuGet for package references. The mode is for what NuGet can’t express: a package shipped from `buildTransitive/`, and a solution that consumes your project by `ProjectReference`. A project reference imports no package assets at all, so the solution imports your targets itself, into every project (this repository does that with `Joinery.Dovetail.Hosting.targets` for its test projects). `Package` is then what limits the templates to projects that reference yours, and `DirectReferenceOnly` to the ones that reference it themselves. ## Write the template [Section titled “Write the template”](#write-the-template) * The generated code is part of the consuming project, compiled against whatever it references. Reference-gate everything it needs (`References`), and your package then depends on none of it. * Make the types `internal` and `[Embedded]`, so an assembly never sees the copy a referenced assembly emitted for itself. A template may also declare joints (`[DovetailExport]`), which the Dovetail source generator picks up like any other. * Backslashes in a template are written as they are. ## Fill in values from metadata [Section titled “Fill in values from metadata”](#fill-in-values-from-metadata) Every metadata value of a `DovetailTemplate`, your own metadata included, replaces `{Name}` and `__Name__` in the template, where `Name` is the metadata’s name. Declare one template under several names with different values and you get one file per name: a joint per client, say, from a template your package ships once. 
```xml
<ItemGroup Condition="'$(DovetailTemplateMetadataTokens)' == 'true'">
  <DovetailTemplate Include="Contoso.RocketsClient" File="$(MSBuildThisFileDirectory)ClientJoint.cs.template" ClientName="RocketsClient" Namespace="MyApp.Rockets" />
  <DovetailTemplate Include="Contoso.LaunchClient" File="$(MSBuildThisFileDirectory)ClientJoint.cs.template" ClientName="LaunchClient" Namespace="MyApp.Launch" />
</ItemGroup>
```
 
```csharp
namespace __Namespace__;


internal static partial class __ClientName__Joint
{
    // Registers {ClientName}.
}
```
 * `__Name__` is an identifier, so the template stays valid C# that an editor and an analyzer can read. Use `{Name}` where an identifier isn’t needed. * A token no metadata fills, or whose metadata is empty, is left as it is. * `Include` names the generated file and is what the gates are keyed on, so it has to be unique across packages; `OutputPrefix` does not change that. Prefix the names you make up with your package’s (`Contoso.RocketsClient`) and pass the bare name as metadata. * `DovetailTemplateMetadataTokens` is `true` wherever Dovetail expands these tokens. An older Dovetail replaces only `{HostName}` and `{HostType}`, so declare token-bearing templates under that condition and a project on an older Dovetail gets nothing rather than a file that doesn’t compile. The [`DovetailTemplate` reference](../../reference/dovetail-template/#tokens) has the full rule. ## When the metadata isn’t enough [Section titled “When the metadata isn’t enough”](#when-the-metadata-isnt-enough) The templates that pass their gates are the `DovetailEmittedTemplate` items, with the metadata above carried over. A target can add to them, or remove from them, after `DovetailResolveTemplates` and before `DovetailGenerateTemplates`: 
```xml
<Target Name="ChooseMyJoint" AfterTargets="DovetailResolveTemplates" BeforeTargets="DovetailGenerateTemplates">
  <ItemGroup>
    <DovetailEmittedTemplate
      Include="MyJoint"
      File="$(MSBuildThisFileDirectory)MyJoint.cs.template"
      Condition="@(DovetailEmittedTemplate->AnyHaveMetadataValue('Identity', 'MyHelpers')) == 'true'" />
  </ItemGroup>
</Target>
```
 `Joinery.Dovetail.Hosting` does this to choose which of its OpenTelemetry joints a host gets, depending on which helpers were emitted, and to leave the host lifecycle helper out of hosts that don’t run it. Removing is `<DovetailEmittedTemplate Remove="MyJoint" />`: only these items are written, so a copy of the list that a package keeps for itself is not enough. ## Test it [Section titled “Test it”](#test-it) The Dovetail SDK tests show how to prove a template’s gates: pack a package that ships the template, reference it from a project that declares the reference and from one that only receives it transitively, build, and read which `DovetailTemplate.*.g.cs` files landed in each project’s `obj/` (`test/Joinery.Dovetail.Sdk.Tests/TemplateExtensionPointTests.cs`). The same tests read what a template’s tokens were replaced with.

These pages list every metadata value an item reads, with its default, so you do not have to read the `.targets` files. # DovetailHost

> The DovetailHost MSBuild item declares the ConfigureDovetail entry points for one host builder type. Which hosts the SDK declares for you, every metadata value and its default, and what is generated.

# DovetailHost [Section titled “DovetailHost”](#dovetailhost) A `DovetailHost` item declares the **entry points of one host**: the `ConfigureDovetail` extension methods on its builder type. Calling one creates the Dovetail context, runs every joint the application imports, and builds the host. 
```c#
var host = await Host.CreateApplicationBuilder(args).ConfigureDovetail();
```
 The item is expanded by MSBuild targets, not by the Roslyn source generator: the C# is written to `obj/` before the compiler runs, so you can open it in your IDE like any other source file. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) In most projects, nobody: `Joinery.Dovetail.Sdk` looks at the project and declares the host for you. You declare your own when the SDK does not, which is one of: * the project does not use `Joinery.Dovetail.Sdk` but references `Joinery.Dovetail`. `sample/Sample`, the benchmarks and most test projects declare their host by hand; * the host is one the SDK does not detect. Aspire’s `IDistributedApplicationBuilder` is declared by hand in `test/Joinery.Dovetail.Aspire.Tests`; the SDK has that case commented out. An integration package can declare its host itself, in the build targets NuGet imports for a direct reference. `Joinery.Dovetail.ModularPipelines` declares one for ModularPipelines’ `PipelineBuilder` that way, for a project that references it without the SDK (see [ModularPipelines](../../guides/modular-pipelines/)). Its helper, `DovetailPipelineHelpers`, is a `Joinery.Dovetail.Hosting` template like the others, and the package depends on `Joinery.Dovetail.Hosting` to get it. Do not declare a host the SDK already did. A second host on the same builder type makes `ConfigureDovetail` ambiguous (see [common mistakes](#common-mistakes)) and gives you two copies of the entry points. ### The hosts the SDK declares [Section titled “The hosts the SDK declares”](#the-hosts-the-sdk-declares) `Joinery.Dovetail.Sdk` declares one host, the first of these that matches the project (`Joinery.Dovetail.HostDetection.targets`), and an Azure Functions application gets `FunctionsApplication` next to its `HostApplication`. It becomes part of the generated class and file names, and, unless you set `HelperName`, of the name of the helper the code calls, so it has to be a valid C# identifier and it must be unique in the project. 
```xml
<!-- test/Joinery.Dovetail.Hosting.Tests/Joinery.Dovetail.Hosting.Tests.csproj -->
<DovetailHost
    Include="HostApplication"
    HostBuilderType="Microsoft.Extensions.Hosting.HostApplicationBuilder"
    HostBuilderName="builder"
    HostType="Microsoft.Extensions.Hosting.IHost"

```
 `HostBuilderType` and `HostType` are all a host needs, and the project needs a helper of the default name (`HostApplication` is named for the one `Joinery.Dovetail.Hosting` emits for the generic host). ## Metadata [Section titled “Metadata”](#metadata) Metadata is optional unless stated. A name the item does not read is ignored without a warning, so a misspelling falls back to the default. Types are written into the generated code exactly as you give them, so write them with `global::`, as the SDK does for builder types. Boolean values are compared with `true` ignoring case; any other non-empty value counts as false. | Metadata | Default | What it changes | | -------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `Namespace` | `$(RootNamespace)` | The namespace of the generated class, and so the namespace a caller imports for `ConfigureDovetail`. | | `HostBuilderType` | none; required | The type the `ConfigureDovetail` extension methods extend (and `Task` of it). The SDK’s MAUI and Uno detection sets them, and the repository’s MAUI and Uno samples and tests set them by hand. They are documented so the generated files make sense, not as a supported way to extend a host: leave them alone on a host of your own. * `SyncEntryPoint="true"` adds `UseDovetail` (from `DovetailHostSync.cs.template`) next to `ConfigureDovetail`, for hosts whose bootstrap method cannot be async (`MauiProgram.CreateMauiApp`). It blocks on `ConfigureDovetail`, which is safe only because Dovetail never resumes on the calling thread’s context: joints must not post back to the UI thread during startup. * `NavigateEntryPoint="true"` adds `ConfigureDovetail<TShell>` (from `DovetailHostNavigate.cs.template`), for Uno.Extensions.Navigation applications that start with `NavigateAsync<TShell>()` instead of `Build()`. `Joinery.Dovetail.Hosting` sets it back to `false` when the project does not reference `Uno.Extensions.Navigation`. ## What is generated [Section titled “What is generated”](#what-is-generated) Each host is written to `$(IntermediateOutputPath)`, which is `obj/<Configuration>/<TargetFramework>/`, as ordinary `Compile` items: | File | Contents | | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | | `DovetailHost.{Name}.g.cs` | The `ConfigureDovetail` entry points. | | `DovetailHost.{Name}.Sync.g.cs` | The `UseDovetail` entry points. Only with `SyncEntryPoint`. | | `DovetailHost.{Name}.Navigate.g.cs` | The `ConfigureDovetail<TShell>` entry points. Only with `NavigateEntryPoint`. | | `DovetailContextBuilder.g.cs` | `DovetailContextBuilder.Create()`, once for the project as soon as it declares any host: a builder populated with the joints the assembly imports. | All of them are in `Namespace`, in `internal static partial class GeneratedDovetail{Name}Extensions`. They are internal, so each assembly that hosts an application declares its own, and a test project that hosts one needs its own `DovetailHost` too. `ConfigureDovetail` has the same five forms on the builder and on a `Task` of it (so a builder you are still awaiting can be chained), each returning `ValueTask<{HostType}>`: 
```c#
ConfigureDovetail(this {HostBuilderType} builder, CancellationToken cancellationToken = default)
ConfigureDovetail(this {HostBuilderType} builder, Action<DovetailContextBuilder> action, CancellationToken cancellationToken = default)
ConfigureDovetail(this {HostBuilderType} builder, Func<DovetailContextBuilder, ValueTask> action, CancellationToken cancellationToken = default)
ConfigureDovetail(this {HostBuilderType} builder, Func<DovetailContextBuilder, CancellationToken, ValueTask> action, CancellationToken cancellationToken = default)
ConfigureDovetail(this {HostBuilderType} builder, DovetailContextBuilder contextBuilder, CancellationToken cancellationToken = default)
```
 Every one ends in the same call, which is where `HelperName`, `BuildExpression` and `HasBuildExpression` apply: 
```c#
return await {HelperName}.Configure(builder{BuildExpression}, contextBuilder, cancellationToken);
```
 `UseDovetail` has the same forms on the builder only and returns the `{HostType}` itself. `ConfigureDovetail<TShell>` has them on the builder only, with `where TShell : Microsoft.UI.Xaml.UIElement, new()`. ## Examples [Section titled “Examples”](#examples) ### A host the SDK declares [Section titled “A host the SDK declares”](#a-host-the-sdk-declares) For a MAUI application the SDK declares this, and `UseDovetail` is the blocking entry point it adds for `MauiProgram.CreateMauiApp` (`src/Sdks/Dovetail/Sdk/Joinery.Dovetail.HostDetection.targets`):

```xml
<DovetailHost Include="Custom" Namespace="Hosts.Custom" HostBuilderType="global::Microsoft.Extensions.Hosting.HostApplicationBuilder" HostType="global::Microsoft.Extensions.Hosting.IHost" HelperName="global::worker.CustomHelper" HostBuilderName="ignored" BuildExpression=", static b => b.Build(), &quot;extra&quot;" />

```

```c#
internal static class DovetailMineHelpers // the default HelperName of a host named Mine
{
    public static ValueTask<IHost> Configure(HostApplicationBuilder builder, Func<HostApplicationBuilder, IHost> build, DovetailContextBuilder contextBuilder, CancellationToken cancellationToken)
        => ValueTask.FromResult(build(builder));
}


internal static class CustomHelper // BuildExpression adds the string between the delegate and the context builder
{
    public static ValueTask<IHost> Configure(HostApplicationBuilder builder, Func<HostApplicationBuilder, IHost> build, string extra, DovetailContextBuilder contextBuilder, CancellationToken cancellationToken)
        => ValueTask.FromResult(build(builder));
}


internal static class NoBuildHelper // HasBuildExpression="false" drops the delegate, although BuildExpression is set
{
    public static ValueTask<IHost> Configure(HostApplicationBuilder builder, DovetailContextBuilder contextBuilder, CancellationToken cancellationToken)
        => ValueTask.FromResult(builder.Build());
}
```
 `Mine` generates `GeneratedDovetailMineExtensions` in `$(RootNamespace)`, and the other two use a namespace each, so their `ConfigureDovetail` methods do not collide. ## Common mistakes [Section titled “Common mistakes”](#common-mistakes) * **A host with no `HelperName` needs a class named `Dovetail{Name}Helpers`.** A host named `Orphan` calls `DovetailOrphanHelpers.Configure`, and the build fails with CS0103 in the generated file unless you wrote that class or named another with `HelperName`. The default fits the hosts `Joinery.Dovetail.Hosting` emits helpers for (`HostApplication`, `Maui`, `Uno`, `WebAssembly`) and Aspire’s `DistributedApplication`; for any other name, set `HelperName`. * **Two hosts on the same builder type in the same namespace make `ConfigureDovetail` ambiguous** (CS0121). An application built with the SDK already has `HostApplication` in `$(RootNamespace)`, so a second host on `HostApplicationBuilder` needs a `Namespace` of its own, and the caller imports only the one it wants. * **`HostBuilderType` and `HostType` have no default.** A host that sets neither generates a file that is not valid C# (CS1001). * **`BuildExpression` is spliced in as text.** It goes straight after `builder`, so it starts with a comma, and the `Configure` method it calls must take exactly those arguments. `HasBuildExpression="false"` removes it, including a `BuildExpression` you set. * **`HostBuilderName` changes nothing.** The template does not use it today. * **Types are written as given.** `HostBuilderType`, `HostType` and `HelperName` go into the generated code unchanged, so a bare name is looked up from `Namespace` outwards, as in any C# file. Use `global::` as the SDK does. * **`SyncEntryPoint` and `NavigateEntryPoint` belong to the MAUI and Uno host models.** `NavigateEntryPoint` emits calls to `{HelperName}.Navigate<TShell>`, which only `DovetailUnoHelpers` has; leave both alone on a host of your own. * **A misspelled metadata name is ignored.** The default applies, with no warning. * **When `Joinery.Dovetail.Hosting` is referenced, a host whose framework is missing is dropped.** If the helper a host names is one of the package’s but the project does not reference the framework it compiles against (a `Microsoft.NET.Sdk.WebAssembly` app without Blazor, say), the host is removed from the build, with a message at normal verbosity, and `ConfigureDovetail` does not exist for it. ## See also [Section titled “See also”](#see-also) * [DovetailJoint](../dovetail-joint/): the joint kinds that `ConfigureDovetail` runs. * [DovetailTemplate](../dovetail-template/): how `Joinery.Dovetail.Hosting` ships the helpers a host calls, and gates them on the host’s framework. * [Host Lifecycle](../../concepts/host-lifecycle/): code that runs as the host starts and stops. * [Defining Dovetails](../../concepts/defining-joints/): the host type a joint can be filtered by.

# DovetailJoint

> The DovetailJoint MSBuild item declares a joint kind, a typed extension point, and the build generates its interfaces, delegates, Apply method and DovetailContextBuilder method. Every metadata value, its default, and what it generates.

# DovetailJoint [Section titled “DovetailJoint”](#dovetailjoint) A `DovetailJoint` item declares a **joint kind**: a typed extension point that other code can contribute to without knowing who applies it. One line in a project file becomes a joint interface, its async twin, the delegates for both, an `Apply` extension that runs every joint of the kind, and a method on `DovetailContextBuilder` that registers a delegate. Dovetail’s own joints (`ISetupJoint`, `IServiceJoint`, `ILoggingJoint`, `IConfigurationJoint`, `IHostCreatedJoint<THost>`) are declared this way, and so are those of [Serilog](../../concepts/serilog/), [OpenTelemetry](../../concepts/opentelemetry/) and Aspire. The item is expanded by MSBuild targets, not by the Roslyn source generator: the C# is written to `obj/` before the compiler runs, so you can open it in your IDE like any other source file. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) A package or application that owns something other code should be able to configure declares a joint kind for it. Serilog’s package declares `Serilog` for `LoggerConfiguration`, so any library can add a sink; `Sample.Core` declares `DatabaseConfigurator` for its own `IDatabaseConfigurator`, so other assemblies can add tables and views. Declare one when: * you hand an object to other code at one point in startup (a builder, a configuration object) and want every library to be able to contribute to it without referencing your application or each other; * you are prepared to call `Apply{Name}` yourself at that point. A joint kind does not run by itself: `SerilogJoint` calls `loggerConfiguration.ApplySerilog(...)` once it has created the `LoggerConfiguration`. Do not declare one when: * you only want to run code at startup. Implement an existing joint such as `IServiceJoint` or `ILoggingJoint` instead, as described in [Defining Dovetails](../../concepts/defining-joints/); * Dovetail or one of its packages already declares a joint for the type you have: `Joinery.Dovetail` covers `IServiceCollection`, `IConfigurationBuilder` and `ILoggingBuilder`, and `Joinery.Dovetail.Hosting` covers the host builders. The item is read by the targets that ship in `Joinery.Dovetail`, so the project that declares it must reference that package (`Joinery.Dovetail.Sdk` adds the reference for you). The generated types are `public`, so anything that references your project sees them as ordinary API. ## Declaring a joint [Section titled “Declaring a joint”](#declaring-a-joint) The item’s `Include` is the joint’s name. It becomes part of every generated type name, and of the generated file names, so it has to be a valid C# identifier, and it must be unique in the project. 
```xml
<!-- src/Joinery.Dovetail/Joinery.Dovetail.csproj -->
<DovetailJoint Include="Setup" Namespace="Joinery.Dovetail.Joints" />
```
 That is the smallest useful declaration: a joint that is handed only the `IDovetailContext`. Everything else is metadata. ## Metadata [Section titled “Metadata”](#metadata) Metadata is optional unless stated. A name the item does not read is ignored without a warning, so a misspelling falls back to the default (`NMAmespace` leaves `Namespace` at its default). Boolean values are compared with `true` ignoring case; any other non-empty value counts as false. | Metadata | Default | What it changes | | ---------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `Namespace` | `$(RootNamespace).Joints` | The namespace of every generated type, and so the namespace consumers import. Joints of one package usually share one, as `Joinery.Dovetail.Joints` does. | | `Accessibility` | `public` | `internal` makes every generated type internal. Use it when `ParameterType` is itself internal, as the types a source generator writes into your project are (ConsoleAppFramework’s `ConsoleApp.ConsoleAppBuilder`): a public joint over an internal type is error CS0051. Any other value is written into the generated code as given. | | `ProvideConfiguration` | empty (false) | `true` adds an `IConfiguration configuration` parameter to `Register`, after the context. The value passed is `context.Configuration`; `Apply{Name}` takes no configuration parameter. | | `ProvideServices` | empty (false) | `true` adds an `IServiceCollection services` parameter to `Register`, after the configuration if there is one. With no `ParameterType` it is also the subject of `Apply{Name}`. | | `ParameterType` | empty | The type of one more `Register` parameter, the last one. It becomes the subject of `Apply{Name}`. Written into the generated code exactly as given; see [common mistakes](#common-mistakes). | | `ParameterName` | `parameter` when `ParameterType` is set | The name of that parameter, as it appears in `Register` and in `Apply{Name}`. Ignored without `ParameterType`. | | `BuilderMethodName` | `Configure{Name}` | The name of the extension method on `DovetailContextBuilder` that registers a delegate. `Service` is declared with `BuilderMethodName="ConfigureServices"`. | | `GenericParameter` | empty | A type parameter name that makes the joint generic: `I{Name}Joint<in T>`, `Apply{Name}<T>`, `Configure{Name}<T>`. `ParameterType` may be this name, and then the parameter is typed `T`. | | `GenericConstraint` | empty | The constraint of that type parameter: `where T : {GenericConstraint}`. Written as given. Ignored without `GenericParameter`. | | `GenericVariance` | `in` when `GenericParameter` is set | The variance modifier on the type parameter of the generated interfaces and delegates. Ignored without `GenericParameter`. When `ParameterType` is the type parameter, only `in` compiles; see [common mistakes](#common-mistakes). | | `IsAsync` | `true` | `false` generates only the synchronous joint. No `I{Name}AsyncJoint`, `{Name}AsyncJointDelegate` or async `Configure{Name}` overload, no `DovetailJointAsync.{Name}.g.cs`, and `Apply{Name}` returns `void` instead of `ValueTask`. | | `ReturnFirstArgument` | empty (false) | `true` makes `Apply{Name}` return `ValueTask<IDovetailContext>`, the context after the joints ran. It compiles only for a joint whose subject is the context itself: no `ParameterType` and no `ProvideServices`. With `IsAsync` false the result is discarded. | ### The parameter lists [Section titled “The parameter lists”](#the-parameter-lists) `Register` takes, in this order, only the parameters that apply: 1. `IDovetailContext context`, always; 2. `IConfiguration configuration`, with `ProvideConfiguration`; 3. `IServiceCollection services`, with `ProvideServices`; 4. `{ParameterType} {ParameterName}`, with `ParameterType`; 5. `CancellationToken cancellationToken = default`, in the async twin only. `Apply{Name}` is an extension method. Its subject (the `this` parameter) is the `ParameterType` if there is one, otherwise the service collection if `ProvideServices` is set, otherwise the context. After the subject come the context (unless it is the subject), the service collection (if `ProvideServices` and `ParameterType` are both set) and, last, a `CancellationToken cancellationToken = default`. ## What is generated [Section titled “What is generated”](#what-is-generated) Each joint is written to `$(IntermediateOutputPath)`, which is `obj/<Configuration>/<TargetFramework>/`, as ordinary `Compile` items: | File | Contents | | -------------------------------- | --------------------------------------------------------------------------------------------------------------- | | `DovetailJoint.{Name}.g.cs` | `I{Name}Joint`, its delegate, `Apply{Name}` and the `Configure{Name}` method for the delegate. | | `DovetailJointAsync.{Name}.g.cs` | `I{Name}AsyncJoint`, its delegate and the `Configure{Name}` method for it. Not written when `IsAsync` is false. | Everything is declared in `Namespace`: | Type | What it is | | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `I{Name}Joint` | The interface a contributor implements: `void Register(...)`. Mark the class `[DovetailExport]` so it is discovered; see [Defining Dovetails](../../concepts/defining-joints/). | | `{Name}JointDelegate` | A delegate with the same parameters, for registering a lambda. | | `I{Name}AsyncJoint` | The async twin: `ValueTask Register(..., CancellationToken cancellationToken = default)`. | | `{Name}AsyncJointDelegate` | The async delegate. | | `{Name}JointExtensions` | A static partial class holding `Apply{Name}`, which runs every registered `I{Name}Joint` and `I{Name}AsyncJoint` through the executor. | | `{Name}HostBuilderExtensions` | A static partial class with an `extension(DovetailContextBuilder)` block: `Configure{Name}(delegate, priority = 0, category = null, hostType = Undefined)`, once for each delegate type. Generated for every joint, including the ones whose subject is the context. | The interfaces derive from `IDovetailJoint` and, like the delegates, carry `[JointName("{Name}")]`. For the Serilog declaration [below](#a-joint-with-a-parameter-services-and-its-own-namespace), the build writes this (abridged from `obj/Debug/net10.0/DovetailJoint.Serilog.g.cs`, which also holds the attributes, the XML comments and the method bodies):

```xml
<DovetailJoint Include="Minimal" />
<DovetailJoint Include="Wired" ProvideConfiguration="true" ProvideServices="true" />
<DovetailJoint Include="Builder" Namespace="Custom.Joints" ProvideServices="true" ParameterType="global::Microsoft.Extensions.Logging.ILoggingBuilder" ParameterName="builder" BuilderMethodName="ConfigureTheBuilder" />
<DovetailJoint Include="Generic" GenericParameter="TBuilder" GenericConstraint="global::Microsoft.Extensions.Hosting.IHostApplicationBuilder" ParameterType="TBuilder" ParameterName="builder" />
<DovetailJoint Include="Covariant" GenericParameter="T" GenericVariance="out" />
<DovetailJoint Include="SyncOnly" IsAsync="false" />
<DovetailJoint Include="Chained" ReturnFirstArgument="true" />
<DovetailJoint Include="ChainedSync" ReturnFirstArgument="true" IsAsync="false" />
<DovetailJoint Include="Unprefixed" ParameterType="Microsoft.Extensions.Logging.ILoggingBuilder" ParameterName="builder" />
<DovetailJoint Include="Ignored" ParameterName="thing" GenericConstraint="class" GenericVariance="out" NMAmespace="Custom.Typo" />
<DovetailJoint Include="Shouting" IsAsync="False" ProvideServices="TRUE" />
<DovetailJoint Include="NotTrue" IsAsync="no" />
```
 * `Minimal` is handed only the context, and its types are in `worker.Joints` (the test project’s `RootNamespace` is `worker`). * `Wired` registers `Register(IDovetailContext context, IConfiguration configuration, IServiceCollection services)`, and its `ApplyWired` is an extension on `IServiceCollection`. * `Builder` is applied with `logging.ApplyBuilder(context, services)` and registered with `ConfigureTheBuilder(...)`. * `Generic` declares `IGenericJoint<in TBuilder> where TBuilder : IHostApplicationBuilder`. * `Covariant` has a type parameter that `Register` does not take, so `out` compiles, and an `ICovariantJoint<string>` is an `ICovariantJoint<object>`. * `SyncOnly` has no async twin, and `context.ApplySyncOnly()` returns `void` but still takes a `CancellationToken`. * `Chained.ApplyChained` returns the context. `ChainedSync` has no async twin and `ApplyChainedSync` returns `void`: the context the executor returns is discarded. * `Unprefixed` is written into the generated code as `Microsoft.Extensions.Logging.ILoggingBuilder`, with nothing in front of it. * `Ignored` generates the same code as `Minimal`: `ParameterName` without a `ParameterType`, `GenericConstraint` and `GenericVariance` without a `GenericParameter`, and the misspelled `NMAmespace` all do nothing, so its types are in `worker.Joints`. * `Shouting` and `NotTrue` are synchronous: `False` and `no` are not `true`. `Shouting` also takes the service collection, because `TRUE` is `true` in any case. ## Common mistakes [Section titled “Common mistakes”](#common-mistakes) * **`ParameterType` and `GenericConstraint` are written exactly as you give them.** Dovetail puts nothing in front of them, so write the type fully qualified with `global::`, as every package in this repository does: `global::Serilog.LoggerConfiguration`. A bare `Serilog.LoggerConfiguration` compiles too, until a namespace that encloses the generated code has a member called `Serilog`, which then captures the name. A project that declares `Custom.Microsoft` does that to a bare `Microsoft.Extensions.Logging.ILoggingBuilder` in a joint in `Custom.Joints`, and the build fails with CS0234. * **A generic joint’s `ParameterType` may be its `GenericParameter`**, and then must be written bare, as `TBuilder`: a `global::` in front of it names a type in the global namespace, not the type parameter. * **`GenericVariance="out"` does not compile when the type parameter is the `ParameterType`** (CS1961): it is an input of `Register`, so a covariant one is invalid, and `in`, the default, is the only value that compiles. With a `GenericParameter` and no `ParameterType`, `Register` does not take the type parameter, and `out` compiles. * **`ReturnFirstArgument` only suits a joint whose subject is the context.** With a `ParameterType` or `ProvideServices` the generated `Apply{Name}` tries to return the `IDovetailContext` as a `ValueTask<ILoggingBuilder>` (or whatever the subject is), which fails with CS0029. * **`ParameterName` without a `ParameterType`, and `GenericConstraint` or `GenericVariance` without a `GenericParameter`, do nothing.** The metadata is ignored, with no warning. * **A misspelled metadata name is ignored too.** `src/Joinery.Dovetail.Aspire.Testing` writes `NMAmespace`, so its namespace is the default, which happens to be the one it meant. * **`IsAsync="false"` leaves contributors no way to do async work for the kind**, since there is no `I{Name}AsyncJoint` to implement. `Apply{Name}` still takes a `CancellationToken`, which the synchronous call ignores. * **The name is part of every generated file and type name**, so declare each joint once. ## See also [Section titled “See also”](#see-also) * [Defining Dovetails](../../concepts/defining-joints/): implementing, ordering and filtering the joints of a kind. * [DovetailHost](../dovetail-host/): the entry points that run the joints. * [Serilog](../../concepts/serilog/) and [OpenTelemetry](../../concepts/opentelemetry/): two packages built on joint kinds.

# DovetailTemplate

> The DovetailTemplate MSBuild item ships C# source from a package and has Dovetail write it into only the projects that should get it. Every metadata value, its default, the gates, the tokens metadata replaces, and where the generated file lands.

# DovetailTemplate [Section titled “DovetailTemplate”](#dovetailtemplate) A `DovetailTemplate` item names a `*.cs.template` file that a package ships and says which projects should get a copy. When the project’s references have resolved, Dovetail checks every template’s gates, writes the ones that pass to `obj/` and adds them to the compilation. Nothing needs to be compiled against, so the shipping package depends on none of the assemblies its templates use: referencing them is what turns a template on. This page lists what the item accepts. [Shipping templates](../../guides/shipping-templates/) is the guide to using it: how to write a template, how to pack the targets that declare it, and how to test the gates. The item is expanded by MSBuild targets (`Joinery.Dovetail.Templates.targets`), not by the Roslyn source generator. ## Who declares one, and when [Section titled “Who declares one, and when”](#who-declares-one-and-when) A package that wants to put C# into the projects that use it declares its templates from its `build/` or `buildTransitive/` targets. `Joinery.Dovetail.Hosting` is the main user: its ASP.NET Core, MAUI, Uno and Blazor WebAssembly helpers and its OpenTelemetry joints are all templates, which is why that package has no dependency on any of those frameworks. A solution can declare templates in a `Directory.Build.targets` to the same effect. Declare one when the code you ship has to be compiled into the consumer, because it uses types the consumer references and you do not. Do not declare one when ordinary compiled code will do: a library the consumer references is simpler, and a template is only worth it for what needs to be gated on the project. A project that does not run the Dovetail source generator (`Joinery.Dovetail.Analyzers`) gets no templates, however they are gated, since a template is meant to hold joints and `[Embedded]` helpers that the generator discovers. ## Declaring a template [Section titled “Declaring a template”](#declaring-a-template) The item’s `Include` is the template’s name. It names the generated file, so it has to be unique across every package a project references. It is also what the gates and the generated file are keyed on, so a different `OutputPrefix` does not keep two templates with one name apart. A package that declares templates from names its consumers choose, such as one per client, should prefix them with its own name (`Include="Chirograph.RocketsClient"`) and pass the bare name as [metadata](#tokens). 
```xml
<!-- a package's declaration, built by test/Joinery.Dovetail.Sdk.Tests/TemplateExtensionPointTests.cs -->
<DovetailTemplate Include="Plain" File="$(MSBuildThisFileDirectory)Plain.cs.template" Package="DovetailTemplateShipper" />
```
 `File` is the only metadata that is required. Leave out `Package`, `References` and `Hosts` and the template goes into every project that runs the generator. ## Metadata [Section titled “Metadata”](#metadata) Metadata is optional unless stated. A name the item does not read is ignored without a warning, so a misspelling falls back to the default. Every gate you set has to pass; a gate you leave out does not restrict anything. Boolean values are compared with `true` ignoring case; any other non-empty value counts as false. | Metadata | Default | What it changes | | --------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `File` | none; required | The full path of the template, usually `$(MSBuildThisFileDirectory)Name.cs.template`. A template without one, or whose file does not exist, fails the build. Backslashes in it are written as they are. | | `Package` | empty | The id of the package that ships the template. The template is only written into a project that references it: the package’s assembly, which is named after the package, is among the project’s resolved references (or, with `DirectReferenceOnly`, the project declares the reference itself). | | `DirectReferenceOnly` | empty (false) | `true` limits the template to projects with a direct reference to `Package`: a `PackageReference` to it (the ones the Dovetail SDK adds count), or a `ProjectReference` to a project named after it. A project that only gets the package transitively gets nothing. Requires `Package`; without it the build fails. | | `References` | empty | Semicolon-separated assembly names (file names without extension). Every one has to be among the project’s resolved references. | | `Hosts` | empty | Semicolon-separated `DovetailHost` names, at least one of which the project has to declare: the host model, as `Joinery.Dovetail.Sdk` detects it (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui`, `Uno`). These are the hosts declared when the templates resolve, before a package narrows them. | | `HostName` | empty | Replaces `{HostName}` and `__HostName__` in the template, but only when `HostType` is set too. | | `HostType` | empty | Replaces `{HostType}` and `__HostType__` in the template, and switches the `HostName` replacement on. Together they let one template be emitted once per host model under different names. | | `OutputPrefix` | `DovetailTemplate` | The prefix of the generated file name, `<prefix>.<name>.g.cs`. | The gates are applied together, and a template that fails any of them is not written. They are read once the project’s references have resolved, which is right after `ResolveAssemblyReferences` and before the compiler runs. ## Tokens [Section titled “Tokens”](#tokens) Every metadata value of the item replaces two tokens in the template: `{Name}` and `__Name__`, where `Name` is the metadata’s name. That holds for the metadata above (`{OutputPrefix}`, `__Package__`, …) and for any metadata you add yourself, which the table does not list because the item reads it only here: 
```xml
<!-- the declaration test/Joinery.Dovetail.Sdk.Tests/TemplateExtensionPointTests.cs builds, less the metadata it adds to cover more tokens -->
<DovetailTemplate Include="Chirograph.RocketsClient" File="$(MSBuildThisFileDirectory)Client.cs.template" ClientName="RocketsClient" Namespace="MyApp.Rockets" />
```
 
```csharp
// Client.cs.template: written as DovetailTemplate.Chirograph.RocketsClient.g.cs
namespace __Namespace__;


internal static class __ClientName__ { }
// {ClientName} in {Namespace}
```
 * **Use `__Name__` where C# needs an identifier.** `__ClientName__` is a valid class name, so the template stays a C# file an editor can read; `{ClientName}` is for comments, strings and anywhere else an identifier is not needed. * **A token no metadata fills is left as it is.** So is the token of a metadata whose value is empty, and `{HostName}` while `HostType` is empty. Metadata names compare ignoring case, as MSBuild’s do. * **Values are written as they are.** Nothing is escaped for C#: a value that ends up inside a string literal has to be valid there. * **The replacement is one pass.** A value that contains a token is not expanded again. Declaring one `File` under several `Include`s, each with its own metadata, writes one file per `Include`; that is how a package emits one joint per client from a single template. ### Knowing that tokens are expanded [Section titled “Knowing that tokens are expanded”](#knowing-that-tokens-are-expanded) `Joinery.Dovetail` sets `DovetailTemplateMetadataTokens` to `true` in the projects it reaches. A version of Dovetail without it only replaces `{HostName}` and `{HostType}`, so a package that depends on other tokens should declare those templates only when the property is set: 
```xml
<ItemGroup Condition="'$(DovetailTemplateMetadataTokens)' == 'true'">
  <DovetailTemplate Include="RocketsClient" File="$(MSBuildThisFileDirectory)Client.cs.template" ClientName="RocketsClient" />
</ItemGroup>
```
 The property is set from Dovetail’s `.props`, so it is there before any package’s `.targets` declare their items. ## What is generated [Section titled “What is generated”](#what-is-generated) Each template that passes is written to `$(IntermediateOutputPath)`, which is `obj/<Configuration>/<TargetFramework>/`, as an ordinary `Compile` item: | File | Contents | | ---------------------- | ---------------------------------------------------------------------------------------------------------------------- | | `<prefix>.<name>.g.cs` | The template’s text, with its [tokens](#tokens) replaced. The prefix is `OutputPrefix`, `DovetailTemplate` by default. | The item adds no namespace, type or method of its own: the template is the C#. For `Joinery.Dovetail.Hosting`, which sets `OutputPrefix="DovetailHosting"`, a generic-host application gets `obj/Debug/net10.0/DovetailHosting.DovetailHostApplicationHelpers.g.cs`. The templates that passed are the `DovetailEmittedTemplate` items, with the metadata above carried over. A target can add to them or remove from them between `DovetailResolveTemplates` and `DovetailGenerateTemplates`; the guide shows how. ## Examples [Section titled “Examples”](#examples) ### Minimal [Section titled “Minimal”](#minimal) The declaration above is the one the extension-point tests build. They pack a package that ships it, reference it from projects that declare the reference themselves and from one that only receives it transitively, and read which `DovetailTemplate.*.g.cs` files land in each `obj/`. ### A package that ships many [Section titled “A package that ships many”](#a-package-that-ships-many) `Joinery.Dovetail.Hosting` lists its helpers with the assemblies each needs, then declares every one as a template for the package: 
```xml

    <_DovetailHostingHelper Include="DovetailUnoHelpers" References="Uno.Extensions.Hosting.WinUI" />

    <_DovetailHostingHelper Include="DovetailWebAssemblyHelpers" References="Microsoft.AspNetCore.Components.WebAssembly" />
```

 `References` carries over from `_DovetailHostingHelper` to each template, so a project gets `DovetailMauiHelpers` only when it references `Microsoft.Maui`. ### One template for several hosts [Section titled “One template for several hosts”](#one-template-for-several-hosts) The OpenTelemetry start joint is one template emitted once per host model, which is what `HostName` and `HostType` are for. The package adds the instances to `DovetailEmittedTemplate` itself, because which of them a host needs depends on helpers that have already been resolved: 
```xml
<!-- src/Joinery.Dovetail.Hosting/build/Joinery.Dovetail.Hosting.targets: one of the items of an ItemGroup, verbatim apart from the indentation -->

  Include="DovetailOpenTelemetryMauiStartJoint"
  Condition="'$(_DovetailHostingMaui)' == 'true'"
  File="$(MSBuildThisFileDirectory)DovetailOpenTelemetryStartJoint.cs.template"
  OutputPrefix="DovetailHosting"
  HostName="Maui"
  HostType="global::Microsoft.Maui.Hosting.MauiApp" />
```

 ### The gates, built [Section titled “The gates, built”](#the-gates-built) `test/Joinery.Dovetail.Sdk.Tests/DovetailItemReferenceTests.cs` builds a project that declares the following, and checks which files land in `obj/` (the project is a generic-host application that references `Microsoft.Extensions.Hosting`; its templates are `Plain.cs.template`, and so on): 
```xml
<DovetailTemplate Include="Plain" File="$(MSBuildThisFileDirectory)Plain.cs.template" />
<DovetailTemplate Include="Prefixed" File="$(MSBuildThisFileDirectory)Prefixed.cs.template" OutputPrefix="Contoso" />
<DovetailTemplate Include="Referenced" File="$(MSBuildThisFileDirectory)Referenced.cs.template" References="Microsoft.Extensions.Hosting" />
<DovetailTemplate Include="MissingReference" File="$(MSBuildThisFileDirectory)MissingReference.cs.template" References="Microsoft.Extensions.Hosting;Not.Referenced.Anywhere" />
<DovetailTemplate Include="ForThisHost" File="$(MSBuildThisFileDirectory)ForThisHost.cs.template" Hosts="Maui;HostApplication" />
<DovetailTemplate Include="ForOtherHosts" File="$(MSBuildThisFileDirectory)ForOtherHosts.cs.template" Hosts="Maui;Uno" />
<DovetailTemplate Include="PerHost" File="$(MSBuildThisFileDirectory)PerHost.cs.template" HostName="Mine" HostType="global::System.Object" />
<DovetailTemplate Include="NameOnly" File="$(MSBuildThisFileDirectory)NameOnly.cs.template" HostName="Mine" />
```
 `Plain`, `Referenced`, `ForThisHost`, `PerHost` and `NameOnly` are written, `Prefixed` as `Contoso.Prefixed.g.cs`; `MissingReference` and `ForOtherHosts` are not. In `PerHost` `{HostName}` and `{HostType}` are replaced; in `NameOnly` the text `{HostName}` is left as it is. ## Common mistakes [Section titled “Common mistakes”](#common-mistakes) * **`Include` is the file name, so it has to be unique across packages.** Two templates with one name write one file, whatever their `OutputPrefix`; prefix the names your package makes up with the package’s name. * **`File` has to be a full path.** Use `$(MSBuildThisFileDirectory)`, which is the directory of the targets file that declares the item. A missing `File` fails the build with `the template '<name>' has no File`, and a path that does not exist with `names a file that doesn't exist`. * **`DirectReferenceOnly` without `Package` fails the build** (`is DirectReferenceOnly, so it needs the Package it is direct to`). * **`Package` is matched against an assembly name.** It is the package’s id, and it has to be the name of the package’s assembly as well, since that is what the project’s resolved references are searched for. * **`HostName` alone does nothing.** `{HostName}` is replaced only when `HostType` is set; set both. * **`Hosts` names are `DovetailHost` names.** Each is matched, by name, against the `DovetailHost` items declared when the templates resolve, which are the ones `Joinery.Dovetail.Sdk` detected (`HostApplication`, `WebApplication`, `WebAssembly`, `Maui`, `Uno`) plus any you declared. See [DovetailHost](../dovetail-host/). * **A transitive reference declares your items but gets no file under `DirectReferenceOnly`.** Its `buildTransitive/` targets still run, so the `DovetailTemplate` items are there; the gate is what leaves the file out. * **A misspelled metadata name is ignored.** The default applies, with no warning, and its tokens stay in the file. * **A token in a template that does not set its metadata is not an error.** `{Unknown}` is written as it is; if it is in code, the compiler is what complains. * **Templates do not reach projects that skip the generator.** A project without `Joinery.Dovetail.Analyzers` gets none. ## See also [Section titled “See also”](#see-also) * [Shipping templates](../../guides/shipping-templates/): the guide to writing, packing and testing templates. * [DovetailHost](../dovetail-host/): the hosts that `Hosts` refers to, and the helpers `Joinery.Dovetail.Hosting` ships as templates. * [DovetailJoint](../dovetail-joint/): the joint kinds a template can declare joints of.
