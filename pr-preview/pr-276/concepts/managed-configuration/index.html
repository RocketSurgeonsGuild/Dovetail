Managed Configuration

Section titled “Managed Configuration”

A library that ships configuration describes it once, as a C# type. Dovetail’s source generator reads that type and produces two things from the same model:

  • a binder that fills the type from IConfiguration and registers it as IOptions<T>, with no reflection, so it is AOT and trimming safe;
  • a JSON Schema fragment that describes the type’s section. The build merges the fragments of every referenced library into one schema for the application, which editors use for completion, hover documentation and validation of appsettings.json, YAML and TOML files. See Editor setup.

The library’s default values still ship as an appsettings file, which Dovetail packs and copies into hosts (below).

Note

The schema and the generated binder need C# 12 or later. In a project with an older LangVersion the generator emits nothing and reports DT0006.

Section names

Section titled “Section names”
AttributeSection
[DovetailConfiguration]The type name with one Options, Settings, Configuration or Config suffix removed: GreetingsOptions becomes Greetings (in the declared key style).

There is no prefix. A name that would become empty after stripping the suffix (a class called Options) is an error (DT0008); give it a path.

Key style

Section titled “Key style”

KeyStyle on [DovetailConfiguration] (and on DovetailConfiguration<T>) picks how the keys of the section are spelled. It is set per attribute; there is no assembly-wide or MSBuild default. There are five values:

KeyStyleWhat the canonical key isMaxFileSizeMbHTTPServerHttpClientOptions section
UndefinedThe declared name exactly as written. The default.MaxFileSizeMbHTTPServerHttpClient
PascalThe declared name with its first letter upper-cased.MaxFileSizeMbHTTPServerHttpClient
CamelLower camel case (JsonNamingPolicy.CamelCase).maxFileSizeMbhttpServerhttpClient
DashLower-case words joined with - (KebabCaseLower).max-file-size-mbhttp-serverhttp-client
UnderscoreLower-case words joined with _ (SnakeCaseLower).max_file_size_mbhttp_serverhttp_client
  • Undefined respells nothing. The binder literal, the schema’s properties key, the strict closing of the section and the derived section path (after the suffix is stripped) are the names as declared. Configuration keys are case-insensitive, so data in any casing binds, as long as the letters are right: maxfilesizemb, MaxFileSizeMb and MAXFILESIZEMB are the same key. Dashes and underscores are other letters, so max-file-size-mb does not match MaxFileSizeMb.
  • Pascal is an explicit style. It upper-cases the first letter of a declared name. C# property names already start in upper case, so for them Undefined and Pascal give identical output; they differ for a member declared as myKey, which stays myKey under Undefined and becomes MyKey under Pascal.
  • What it covers. The key of every bound property and constructor parameter of the options type and of every object type nested in it (in lists and dictionary values too). The generated binder reads those keys, and the schema uses them for properties, the case-insensitive patternProperties twins and the strict propertyNames.
  • What it leaves alone. Dictionary keys, enum values and every other piece of data are never restyled, and neither is an explicit section string ("Http:Retry" is used as written, segment by segment).
  • Word splitting is System.Text.Json’s: Camel is JsonNamingPolicy.CamelCase, Dash is JsonNamingPolicy.KebabCaseLower and Underscore is JsonNamingPolicy.SnakeCaseLower, so HTTPServer is httpServer, http-server and http_server, and Http2Enabled is http2Enabled, http2-enabled and http2_enabled.
  • [ConfigurationKeyName] wins. An explicit key name is used verbatim, in every style.
  • Derived section names follow the style, after the Options, Settings, Configuration or Config suffix is removed: GreetingsOptions is Greetings, greetings and greetings; HttpClientOptions is HttpClient, httpClient, http-client and http_client.
  • Case. Because keys ignore case, Camel against Undefined or Pascal only changes the spelling the schema suggests; maxFileSizeMb and MaxFileSizeMb bind the same value. Dash and Underscore change the letters the binder reads: a value written as MaxFileSizeMb no longer binds (max-file-size-mb or max_file_size_mb does), and the schema’s patternProperties only accept those keys in any case.
  • One spelling per type. The generated binder exists once for each type, so a type reached from sections that spell its keys differently, such as a RetryOptions used by a camel section and a dash section, can’t be bound correctly. The later declaration is reported as DT0016 and produces nothing, the same way as DT0015. The comparison is of the effective keys, not of the style names: Undefined and Pascal do not conflict on ordinary names, which spell the same keys, but do on a member declared in lower case. Use the same KeyStyle for every section that reaches the type, or give the shared type [ConfigurationKeyName] attributes (a type whose keys don’t depend on the style isn’t a conflict). Sections with RegisterOptions = false bind nothing, so they can’t conflict.

One section per type

Section titled “One section per type”

A type has exactly one section, so it is declared once. There are two attribute forms:

  • [DovetailConfiguration] (or [DovetailConfiguration("Section")]) on the class. It can’t be repeated on a type.
  • [assembly: DovetailConfiguration<T>("Section")] for a type you don’t own. Repeat it for each type; naming the same T twice is DT0015 as well.

Declaring a type with both forms is an error (DT0015). The diagnostic is reported on the assembly attribute; the class declaration is the one that produces the schema fragment and the registration, and the assembly attribute produces nothing.

At run time each library reads only its own section from the application’s complete IConfiguration, which the service provider supplies when the options are first created, and creates or binds its options from it. Dovetail doesn’t order, de-duplicate or merge sections. The generated joint registers an assembly’s types by section path, then type name, and the standard options pipeline does the rest.

Every type is created by generated code and registered through an IOptionsFactory<T>, so your own Configure<T>, PostConfigure<T> and validators run on the created instance, whenever they were registered.

Registering by hand

Section titled “Registering by hand”

The generated joint calls one public extension method on IServiceCollection, AddDovetailConfigurationOptions. You can call it yourself, for example for a type declared with RegisterOptions = false. It returns the OptionsBuilder<TOptions>, so Validate and ValidateOnStart() chain as usual.

OverloadDoes
AddDovetailConfigurationOptions<T>(sectionPath, Func<IConfiguration, T> create)Creates the default T with create, from the section at sectionPath, and watches the configuration for reloads. Reflection free, so it is AOT safe.

There is one overload because everything is created through generated create code: for a type with a public parameterless constructor the generator emits new T() followed by the bind, and for the rest the constructor or initializer call. No registration path uses reflection. To bind a type with reflection, use Microsoft’s Configure<T>(IConfiguration) or AddOptions<T>().Bind(...) yourself.

  • The configuration is the application’s complete IConfiguration, resolved from the service provider when the options are first created. create receives that configuration’s section at sectionPath (such as Http:Retry). An empty path throws.
  • A change token source watches the configuration, so IOptionsMonitor<T> and IOptionsSnapshot<T> see reloads of the default options.
  • The call registers an IOptionsFactory<T> with TryAdd: the first registration for a type wins, and later calls are ignored. A factory your application registers itself wins over Dovetail’s, so create is never called for that type.
  • The factory derives from OptionsFactory<T>, so configure and post-configure actions and validators still run on the instance create returns. On .NET 11, don’t give such a type asynchronous validators: they fail synchronous validation through a derived factory.

Named options

Section titled “Named options”

Dovetail registers the default options only. Reading a name other than the default, such as IOptionsMonitor<T>.Get("tenant-a"), throws an InvalidOperationException naming the type and the options name.

Validation

Section titled “Validation”

Dovetail never turns on ValidateDataAnnotations. [Range], [MinLength] and the other annotations describe the schema, which is how editors flag a bad value; they are not enforced at run time. To enforce rules, write an [OptionsValidator] class, the options validation source generator from Microsoft.Extensions.Options:

Dovetail registers every such validator in the assembly for the option types it registers, with TryAddEnumerable, so it never duplicates one you added yourself. Add ValidateOnStart = true on the attribute and a bad configuration fails the host at startup.

Supported types

Section titled “Supported types”

The generator follows Microsoft’s configuration binding source generator, not the serializer:

  • string, bool, every numeric type (including Half, Int128 and UInt128), char, enums (any casing), TimeSpan, DateTime, DateTimeOffset, DateOnly, TimeOnly, Guid, Version, Uri, CultureInfo, byte[];
  • Nullable<T> of the above;
  • nested classes, structs and records, and recursive types (the schema uses $ref);
  • arrays, lists, sets and the other collection types the binder supports, and dictionaries with string, enum or integer keys;
  • object and IConfigurationSection, which accept any value.

A type with a [TypeConverter] is described as an object, because the binder ignores converters. A member the binder can’t bind is left out of both the schema and the binder, with warning DT0009. [ConfigurationKeyName] renames a key (see Key style for restyling them all), and from binder 11 [ConfigurationIgnore] leaves a member out.

Ranges and defaults are also written into the description, since editors don’t show them. A default of "" is skipped, both as default and in the description, because “Default: .” tells nobody anything. The XML summary is read from the source whether or not GenerateDocumentationFile is on. <inheritdoc /> and <include> produce no description. Annotations that JSON Schema can’t express are dropped with DT0013.

Fragments are permissive: nothing is required unless you set <DovetailConfigurationSchemaRequired>true</DovetailConfigurationSchemaRequired>, which marks required members, [Required] properties and value-type constructor parameters without defaults.

The generated binder

Section titled “The generated binder”

Dovetail doesn’t call Microsoft’s binding generator. A source generator never sees another generator’s output, so the calls in Dovetail’s own code would not be intercepted. Instead it ports that generator: the parser, the type specifications and the emitter from dotnet/runtime (MIT), at tags v10.0.13 and v11.0.0-rc.2. The rules follow the major version of Microsoft.Extensions.Configuration.Binder that the project references (version 11 when it references none), not the target framework, because a net10.0 application can reference Binder 11.

What the two versions do differently:

The same data is bound three ways in the parity tests (Microsoft’s generator, the reflection binder, Dovetail’s) on both versions.

Records and other immutable types

Section titled “Records and other immutable types”

Types the options pipeline can’t create (constructor parameters, init-only or required members) are registered like any other type: the generated create code builds the instance from the type’s section, and your Configure<T> and validators still run on it.

Where Dovetail differs from Microsoft’s generator, on purpose

Section titled “Where Dovetail differs from Microsoft’s generator, on purpose”
  1. Object-initializer types. Microsoft’s generator never sets init-only members of a type with a parameterless constructor, and can’t create a type with required members (CS9035). Dovetail creates them with an object initializer, then binds the rest. A missing key keeps the member’s own initial value, as the reflection binder does; a required member with no value gets default.
  2. required members that can’t be bound (an unsupported type or [ConfigurationIgnore]) are set to default!, so the generated code compiles. DT0009 reports the member.
  3. Empty sections still produce an instance for factory types. Get<T>() returns null there, but IOptions<T>.Value can’t be null. A missing required constructor parameter throws the first time the options are read.
  4. No NotSupportedExceptions and no BindNonPublicProperties.
  5. Self-expanding generics such as class Node<T> { Node<Node<T>> Next; } are treated as unsupported past a nesting depth of 10 or 1,000 types, instead of making the analysis run forever. The schema reports DT0012 for the same graphs.

Microsoft’s own quirks are kept. A positional record’s extra init-only property is set to default when its key is missing, overriding its initializer, and Binder 10 binds constructor-bound collections twice.

Registration also differs from services.Configure<T>(section) in that the configuration’s reload token feeds IOptionsMonitor<T> through one change token source per type, and the IConfiguration is resolved from the container when the options are first created, not captured at registration.

The schema

Section titled “The schema”

Library fragments

Section titled “Library fragments”

Each assembly embeds one fragment per section as [assembly: AssemblyMetadata("Dovetail.ConfigurationSchema.v1:<Section>", "<JSON Schema>")]. Each fragment is a Draft-07 schema of the section’s value, with every object type described once under definitions. Every key also has a case-insensitive patternProperties entry with the same schema, so retries: 99 is checked even when written as Retries.

Every project that isn’t a host (a library) also writes its own fragments as $(IntermediateOutputPath)ConfigurationSchema.json (permissive, rooted at the configuration root like Aspire’s) and packs it at the NuGet package root, so Visual Studio and other tools that understand Aspire’s layout can use it. A multi-targeted library writes one per target framework and packs the first one’s. A library with no sections writes nothing.

The merged application schema

Section titled “The merged application schema”

Hosts are test projects (IsTestProject) and applications (detected by Joinery.Dovetail.Sdk, or OutputType of Exe or WinExe). A host merges its own fragments and those of every referenced assembly into $(BaseIntermediateOutputPath)appsettings.schema.json, normally obj/appsettings.schema.json.

  • The file is a stable path editors can point at. A host that targets several frameworks writes that file from its first target framework, and $(IntermediateOutputPath)appsettings.schema.json (for example obj/Debug/net10.0/) from the others.

  • It is copied to $(OutDir), next to appsettings.json, and published as appsettings.schema.json. A project that references the host (a test project referencing an application) doesn’t get a second copy.

  • Hosts that embed their configuration (DovetailEmbedConfiguration is true, which Joinery.Dovetail.Sdk sets for MAUI and Uno applications) keep the file in obj/ only: no copy to the output directory and no publishing.

  • A hand-made appsettings.schema.json (Web SDK content, or one from a reference) is removed from the publish items so it doesn’t collide with the generated one (NETSDK1152). The generated file is what gets published.

  • It is strict. Each Dovetail section, and the object types it uses, accepts only its own keys. The check is a case-insensitive propertyNames pattern rather than additionalProperties: false, so message is accepted and Mesage is flagged, with an error that lists the known keys. The root, parents shared between sections, dictionaries and sections declared by more than one assembly stay open for keys of other sources.

  • It includes SchemaStore’s appsettings.json schema, embedded rather than referenced, so Logging, Kestrel and ConnectionStrings complete too, online or offline. The copy ships with Dovetail and is refreshed each release (Apache-2.0).

  • It is deterministic. Sections compare ignoring case; when libraries spell a section differently, the ordinal-smallest spelling is displayed. A section several assemblies declare is merged into one object. The same references always produce a byte-identical file.

PropertyDefaultEffect
DovetailConfigurationSchemaonfalse writes no schema files at all, and removes the ones an earlier build wrote.
DovetailConfigurationSchemaHostdetectedtrue or false overrides which projects count as hosts.
DovetailConfigurationSchemaStricttruefalse leaves Dovetail’s sections open (no propertyNames) in the host file.
DovetailConfigurationSchemaIncludeSchemaStoretruefalse leaves SchemaStore’s schema out of the host file.
DovetailEmbedConfigurationdetectedtrue for hosts that embed their configuration (Joinery.Dovetail.Sdk sets it for MAUI and Uno): the schema stays in obj/, with no copy to the output and no publish.
DovetailConfigurationSchemaRequiredfalsetrue lists required members in required. The generator reads this one, so it changes the fragments in every project; the MSBuild targets don’t use it.

Note

Editors flag a quoted number such as "Timeout": "30" as an incorrect type, although the .NET binder accepts it. Dovetail keeps the schema strict about types so that ranges are always checked.

The build target runs after CoreCompile and skips design-time builds. It writes only when its inputs change: the references, the project’s own assembly and the properties above. Merging runs in a compiled MSBuild task (Joinery.Dovetail.Build.Tasks) that reads the fragments with System.Reflection.Metadata, so no assembly is loaded and nothing is embedded in your application.

Serilog

Section titled “Serilog”

Joinery.Dovetail.Serilog ships a schema for the Serilog section, so a host that references it gets completion and validation for Serilog without any setup. The section is read by hand (see Serilog), so no options type describes it and the generator has nothing to emit. Joinery.Dovetail.Serilog carries the same AssemblyMetadata fragment as a hand-written attribute instead, and it goes through the pipeline above unchanged: the library’s ConfigurationSchema.json is packed at the package root, and a host merges the fragment into its appsettings.schema.json like any other.

The schema describes what Joinery.Dovetail.Serilog reads, which is the minimum level and nothing else, because the rest of Serilog.Settings.Configuration’s format needs reflection that is not trimming or Native AOT safe. It models one key:

  • MinimumLevel, as a level name (Verbose, Debug, Information, Warning, Error or Fatal; the names are matched exactly) or as an object with Default and Override (a map from a source such as Microsoft.AspNetCore to a level). A number, or an unknown name, is flagged.

Every other key of the section (Using, WriteTo, AuditTo, Enrich, Filter, Destructure, Properties, LevelSwitches, FilterSwitches and MinimumLevel’s ControlledBy, or a level switch given as a value) is flagged by the strict merged schema rather than accepted, so that configuration copied from Serilog’s documentation, which would be ignored, does not look as if it were working. The level rules follow the Serilog definition in SchemaStore’s appsettings.json schema, the one the merged file embeds by default, narrowed to the six levels (SchemaStore also lists Off, which Serilog has no level for) and with no switches. Both apply in the merged file, so the fragment is what rejects the keys that are not read.

What else differs from SchemaStore’s schema, and why it is harmless:

  • Casing. Configuration keys ignore case, so the fragment, like every Dovetail fragment, accepts any casing of its keys. SchemaStore’s schema lists them case-sensitively, and both apply in the merged file, so minimumlevel is flagged by SchemaStore’s half.
  • Flat keys. SchemaStore’s schema accepts the flat forms "WriteTo:Async" and "Enrich:0", which Serilog reads. They are flagged like the other keys that are not read. Set DovetailConfigurationSchemaStrict to false to leave the section open.

Serving the schema

Section titled “Serving the schema”

ASP.NET Core applications that reference Joinery.Dovetail.Hosting can serve the merged schema over HTTP at GET /.well-known/dovetail/configuration-schema. It is off by default. Setting DovetailConfigurationSchemaEndpoint to true generates a joint that maps it, and the MapDovetailConfigurationSchema(fallbackDirectory, environments) extension on IEndpointRouteBuilder, which Joinery.Dovetail.Hosting emits into ASP.NET Core projects, maps it by hand. The properties, the response and the security trade-off are described in Editor setup.

Shipping default values

Section titled “Shipping default values”

Defaults still live in a normal appsettings file in the library. The SDK renames it, packs it, and loads it into the host’s configuration, where the generated binder picks it up:

  • appsettings.{ext} becomes MyLibrary.{ext} (appsettings.Production.json becomes MyLibrary.Production.json), so several libraries can ship their own file into one output directory.
  • The files are packed under contentFiles/any/any/configuration/, copied to a same-solution host’s output directory through a ProjectReference, and restored from the package otherwise.
  • The generated joint loads, in ascending precedence, MyLibrary.{ext}, MyLibrary.{Environment}.{ext} and MyLibrary.local.{ext}. The local layer is never packed, and the SDK warns when no .gitignore at or above the project ignores appsettings.local.*.
  • JSON, YAML and TOML are supported. Opt in with DovetailEnableConfiguration; YAML is the default format, and DovetailEnableJsonConfiguration or DovetailEnableTomlConfiguration chooses another. Hosts with no file system (MAUI, Uno) read copies embedded in the assembly: DovetailEmbedConfiguration.
PropertyDefaultPurpose
DovetailEnableConfigurationfalseTurns the pipeline on. Existing consumers see no change until it or a format flag is set.
DovetailEnableYamlConfigurationtrue when no other format is setAdds the YAML provider. Setting it to true also enables the pipeline.
DovetailEnableJsonConfigurationfalseAdds the JSON provider. Setting it to true also enables the pipeline, replacing the YAML default.
DovetailEnableTomlConfigurationfalseAdds the TOML provider. Setting it to true also enables the pipeline, replacing the YAML default.
DovetailPackConfigurationtrue, false if not packablePacks the library’s configuration files into the package.
